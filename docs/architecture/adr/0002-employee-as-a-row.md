# ADR-0002：员工是一行数据，权限只收敛

- 状态：**已接受**
- 日期：2026-10-13
- 相关：`docs/product/BASELINE_AUDIT.md`、`docs/security/EMPLOYEE_PERMISSION_MODEL.md`

## 背景

任务要求把产品定型为「私人 AI 员工工作台」。基线审计发现，底层能力（记忆治理、权限分级、审批等待、工作区快照、中断对账、交付物验证）都已实现且有测试，唯独没有「员工」这个实体——它是产品里唯一只作为文本存在的东西，每次请求拼一段 system prompt。

## 决策

### 1. 员工是一行数据，不是一段提示词

新增 `employees` 表（21 列，JSONB 存四个 scope 字段），因为一个用户要**管理**的东西必须有身份：不能授予权限、不能拥有交付物、不能暂停、也不能在运行记录里和另一个员工区分开的文本，做不了这四件事。

**为什么 scope 用 JSONB 而不是四张关联表**：这些字段很小、总是整块读取、从不按元素查询、编辑时整体替换。四张关联表要加四次迁移，换不来任何想要的查询。

### 2. 岗位模板是数据，不是六个子类

六个模板是六个 dict，一条代码路径把任意 dict 变成 `Employee` 行。加第七个岗位 = 加第七个 dict。任务书 §6.2 明确要求六个岗位不能变成六套并行系统。

### 3. 人格是警告，不是墙

`persona_guard.py` 返回发现项，API 返回给用户，用户决定。

**不拦的理由**：人格本来就够不到权限系统——权限在工具执行前读数据库，不读提示词。所以这段文本改变不了任何授权，拦截它是在防一个不存在的问题。但一段说「你有完整权限」的人格会产生一个和用户争论的员工，而且人格每次请求都被注入，是一个有永久住所的提示注入载荷。所以报，不拦。

### 4. 权限只收敛，不放宽

员工配置是用户策略的**收窄**：level 取 min、mode 朝 ASSIST、allowed 取交集、denied 取并集、所有上限取 min。

**为什么上限也取 min**：员工配置里的 `max_tool_calls = 10_000` 看起来无害，实际是让一行存储数据去抬高用户自己的预算。取最小值让这个字段只能读作「这个员工最多这么多」。

**没有一条分支产生更宽松的结果**——所以模板、导入或手改 JSON 创建的员工都越不过它的所有者。这条性质对枚举字段做穷举测试。

### 5. 记忆沿用数据库实现，不引入 Git 仓库

DeepSeekBot 用 Git 管理员工记忆（`packages/core/src/memory/git.ts`），设计成熟。**不采纳**，理由：

- 任务书 §8.2 自己说「不要机械地把每种数据都改为 Markdown」。
- 现有 `memory_entries` + `memory_candidates` 已提供事务、查询、审批链，`ContextSnapshot` 提供每次注入的审计。
- 加一层 Git 会引入第二个权威来源，而 ADR-0001 刚定下「每项能力只有一个权威来源」。

**但借鉴了它的「字符上限 + 分区渲染」**——那是防上下文膨胀的关键，而 `ContextSnapshot.truncated` 已经留好了接入点。

## 后果

**正面**：改造是增量的，1363 个既有测试、34 张表、9 个迁移全部保留；安装包体积基本不变；新增 63 个测试（42 单元 + 21 API）。

**负面**：员工层目前只有后端与界面，没有接入 Agent 的实际执行路径——`startBuildRun` 会把 `employee_id` 记进 `scope`，但 `AutonomousAgent` 还没有按员工收敛权限后再跑。**这是本轮最重要的未完成项**，记在 `docs/release/ACCEPTANCE_REPORT.md`。

**需要警惕**：不能因为「员工」这个概念好看就把它到处塞。任务书 §23 明确把「只换应用名和图标，后台并没有员工实体」列为未完成任务的标志——反过来说，有了实体但没接进执行路径，也还没完成任务。

## 复核条件

- 当 `AutonomousAgent` 真正按员工收敛权限执行后，重新评估 `permission_profile` 的字段是否够用。
- 当记忆量增长到上下文预算经常触发截断时，重新评估是否需要文件化 + 版本回滚。
