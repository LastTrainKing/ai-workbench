# 第一章 项目背景

## 1.1 课题来源与选题依据

本课题为软件工程专业本科毕业设计，课题名称为 **AI Workbench——本地优先的 AI 知识管理与任务执行平台**。项目的设计动机来自一个在实践中反复出现、但在现有工具中很少被完整解决的问题：**个人知识管理与任务执行之间是割裂的**。

在典型的学习与工作场景中，用户往往同时使用三类工具：

1. **笔记与知识库工具**（如各类 Markdown 笔记软件、文档管理软件），用于沉淀资料；
2. **任务管理工具**（如待办清单、看板工具），用于安排执行；
3. **大语言模型对话工具**（如各类 AI 助手），用于问答、总结与生成。

这三类工具各自解决了一个环节，但彼此之间缺乏可靠的连接：笔记软件中的资料无法直接驱动任务生成；任务工具不知道执行某个任务应当参考哪份资料；AI 对话工具的回答往往无法追溯到具体来源，用户无法验证其真实性，也无法把一次有价值的问答沉淀回知识库。用户被迫在多个工具之间手工搬运信息，知识无法闭环地转化为行动，行动的结果也无法自动回流为新的知识。

本课题的目标，是把上述三个环节收敛到一个系统中，形成一条完整的闭环：

```
资料 → 知识 → 任务 → 执行 → 结果 → 再沉淀为知识
```

围绕这条闭环，本课题需要解决的核心工程问题包括：

* **如何把非结构化文档转化为可检索、可追溯的知识**，即文档解析、分块、向量化与混合检索；
* **如何让 AI 的回答有据可查**，即检索增强生成（RAG）与引用约束；
* **如何把知识自动转化为可执行的任务**，即任务规划器与任务树；
* **如何让 AI 具备执行能力而不失控**，即受控的工具调用 Agent；
* **如何让 AI 的每一次执行都可审计**，即执行轨迹（AI Run）的记录。

## 1.2 研究背景

### 1.2.1 大语言模型的落地瓶颈

大语言模型（Large Language Model, LLM）在文本理解与生成上表现出很强的一般能力，但在实际落地中面临三个公认的瓶颈：

**第一，事实性问题（幻觉）。** 模型可能生成看似合理但与事实不符的内容。在知识密集型场景中，这一缺陷是致命的：用户无法判断回答是否可以采信。

**第二，时效性与私域知识缺失。** 模型的参数知识固定在训练时刻，且不包含用户私有的文档。对于"根据我的资料回答问题"这类需求，纯参数化模型无能为力。

**第三，不可追溯。** 即使模型回答正确，用户也无法知道答案来自哪一段资料、依据是否充分。

检索增强生成（Retrieval-Augmented Generation, RAG）是针对上述瓶颈的主流技术路线：先从外部知识库检索与问题相关的片段，再把这些片段作为上下文交给模型生成答案。RAG 把"知识"从模型参数中解耦出来，使回答可以基于用户自己的资料，并且天然具备引用来源的可能。

### 1.2.2 Agent 与工具调用

如果说 RAG 解决的是"AI 能否正确回答"，那么工具调用（tool calling）解决的是"AI 能否正确做事"。具备工具调用能力的 Agent 可以读取数据、调用外部函数、写入结果，从而把自然语言目标转化为真实系统变更。

但 Agent 也带来了新的工程风险：它可能陷入无限循环、可能重复调用同一工具、可能越权写入大量数据、可能因为工具静默失败而给出错误结论。因此，**一个可用的 Agent 必须具备明确的边界、可观测的轨迹和可终止的循环**，而不是简单地把模型输出当作指令执行。

### 1.2.3 本地优先（Local-first）

本课题选择"本地优先"作为系统的基本立场，出于三方面考虑：

* **隐私。** 用户的笔记、文档、任务属于私密数据。本地优先意味着数据默认不出本机；只有在用户显式配置云端模型时，必要的检索片段才会发送给模型服务。
* **可用性。** 许多教学与个人场景没有稳定的云端 API 访问条件。系统必须能够在**零 API Key、零外部依赖**的前提下完整运行，而不是在缺少密钥时直接不可用。
* **可复现性。** 毕业设计需要可复现的验证结果。一个不依赖外部服务、行为确定的系统，更容易被评审者复现。

正是基于这一立场，本课题实现了一个**确定性离线推理引擎**（deterministic offline engine）作为兜底：当没有配置任何云端密钥、也没有本地模型服务时，系统使用基于哈希词袋的向量化、基于句子打分的抽取式问答、基于 TF-IDF 的关键词与术语抽取、基于标题的计划生成，使全部业务流程仍然可用。这一点是本项目与"必须联网才能演示"的同类作品的重要区别。

### 1.2.4 个人知识管理与任务执行的演进

个人知识管理并非新问题。从早期的文件夹与标签体系，到以"卡片盒笔记法"（Zettelkasten）为代表的双向链接笔记，再到近年流行的"第二大脑"（Second Brain）理念，其共同目标是让零散信息在积累中形成可复用的结构。与此同时，任务管理从简单的待办清单演化为看板（Kanban）、层级化任务树与依赖关系图，用于表达执行的先后与结构。

然而，这两条脉络长期平行发展：知识管理关注"知道什么"，任务管理关注"做什么"，二者之间缺少自动化的桥接。大语言模型的出现首次使这种桥接成为可能——模型可以阅读资料并据此生成任务，也可以在执行后把结果总结为新的知识。本课题正是抓住这一机会，把"知识"与"任务"通过模型能力真正连接起来，并进一步把连接过程本身变成可追溯、可审计的数据。

值得注意的是，这种连接必须建立在"有据可依"之上：如果模型可以脱离用户资料凭空生成任务或结论，那么连接得越快，误导的风险也越大。因此本课题把**引用约束**与**执行轨迹**作为不可妥协的设计前提，而不是可选的附加功能。

## 1.3 国内外研究与应用现状

### 1.3.1 检索增强生成

RAG 由 Lewis 等人于 2020 年提出，其核心思想是把参数化记忆与非参数化记忆结合。此后，工业界与学术界围绕 RAG 形成了较为成熟的工程范式：

* **检索阶段**：稠密向量检索（基于嵌入模型与向量数据库）与稀疏检索（基于 BM25 等词频模型）各有优势，混合检索（hybrid retrieval）通过融合两者提升召回质量；
* **重排阶段**：使用交叉编码器（cross-encoder）或轻量词法特征对候选片段重排；
* **生成阶段**：将检索片段组装为上下文，约束模型"仅依据上下文作答"并给出引用。

主流向量数据库（如 Milvus、Qdrant、Weaviate、pgvector）已经能够支撑上述流程。开源框架（如 LangChain、LlamaIndex）提供了较高层次的封装。

### 1.3.2 任务规划与 Agent

以 ReAct（Reasoning + Acting）为代表的范式把"推理"与"行动"交替进行，成为工具调用 Agent 的基础。此后出现了大量 Agent 框架。它们普遍支持多工具、多步循环与记忆，但也普遍存在**轨迹不透明、失败不显式、边界不清晰**的问题。

### 1.3.3 现有方案的不足

综合来看，现有方案在以下方面仍存在不足，也正是本课题的切入点：

1. **知识、任务、执行三者割裂。** 多数产品只覆盖其中一到两个环节，缺少"资料驱动任务、任务关联资料、执行结果回流知识"的完整闭环。
2. **离线不可用。** 多数方案强依赖云端 API，缺少可用的本地兜底，无法在无密钥环境下完整演示。
3. **可追溯性弱。** AI 执行缺少统一、结构化、可查询的轨迹记录。
4. **工程细节缺失。** 面向教学与毕业设计的完整工程实现（分层架构、错误分类、重试策略、缓存降级、后台任务可靠性）较少系统性地呈现。

为更清楚地定位本课题，下表按能力维度对几类典型方案作定性对比（"部分"表示仅覆盖某一环节或能力有限）：

| 能力维度 | 纯笔记/知识库工具 | 纯任务管理工具 | 通用 AI 对话工具 | 通用 Agent 框架 | 本课题 |
|---|---|---|---|---|---|
| 资料沉淀与检索 | 强 | 无 | 无 | 部分 | 强（混合检索） |
| 有据可查的问答（引用） | 部分 | 无 | 弱 | 部分 | 强（引用约束） |
| 知识驱动任务生成 | 无 | 无 | 部分 | 部分 | 强（规划器） |
| 任务与知识的关联 | 无 | 部分 | 无 | 部分 | 强（知识关联） |
| 受控的工具执行 | 无 | 无 | 无 | 部分 | 强（有界 Agent） |
| 统一执行轨迹 | 无 | 无 | 弱 | 弱 | 强（AI Run） |
| 离线可用 | 强 | 强 | 无 | 部分 | 强（离线引擎兜底） |

该对比表明：本课题并非在单一维度上追求极致，而是在**"闭环完整性"与"可追溯性"**上形成差异，并补齐离线可用这一常被忽略的工程前提。

## 1.4 本课题的主要工作

本课题完成了一个可运行、可验证的完整系统，主要工作包括：

### 1.4.1 系统设计与实现

* **分层后端架构**：采用 `API → Service → Repository → Model/Infrastructure` 的单向依赖分层，并以代码审查与类型检查约束层次规则；
* **22 张数据表**：覆盖用户、项目、知识库、文档、分块、标签、概念、任务、依赖、笔记、提示词、AI 执行轨迹、后台任务与活动流；
* **文档摄取流水线**：上传 → 校验 → 存储 → 解析（Markdown/TXT/PDF）→ 归一化 → 分块 → 向量化 → 写入向量库；
* **混合检索**：Qdrant 稠密检索 + PostgreSQL 稀疏候选生成 + 进程内 BM25 打分 + 归一化加权融合 + 词法重排；
* **受约束的 RAG 问答**：查询改写 → 混合检索 → 词法重排 → 预算化上下文装配 → 生成 → 引用抽取与映射；
* **任务规划器**：目标 → 阶段 → 任务 → 子任务，带工作量估算、依赖与可验证的完成标准；
* **工具调用 Agent**：受步数、写操作数量与重复调用检测约束的有界循环，11 个注册工具；
* **AI 执行轨迹**：每次执行记录提示词名称与版本、检索来源、工具调用、Token 用量、时延、重试与错误；
* **AI Provider 抽象**：OpenAI 兼容、Ollama 本地、确定性离线引擎三种后端，切换仅需配置。

### 1.4.2 工程保障

* **后台任务**：基于 PostgreSQL 的自建队列，使用 `SELECT ... FOR UPDATE SKIP LOCKED` 安全领取，具备有界重试、指数退避、陈旧任务恢复与任务级超时；
* **缓存降级**：Redis 缓存检索结果、提示词、统计与嵌入，缓存故障时降级为无缓存并记录告警，绝不导致请求失败；
* **可观测性**：每请求 `request_id`、每 AI 执行 `run_id`、结构化单行日志、响应头 `X-Request-ID` 与 `X-Process-Time-Ms`、`/metrics` 端点；
* **安全措施**：扩展名白名单与 MIME 一致性校验、流式大小限制、UUID 生成存储文件名、存储根目录包含性检查、JWT（HS256）与 bcrypt 口令哈希、Pydantic 全量入参校验、参数化 SQL、CORS 白名单、日志密钥脱敏、LIKE 通配符转义。

### 1.4.3 验证工作

* **单元测试**：分块器、离线引擎、重试助手、安全与文件处理；
* **端到端冒烟测试**：16 组共 75 项断言，覆盖健康检查、认证、知识库、文档摄取、三种检索模式、RAG、规划器、Agent、文档分析、执行轨迹、提示词版本、仪表盘与图谱、错误处理、任务工作流与级联删除；
* **实测结果**：PostgreSQL 16.4、Redis、Qdrant 1.12.4 均可连通；四份样例文档分别切分为 8/7/1/3 个分块，嵌入成功率 100%；75/75 项检查通过（测试日期 2026-10-03）。

## 1.7 本章小结

本章阐述了课题的来源与动机：个人知识管理、任务执行与 AI 对话三类工具彼此割裂，导致知识无法闭环转化为行动。本章进一步分析了 RAG 与 Agent 的技术背景、本地优先立场的必要性，以及现有方案的不足，并通过能力维度对比定位了本课题在"闭环完整性、可追溯性、离线可用"上的差异。最后概述了本课题的主要工作、术语约定与论文结构。后续章节将围绕需求、设计、实现与测试逐层展开。
