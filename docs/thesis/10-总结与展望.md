# 第十章 总结与展望

本章总结全文工作，给出主要结论与创新点，并**如实**列出当前实现的不足与后续
工作方向。凡本快照中不存在的内容，均在本章明确标注为"未实现"。

## 10.1 全文工作总结

本文围绕"个人与小团队如何把零散资料转化为可执行、可追溯的成果"这一问题，设计
并实现了一个本地优先的 AI 知识与任务执行平台 **AI Workbench**。系统闭合了一条
完整的循环：

```
资料 → 知识 → 任务 → 执行 → 结果 → 再沉淀为知识
```

围绕这条循环，本文完成了以下工作：

1. **需求与可行性分析**（第 2、3 章）：界定用户角色与用例，提炼 32 条功能需求与
   12 条非功能需求，从技术、经济、操作、法律、进度五个维度论证可行性。
2. **总体设计**（第 4 章）：确立 `API → Service → Repository → Model/Infrastructure`
   分层架构，AI 层与数据库驱动 worker 作为独立关注点，给出进程拓扑、请求生命周期
   与各状态机。
3. **数据库设计**（第 5 章）：设计 22 张表，覆盖身份、工作区、知识、任务、沉淀、
   AI 治理与运行、队列与审计七个业务域，并以精心的级联策略在删除与溯源之间取得
   平衡。
4. **详细设计**（第 6 章）：给出接口、服务、仓储、基础设施四层的内部设计，以及
   文档摄取流水线、后台执行器与横切关注点的实现路径。
5. **AI 模块设计**（第 7 章）：设计提供商抽象与优雅降级、真实可用的离线引擎、
   RAG 混合检索管线、有界工具调用智能体、提示词版本化与执行追踪。
6. **系统实现**（第 8 章）：说明真实环境下的实现方式与实现过程中修复的六类缺陷。
7. **系统测试**（第 9 章）：给出三层测试策略与实测结果，端到端 **75/75 通过**。

## 10.2 主要成果

### 10.2.1 功能成果

系统在真实基础设施（PostgreSQL 16.4、Redis、Qdrant 1.12.4）上完成了端到端验证，
实现了以下能力：

- **知识摄取**：Markdown / TXT / PDF 的上传、解析、分块、嵌入与向量索引，含去重、
  大小限制与安全文件名处理。
- **有据可依的问答（RAG）**：查询改写 → 稠密 + 稀疏混合检索 → 词法重排 →
  预算内上下文组装 → 生成 → 引用抽取，答案强制携带引用。
- **任务规划**：从目标生成"目标 → 阶段 → 任务 → 子任务"树，含工时估算、依赖与
  可验证的完成标准。
- **工具调用智能体**：在类型化工具注册表上运行的有界 ReAct 循环，智能体只能通过
  工具触达数据库。
- **AI 执行追踪**：每次运行记录提示词名**与版本**、检索来源、工具调用、Token 用量、
  延迟、重试与错误。
- **提供商抽象**：OpenAI 兼容、Ollama（完全本地）或确定性离线引擎，切换只需改配置。

### 10.2.2 工程成果

- 后端 **77 个 Python 文件、约 13973 行**，测试 **14 个文件、约 2618 行**。
- 端到端冒烟测试 **16 组 75 断言**，实测全部通过。
- 发现并修复 **6 类真实缺陷**，含导致进程冻结的事件循环饥饿（D1）。

## 10.3 主要特色

本文认为以下三点是系统的核心特色，且均有实现支撑：

### 10.3.1 零依赖可运行的优雅降级

系统提供真实的**离线启发式引擎**（`HeuristicLLMProvider` /
`HeuristicEmbeddingProvider`），它不是占位桩，而是实现了分词、哈希 n-gram 嵌入、
抽取式问答、摘要、知识抽取、任务规划与智能体策略的完整算法集合。当未配置
`AI_API_KEY` 或云端不可达时，系统自动降级到离线引擎，并把降级状态**显式暴露**
在 `GET /health/deps`、仪表盘与每条 `ai_runs` 记录中，**从不假装离线结果是云端
模型的产物**。这使得系统在无网络、无 Key 的环境下仍可完整演示与使用。

### 10.3.2 可追溯性贯穿始终

每一次 AI 调用都写入 `ai_runs`，记录提供商、模型、提示词名与版本、检索元数据、
Token、延迟、成本与错误；每一条引用写入 `ai_run_sources`，且其 `document_id`
为 `SET NULL`——即使源文档被删除，引用的标题与片段文本仍然保留。因此任何一次
回答都能被回溯到它的输入证据，且溯源信息不会因删除而丢失。

### 10.3.3 不信任模型输出的防御式设计

模型返回的内容一律先经归一化与校验：`load_json_object` 宽容解析 JSON；
`PlannerService._normalise_plan` 配合 `_safe_int` / `_safe_priority` 兜底非法值；
智能体工具参数逐个校验；`_sanitize` 裁剪超大载荷。系统在设计上把模型视为**不可信
输入源**，而非可信组件。

## 10.4 不足与后续工作

本节如实列出当前实现的局限。这些局限来自本仓库快照的实际状态，读者可逐一核对。

### 10.4.1 前端缺少浏览器端到端自动化测试

前端工程（React 18 + TypeScript + Vite 5 + Tailwind）位于 `frontend/`，共 18 个页面，
覆盖仪表盘、知识库、文档、检索、RAG 问答、任务规划、任务、项目、笔记、Agent、
AI 运行、关系图谱与设置，并配有 114 个 Vitest 测试（含一个对
`http://127.0.0.1:8000` 真实后端的接口流程测试）。

不足在于：**没有接入 Playwright 等浏览器端到端测试**，页面级交互（登录、上传、
命令面板、图谱拖拽）目前只通过截图脚本 `scripts/capture-screenshots.mjs` 人工核验，
未纳入自动化回归。

**后续工作**：接入 Playwright，把关键用户路径（登录 → 建知识库 → 上传 → 检索 →
提问 → 规划 → Agent 执行）固化为 CI 中的浏览器测试。

### 10.4.2 模式缺少迁移版本化（已解决，保留作为设计说明）

本项在开发过程中确实存在：早期 `backend/alembic/versions/` 为空，模式依赖启动时的
`Base.metadata.create_all`，它**只能建表、不能改表**，也无法回答"库对应哪个代码版本"。

现已补齐：`backend/alembic/versions/20261003_0159_368e36738b68_initial_schema.py`
是完整基线迁移（531 行，22 张表）。验证方式为在空库上执行
`alembic upgrade head` 得到 23 张表（22 张业务表 + `alembic_version`），
`alembic check` 输出 `No new upgrade operations detected`（即模型与迁移无漂移），
`alembic downgrade base` 可干净回退。

**后续工作**：保持"先改模型、再生成迁移、最后跑 `alembic check`"的流程，
并在 CI 中加入迁移双向测试。

### 10.4.3 容器化路径未验证

项目**刻意不使用 Docker**（开发机无 Docker Desktop、Hub 不可达），改用原生 Windows
二进制经 `scripts/infra-start.ps1` 启动。仓库中**包含** `docker-compose.yml` 与
`backend/Dockerfile`、`frontend/Dockerfile`、`worker/Dockerfile`，但该路径
**未在本机构建或启动**，`FINAL_CHECKLIST.md` 中对应两项记为 N/A。

一键启动脚本已提供：Windows 用 `start.bat` / `stop.bat`（已实测），
Linux/macOS 用 `start.sh` / `stop.sh`（已提供，未实测）。

**后续工作**：在有 Docker 的环境中构建并验证 compose 编排，并在 Linux 上实测
`start.sh`。

### 10.4.4 检索质量缺少量化评估

系统实现了混合检索、融合与词法重排，但**未对标注集计算 recall@k、MRR、nDCG 等
指标**；检索质量仅以"返回命中""分数组件存在"作断言。重排为**词法重排**，未引入
交叉编码器（cross-encoder）重排模型。

**后续工作**：构建带标注的检索评测集，引入交叉编码器重排并量化对比，调优
`HYBRID_ALPHA` 与重排权重。

### 10.4.5 测试覆盖存在明显缺口

- **无负载/性能测试**：无吞吐、并发、内存基准；多 worker 的
  `FOR UPDATE SKIP LOCKED` 认领未做并发压力验证。
- **无安全扫描**：未做 SAST/DAST、依赖漏洞扫描或渗透测试。
- **无故障注入测试**：Redis/Qdrant 降级路径已实现但未自动测试。
- **云端提供商无自动化测试**：套件强制离线引擎，OpenAI 兼容与 Ollama 提供商
  仅人工验证。
- **前端测试不在本套件内**：前端为独立工作流（Vitest + Testing Library），其测试
  不由本后端套件运行。

**后续工作**：补充性能基准、并发 worker 压测、混沌/故障注入测试、云端提供商的可
模拟（mock）测试，以及前端组件与浏览器端到端测试。

### 10.4.6 功能边界

- **无 OCR**：扫描版 PDF 无法处理，会显式失败；无 OCR 路径。
- **解析格式有限**：仅支持 Markdown / TXT / PDF，未支持 DOCX、PPTX、HTML 等。
- **成本估算为量级估算**：`estimate_cost` 使用小型价目表，对未知模型返回 0，仅作
  量级参考。
- **无多租户隔离的强保证**：系统面向本地单机多用户，未实现组织级权限模型与
  资源配额。
- **仓库工程配套缺失**：仓库中无 `README`、根目录无 `.gitignore`，且当前目录不是
  git 仓库；根目录 `tests/` 为空目录。

**后续工作**：按需扩展解析格式与 OCR；补充工程配套文件；若面向团队部署，设计
组织级权限与配额模型。

### 10.4.7 文档范围与一致性说明

需要特别说明的是，本文档集描述的是**后端完整、前端在建**的状态。论文第 4 至第 9
章聚焦后端的接口、服务、AI 与数据设计，前端页面级实现细节不在其中。凡本文提到
"前端"的地方，均指位于 `frontend/` 的并行工作流，而非本文档集的交付内容。读者可
在 `docs/` 与 `docs/thesis/` 中逐条核对本文的所有技术论断，包括本文第 10.6 节给出
的"章节与实现对应关系表"。

## 10.5 展望

从更长远的角度看，AI Workbench 可沿以下方向演进：

1. **从个人工具到团队协作**：引入组织、成员与权限模型，使知识与任务可在团队内
   共享与协作，同时保持可追溯性。
2. **从词法重排到语义重排**：引入交叉编码器与学习排序，配合评测集持续优化检索
   质量。
3. **从单机到可水平扩展**：把数据库驱动的 worker 扩展为多进程/多机部署，配合
   迁移版本化与容器化，形成可运维的生产形态。
4. **从被动检索到主动沉淀**：让系统在任务执行完成后自动提炼结果、生成笔记并
   回灌知识库，进一步强化"再沉淀为知识"的闭环。
5. **从单一模态到多模态**：扩展对图片、音视频等资料的处理能力。

## 10.7 结束语

本文完成了一个可运行、可验证、可追溯的本地优先 AI 知识与任务执行平台。系统的
价值不在于堆叠功能，而在于**把"证据"与"行动"用一条可追溯的链路连接起来**：每一
条知识都有来源，每一个任务都有依据，每一次 AI 执行都有记录。同时，本文坚持如实
描述实现的边界——前端页面在建、迁移未版本化、部署未容器化、检索质量未量化——因为
一份诚实的工程文档，其价值正在于让读者能够打开代码库，逐条确认所读即所得。
