# 第十一章 创新点

本章说明本系统与"又一个 AI 聊天应用"或"又一个 Agent 框架"的区别。下面六点都
不是设计意图，而是**已经在代码里实现、并被真实运行验证过**的机制；每一点都给出
可核对的证据位置。

---

## 11.1 交付闭环：把"产出"当成起点而不是终点

多数 AI 应用的能力边界是"生成一段内容"。本系统的边界是**一条闭合的回路**：

```
资料 → 知识 → 规划 → 产出 → 机器验证 → 用户验收 → 偏好沉淀 →（下一次产出）
```

回路的关键是最后一根箭头。系统在用户"看过并表态"之前不算完成：

- 产出的文件必须能被独立读回（`document_read` / `python-pptx` / `openpyxl`），
  读回结果作为证据保存，而不是由模型自述；
- 用户可以**退回**，退回必须给理由（空理由返回 422）；
- 退回理由进入记忆评估器，成为关于用户标准的陈述；
- 下一次同类产出，这条陈述会被注入到规划器与执行器的上下文里。

**证据：** Demo 1 两版对比。第一版 11 页 / 0 图 / 70,538 B；退回后（"图表太少，
文字堆得太满，页数也偏多"）第二版服从 15 分钟硬约束并带上了图表，两版之间的差异
可以在 `deliverables.parent_id` 链上直接走出来。

## 11.2 验证与验收的分离

`Deliverable` 上有两个独立字段：

| 字段 | 判定者 | 含义 |
|---|---|---|
| `verified` | 机器 | 文件真实存在、能打开、页数/行列数/段落数与声明一致 |
| `accepted` | 用户 | 这就是我要的东西 |

`accepted` 在用户表态前是 `null`——"还没看"和"不满意"是两个不同的状态。

**为什么要分开：** 一份文件可以通过全部机器检查，同时被用户拒绝。这个组合是
整个系统里信息量最大的事件：它说明"机器能证明的东西"和"用户在意的东西"之间存在
一个缺口，而这个缺口正是产品要收集的信号。把两者合并成一个布尔值，就恰好丢掉了
这个信号。

**这条设计原则可以推广：** 当两个判断由不同主体做出时，不要让它们互相覆盖。

---

## 11.3 记忆是执行的沉淀物，不是聊天记录

本系统记忆的触发点是**交付验收**，不是每一轮对话。

区别在于证据强度：

- 对话里的一句"我比较喜欢简洁"是一个**推测**——用户说了一句话，系统去推断；
- 用户在看过一份真实产出之后按下"退回"并写下原因，是一个**陈述**——关于他持有的
  标准，由唯一知道这个标准的人做出。

因此，被送去评估的输入是"用户退回了《毕业设计答辩.pptx》第 1 版，理由是……"，
而不是对话历史。Agent 运行的目标（用户自己的原话）也会被送去评估，运行轨迹不会
——那是机制，不是偏好。

**配套的"精纯"原则：** 记错比不记更糟。评估管线依次经过规则预过滤（寒暄、一次性
事务、敏感信息在调用模型之前就被丢弃）、结构化判定、去重、冲突检测、分级落库；
置信度低于 0.5 直接丢弃，0.5–0.8 只能成为待确认候选。实测中九次评估写入零条记忆，
这个比例是设计目标而不是故障。

**来源可追溯：** 每条记忆记录 `structured.origin`——哪一次交付、第几版、用户当时的
原话。记忆页把它渲染出来并提供"查看那次交付"的跳转。没有来源的记忆是一句无出处的
断言，不可复核。

## 11.4 偏好是约束，不是指令

上一轮真实出现过的失败：

```
目标：做一份 15 分钟的答辩 PPT
偏好：页数更少
结果：2 页
```

没有任何报错，所有检查都通过。问题在于"页数更少"被当成了**要做的事**，而不是
**做这件事时的标准**——而一个 15 分钟的汇报有它的物理下限。

系统实现的语义是：

```
任务目标（硬约束）  >  长期偏好（软约束）  >  默认行为
```

三点具体做法：

1. **硬约束在代码里推导，不由模型决定。** `derive_constraints()` 从目标文本里读出
   时长，按一张有据可查的语速表换算成页数区间（15 分钟 → 10~14 页，3 分钟 → 3~5 页）。
   若交给模型，"页数更少"就会与一个"模型只是被告知过"的时长放在一起权衡，而同时
   满足两个要求时，模型有时会满足错的那个。代码里推导出的数字无法被谈判掉。
2. **偏好按"意图"逐条解析，不按句子。** 一条学到的记忆可能写成"用户偏好演示文稿
   图表更多、页数更少"——一句话里两个偏好。整句匹配只会满足先被检测到的那个，静默
   丢掉另一个。系统为每个意图单独给出结论：`applied` / `bounded` / `unsatisfiable`。
3. **取舍说明是生成的，不是要求的。**"它有没有解释为什么是 10 页"必须能从输出里
   回答，而模型恰好没提就会让诚实答案是"没有"。因此这段文字由代码确定性地拼出来，
   附在运行报告末尾。

**无法执行的偏好必须报告。** 一个被静默忽略的偏好比一个被明确拒绝的偏好更糟，
因为用户会以为它生效了。`unsatisfiable` 的偏好同时进入事件流和最终报告。

## 11.5 失败可见性原则

本项目在开发过程中反复踩到同一个形状的 bug：

```python
try:
    ...
except Exception:
    return None      # 失败被转换成一个看起来合理的空值
```

五个致命缺陷都是这个形状。最典型的一例就在交付路径上：`_render_chart()` 在图表
渲染失败时返回 `None` 并打一条 warning，于是"图表没画出来"和"这一页本来就没有
图表"变得无法区分——幻灯片出来了，结果是成功的，用户"图表更多"的偏好被静默地没有
执行。**一个调用者看不见的失败不是被处理的失败，而是被藏起来的失败。**

系统为此确立的规则：

- 失败必须**以调用者能区分的方式**呈现（抛异常、返回 `ok=False` 并说明原因、
  或写入结构化证据），不能降级为一个中性的空值；
- 会产生副作用的工具必须**如实报告它产出了什么**（`images` / `chart_failures` /
  `slides_dropped`），而不是报告"成功"；
- 运行状态与产出物必须一致：一次没有走完的运行留下的文件被登记为"部分完成"，
  并且不再挂 `verified=true`。

这条原则的收益是直接的：正因为图表失败是响亮的，才暴露出真正的契约缺陷——模型
发送的 `series` 是 `[{name, data}]`（字段名最自然的读法），而实现只接受一个私有
形状。**如果当初那个 `None` 没有被去掉，这个 bug 会一直以"用户偏好没生效"的形式
存在。**

## 11.6 本地优先

- 所有个人数据（PostgreSQL、Qdrant、上传文件、工作区、日志）都在本机 `.runtime/`
  下，不出机器；
- 模型层是可替换的：云端提供商、本地 Ollama、以及一个**不依赖任何外部服务的
  确定性离线引擎**。没有 API Key 时自动降级，并且降级状态在 `/health/deps` 与每条
  `ai_runs` 记录上可见，不假装是云端回答；
- 嵌入向量在离线模式下用确定性哈希，不下载任何模型文件；
- 以桌面应用形态运行：原生窗口、无浏览器、无地址栏；关闭窗口时由 Windows 作业对象
  保证后端进程一并退出，不留残留进程。

## 11.7 与常见方案的差异（小结）

| 维度 | 常见做法 | 本系统 |
|---|---|---|
| 成功判定 | 模型自述"已完成" | 工具退出码 + 独立读回证据 |
| 产出之后 | 结束 | 机器验证 → 用户验收 → 沉淀 |
| 记忆来源 | 对话历史 | 交付验收事件 |
| 偏好处理 | 直接当指令执行 | 硬约束 > 偏好 > 默认，冲突时说明取舍 |
| 无法执行的偏好 | 静默忽略 | 明确报告 |
| 工具失败 | 返回空值 / 打日志 | 以调用者可区分的方式呈现 |
| 运行状态与产物 | 各自记录 | 强制一致（COMPLETED / PARTIAL / FAILED） |
| 数据位置 | 云端 | 本机，且模型可替换为离线 |
