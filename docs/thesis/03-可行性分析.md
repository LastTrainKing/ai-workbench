# 第三章 可行性分析

## 3.1 分析目的与方法

可行性分析的目的是在投入实现之前，判断课题在**技术、经济、操作、法律与进度**五个维度上是否成立，识别主要风险并给出规避措施。本章逐项论证，并给出结论。

## 3.2 技术可行性

### 3.2.1 技术栈成熟度

本课题所选技术栈均为成熟、文档完备、社区活跃的开源组件，不存在需要自行发明的基础能力：

| 方向 | 选型 | 成熟度判断 |
|---|---|---|
| Web 框架 | FastAPI | 主流异步 Web 框架，自带 OpenAPI 文档生成 |
| ORM | SQLAlchemy 2.0（异步）+ asyncpg | 主流 ORM，2.0 版本原生支持异步 |
| 数据校验 | Pydantic v2 | 主流校验库，性能与类型体验良好 |
| 关系数据库 | PostgreSQL 16 | 成熟稳定，支持 `FOR UPDATE SKIP LOCKED`、JSONB |
| 缓存 | Redis 5 | 成熟稳定 |
| 向量数据库 | Qdrant 1.12 | 主流向量库，支持负载过滤与按维度建集合 |
| 向量化与生成 | OpenAI 兼容接口 / Ollama | 接口标准化，可替换 |
| 文档解析 | pypdf | 成熟的 PDF 文本抽取库 |
| 认证 | PyJWT + bcrypt | 标准实现 |

结论：**技术栈无不可控依赖，技术可行性成立。**

### 3.2.2 关键技术的可实现性

**（1）混合检索的可实现性。**
稠密检索依赖向量库，稀疏检索需要一个词频模型。本项目刻意不依赖 PostgreSQL 的 `to_tsvector`，原因是 PostgreSQL 默认不带中文分词器，在标准安装上对中文支持不足。因此稀疏检索采用"`ILIKE` 候选生成 + 进程内 BM25 打分"的方案：先用 SQL 做低成本候选召回，再在进程内用 BM25 公式对候选打分。这一方案在技术上完全可实现，且不引入额外依赖。融合采用归一化加权求和，实现简单、可解释。

**（2）确定性离线引擎的可实现性。**
在无模型可用时，需要一种**确定性、无依赖**的文本处理方案。本课题采用哈希词袋向量化（token 经 BLAKE2b 哈希到固定维度桶，使用次线性词频与 L2 归一化），配合抽取式问答（句子按查询词覆盖、词汇密度与位置先验打分）。这是一类成熟的经典方法，实现难度可控，且不下载任何模型文件。

**（3）受控 Agent 的可实现性。**
Agent 的循环控制是纯工程问题：限制最大步数、每步一个工具、对调用签名去重、限制写操作数量。这些约束均可在执行器中直接实现，不依赖模型本身的能力。

**（4）后台任务的可靠性。**
不引入 Celery 等外部中间件，而是使用 PostgreSQL 表作为队列，借助 `SELECT ... FOR UPDATE SKIP LOCKED` 实现安全领取。该特性自 PostgreSQL 9.5 起提供，16 版本稳定可用。有界重试、指数退避、陈旧任务恢复与任务级超时均可在应用层实现。

结论：**关键技术均有明确、可行的实现路径，技术可行性成立。**

### 3.2.3 技术风险与规避

| 风险 | 影响 | 规避措施 |
|---|---|---|
| 云端模型不可用或未配置密钥 | 演示中断 | 实现确定性离线引擎兜底，并在健康检查与执行轨迹中如实标注 `degraded` |
| 向量库不可达 | 语义检索失败 | 混合模式下降级为关键词检索并记录告警；语义模式下明确报错 |
| 缓存不可达 | 性能下降 | 降级为无缓存，请求仍然成功 |
| 嵌入维度变化 | 向量库集合不兼容 | 集合按实际维度按需创建；维度不一致时给出重建指引 |
| 后台任务异常退出 | 任务卡死 | 陈旧任务恢复 + 任务级超时 + 有界重试 |
| 中文分词缺失 | 稀疏检索效果差 | 自研语言无关分词（拉丁词 + 中文字符二元组），不依赖数据库分词 |

### 3.2.4 关键选型的对比论证

为避免"默认采用最流行方案"，下面对三处关键选型给出对比论证。

**（1）后台队列：数据库表队列 vs Celery。**

| 维度 | Celery + Broker | PostgreSQL 表队列（本课题） |
|---|---|---|
| 额外组件 | 需要 Redis/RabbitMQ 作为 broker | 复用已有的 PostgreSQL |
| 部署复杂度 | 高（需管理 broker 与 worker 进程） | 低（worker 为进程内任务） |
| 事务一致性 | 入队与业务写入不在同一事务 | 入队与业务写入可在同一事务 |
| 并发领取 | 由 broker 保证 | `FOR UPDATE SKIP LOCKED` 保证 |
| 适用规模 | 大规模分布式 | 单机/小团队 |

本课题面向本地优先的单机场景，任务量可控，复用 PostgreSQL 可显著降低组件数量与
部署复杂度，且天然获得"业务写入与入队同事务"的一致性优势。因此**刻意不引入
Celery**。

**（2）向量库：Qdrant vs pgvector。**

| 维度 | pgvector | Qdrant（本课题） |
|---|---|---|
| 部署 | 作为 PostgreSQL 扩展 | 独立进程 |
| 过滤检索 | 需与关系查询混合，写法较复杂 | 原生载荷索引与按字段过滤 |
| 与关系库耦合 | 高（向量与元数据同库） | 低（职责分离） |
| 运维 | 只需维护一个数据库 | 需维护一个额外进程 |

本课题选择 Qdrant，是为了把"关系型事务"与"向量近邻搜索"交给各自最合适的引擎，
并以 `vector_id` 建立映射。代价是多维护一个本地进程，由 `infra-start.ps1` 统一
管理，成本可控。

**（3）稀疏检索：数据库全文检索 vs 进程内 BM25。**

PostgreSQL 默认不带中文分词器，标准安装对中文全文检索支持不足；引入
`zhparser` 等扩展会提高部署门槛。因此本课题采用"`ILIKE` 低成本候选召回 + 进程内
BM25 打分"，既不依赖数据库扩展，又能获得可解释的词频打分。缺点是候选召回依赖
`ILIKE` 的匹配质量，这一取舍在第五章的检索设计中有进一步说明。

结论：**三处关键选型均经过对比论证，选择依据与代价清晰，技术可行性成立。**

## 3.3 经济可行性

### 3.3.1 成本构成

| 成本项 | 说明 | 金额 |
|---|---|---|
| 软件许可 | 全部组件为开源软件（MIT/BSD/Apache 等） | 0 |
| 开发环境 | 使用个人计算机 | 0 |
| 基础设施 | 本机运行 PostgreSQL/Redis/Qdrant，不产生云资源费用 | 0 |
| 模型调用 | 离线引擎零成本；若配置云端模型，按量计费 | 视使用而定 |
| 人力 | 毕业设计为个人独立完成 | 不计入 |

### 3.3.2 成本控制设计

系统在成本控制上有明确设计：

* **离线兜底**使演示与验证不需要任何模型费用；
* **嵌入缓存**以"内容哈希 + 模型"为键，同一文本永不重复向量化，是重复处理场景下最大的成本节省点；
* **检索缓存**避免相同查询重复计算；
* **成本估算**仅对已知模型家族给出量级估算，未知模型返回 0 而不猜测，避免误导。

### 3.3.3 成本效益分析

本课题的成本效益体现在"以极低成本获得完整闭环能力"：

| 维度 | 说明 |
|---|---|
| 直接成本 | 软件许可 0 元；基础设施本机运行 0 元；离线引擎 0 元 |
| 可选成本 | 若配置云端模型，按量计费，且由缓存与预算化上下文装配控制用量 |
| 收益 | 知识、任务、执行三者闭环；AI 回答有据可查；执行全程可审计 |
| 隐性成本规避 | 不引入 Docker、Celery、外部 broker、数据库分词扩展，减少运维与学习成本 |

需要客观指出：本课题的"零成本"建立在使用个人计算机与本地开源组件之上，未计入
硬件折旧与人力投入。若迁移到云端部署，则会产生服务器与可能的模型调用费用。因此
"成本极低"的结论**仅适用于本地优先的使用场景**。

结论：**课题总成本极低，经济可行性成立。**

## 3.4 操作可行性

### 3.4.1 部署操作

系统刻意规避了 Docker，改为下载原生二进制并在项目目录内以项目级进程运行，原因是开发机不具备 Docker 环境。启动流程被封装为两条命令：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\fetch-runtime.ps1   # 下载运行时
powershell -ExecutionPolicy Bypass -File scripts\infra-start.ps1     # 启动基础设施
powershell -ExecutionPolicy Bypass -File scripts\dev.ps1 start       # 启动应用
```

脚本具备幂等性：重复执行不会破坏已有数据；PostgreSQL 集群仅在首次运行时初始化；角色与数据库的创建带存在性判断。所有进程、数据文件与日志均位于仓库内，不注册系统服务、不修改系统配置。

### 3.4.2 使用操作

* 提供 `/docs` 交互式 API 文档，评审者可直接在浏览器中调用接口；
* 提供 `scripts/smoke_test.py` 一键端到端验证，输出逐项通过/失败与汇总；
* 提供 `python -m app.cli check` 一键检查全部外部依赖；
* 提供 `python -m app.cli stats` 打印各表行数，便于观察数据。

### 3.4.3 运维与故障处理

系统在设计上把常见故障的处置方式内置，降低运维门槛：

| 故障 | 系统行为 | 运维动作 |
|---|---|---|
| Redis 不可用 | 自动降级为无缓存，请求仍成功 | 无需立即干预；恢复后自动使用缓存 |
| Qdrant 不可用 | 混合检索降级为关键词检索；语义模式明确报错 | 重启 Qdrant 进程 |
| 云端模型不可用 | 降级到离线引擎，健康检查标注 `degraded` | 检查密钥与网络 |
| worker 异常退出 | 启动时回收陈旧任务重新入队 | 重启应用即可 |
| 后台任务超时 | 任务级超时按失败处理并按退避重试 | 查看 `jobs.error_message` |
| 模式缺失 | 启动时自举建表并快速失败提示 | 检查数据库连接 |

结论：**部署与使用操作简单、故障处置有内置路径，操作可行性成立。**

## 3.5 法律与合规可行性

| 维度 | 说明 |
|---|---|
| 软件许可 | 使用的组件均为宽松开源许可，允许教学与个人使用 |
| 数据隐私 | 系统本地优先，数据默认不出本机；仅在用户显式配置云端模型时，必要的检索片段才会发送给模型服务 |
| 用户数据 | 不采集、不上传用户数据；无第三方埋点 |
| 内容合规 | 系统不生成违法内容；提示词约束模型"仅依据资料作答"，降低编造风险 |
| 知识产权 | 系统代码为自主实现；示例文档为自建样例 |

需要说明的合规边界：系统对上传内容不做病毒扫描与内容审查，若用于生产环境需另行补充。这一点在可行性结论中作为限制列出，并在第十章"不足与后续工作"中再次说明。

结论：**在法律与合规层面不存在阻碍，法律可行性成立。**

## 3.6 进度可行性

课题按模块拆分，各模块相对独立，可增量交付。总体安排如下（相对顺序，不含具体工期）：

```mermaid
flowchart LR
    A["需求分析\n与总体设计"] --> B["数据库设计\n与模型实现"]
    B --> C["核心基础设施\n配置/日志/错误/缓存/重试"]
    C --> D["认证与工作区\n项目/知识库"]
    D --> E["文档摄取流水线\n解析/分块/向量化"]
    E --> F["检索与 RAG\n混合检索/重排/引用"]
    F --> G["规划器与 Agent\n工具/执行器"]
    G --> H["执行轨迹\n与可观测性"]
    H --> I["测试与缺陷修复\n冒烟测试"]
    I --> J["文档与论文"]
```

进度可控的理由：

1. **依赖清晰**：各模块的输入输出明确，前序模块完成后即可并行推进后续模块；
2. **可独立验证**：每个模块都有对应的端点或测试，可增量验证；
3. **无外部阻塞**：不依赖第三方服务审批、不依赖云资源开通；
4. **风险前置**：技术风险在第三章识别并给出规避措施，避免后期返工。

结论：**进度安排合理，进度可行性成立。**

**课题在五个维度上均可行，具备实施条件。** 主要风险是云端模型不可用，但已通过确定性离线引擎兜底化解；其次是运行环境差异，已在文档中明确说明验证环境与限制。
