# 基于大语言模型的本地优先个人知识管理与智能任务执行平台的设计与实现

**Design and Implementation of a Local-First Personal Knowledge Management and Intelligent Task Execution Platform Based on Large Language Models**

---

## 摘要

个人在日常学习与工作中积累的资料、待办事项和与人工智能的对话通常分散在互不相通的工具里：资料存在于网盘或笔记软件，任务存在于待办清单，而与模型的交互则停留在一次性的对话框，既无法引用自己的资料，也不产生可追溯的执行记录。与此同时，通用云端助手虽然具备较强的生成能力，但其数据保存在服务商侧，执行过程对用户不可见，也难以约束其对本机文件的操作范围。

本文设计并实现了一个面向单用户的本地优先桌面平台，将资料摄取、知识检索、任务规划、智能体工具调用与结果追踪整合在同一个系统中。系统采用三层职责划分：认知层负责理解与规划，行动层负责在权限约束下执行工具调用，交付层负责产出物的机器校验与用户验收。数据以本机为权威副本，存储在本地 PostgreSQL 集群中，向量索引保存在本地 Qdrant，缓存使用本地 Redis；模型调用通过统一的提供方抽象接入，可在云端模型、本地 Ollama 与确定性离线引擎之间切换，任一提供方不可用时系统降级而非失效。

系统桌面端采用 Qt 6 与 QML 实现原生界面，后端采用 Python 3.13 与 FastAPI 异步框架，二者通过进程内的桥接层以信号—槽机制通信。数据库结构由 Alembic 迁移管理，共 34 张表、9 个版本化迁移，并实现了对既有数据库的接纳机制。系统对外暴露 123 个 HTTP 路径、155 个操作，内置 11 个业务工具与 44 个计算机操作工具，工具按 8 类组织并受四级权限策略约束。

在验证方面，后端测试套件共收集 1377 个用例，其中 1367 个通过、10 个跳过、0 个失败；另有针对界面控件树的自动化验证、跨 15 个页面与 3 种窗口尺寸的布局审计，以及覆盖安装、重启、数据持久化与关闭流程的端到端检查。测试结果表明系统在功能正确性、数据一致性与异常处理方面达到设计目标；同时，本文明确指出了尚未测量的指标与当前限制，包括缺少检索质量标注集、未进行并发与多设备实验、真实嵌入服务尚未配置时语义检索不可用等。

**关键词**：大语言模型；个人知识管理；检索增强生成；智能体；本地优先架构

## Abstract

Personal materials, to-do items and conversations with artificial intelligence are usually scattered across tools that cannot talk to each other: documents live in cloud drives or note-taking apps, tasks in separate to-do lists, and model interactions in one-off chat windows that can neither cite one's own materials nor leave a traceable execution record. General-purpose cloud assistants are capable, but they keep the data on the provider's side, hide the execution process from the user, and are difficult to constrain in what they may do to local files.

This thesis designs and implements a local-first desktop platform for a single user that integrates document ingestion, knowledge retrieval, task planning, agent tool invocation and result tracking into one system. Responsibilities are divided into three layers: a cognition layer for understanding and planning, an action layer that executes tool calls under permission constraints, and a delivery layer that performs machine verification of artifacts and user acceptance. The authoritative copy of the data is local — a local PostgreSQL cluster, a local Qdrant vector index, and a local Redis cache. Model access goes through a unified provider abstraction that can switch between a cloud model, a local Ollama instance and a deterministic offline engine, degrading rather than failing when a provider is unavailable.

The desktop client is a native interface built with Qt 6 and QML; the backend is an asynchronous Python 3.13 / FastAPI application. The two communicate in-process through a bridge layer using Qt's signal-and-slot mechanism. The schema is managed by Alembic: 34 tables across 9 versioned migrations, with an adoption path for pre-existing databases. The system exposes 123 HTTP paths and 155 operations, and provides 11 business tools and 44 computer-operation tools organised into 8 categories under a four-level permission policy.

The backend test suite collects 1377 cases, of which 1367 pass, 10 are skipped and none fail; separate automated checks verify the interface control tree, audit layout across 15 pages and 3 window sizes, and cover installation, restart, data persistence and shutdown. The results show that the system meets its design goals for functional correctness, data consistency and error handling. Metrics that have not been measured, and the system's current limitations — the absence of a retrieval-quality annotation set, the lack of concurrency and multi-device experiments, and the unavailability of semantic retrieval when no embedding credential is configured — are stated explicitly rather than estimated.

**Keywords**: large language model; personal knowledge management; retrieval-augmented generation; agent; local-first architecture

## 第一章 绪论

### 1.1 课题背景与意义

#### 1.1.1 个人知识资产的碎片化

个人的知识资产通常由三类内容构成：**资料**（文档、笔记、摘录）、**任务**（待办、计划、依赖关系）与**交互记录**（提问、回答、结论）。在常见的工作方式中，这三类内容分属不同工具：资料保存在笔记软件或网盘，任务保存在待办应用，而与人工智能的交互停留在对话框，关闭页面即失去上下文。

这种割裂带来三个具体问题。其一，**引用困难**：当用户希望模型基于自己的资料作答时，需要手工复制粘贴，且无法保证引用的是最新版本。其二，**过程不可追溯**：模型给出的结论无法回溯到具体依据，用户难以判断其可信度。其三，**重复劳动**：同一份资料在不同任务中被反复阅读与整理，沉淀不下来。

#### 1.1.2 通用云端助手的能力与边界

以对话形式提供服务的通用助手具备较强的自然语言理解与生成能力，但在个人知识管理场景中存在边界。**数据位置**方面，用户资料需上传至服务商侧才能被检索，对隐私敏感的资料构成障碍。**执行能力**方面，多数助手只能生成文本，无法在用户本机完成文件读写、代码修改、命令执行等操作；具备此类能力的系统又往往缺少细粒度的权限约束与完整的审计记录。**可复现性**方面，模型服务的版本、配额与可用性由服务商决定，用户无法在服务不可用时继续工作。

#### 1.1.3 本课题的切入点

上述两方面的问题指向同一个设计问题：**如何在保留本地数据主权的前提下，把"理解—检索—规划—执行—验收"组织成一条可追溯的闭环**。本文的工作正是围绕这一问题展开：构建一个本地优先的桌面平台，使个人资料成为可被检索与引用的知识库，使模型输出成为受权限约束、可被机器校验、可被用户验收的执行结果。

从工程角度看，该课题的意义在于：它要求同时处理**数据一致性**（资料、分块、向量、任务之间的引用关系）、**执行安全性**（模型发起的文件与命令操作必须受限）、**故障可见性**（模型服务不可用、执行中断、结果不确定时系统必须如实呈现而非静默失败）三类问题，具有典型的软件工程综合性。

### 1.2 国内外研究现状

#### 1.2.1 检索增强生成

检索增强生成（Retrieval-Augmented Generation，RAG）由 Lewis 等人于 2020 年提出，其核心思想是把参数化记忆（模型权重）与非参数化记忆（外部文档索引）结合，在生成前检索相关文档片段作为条件[1]。该范式在知识密集型任务上显著优于纯生成模型，并成为后续大量系统的基础架构。

2023 年之后，围绕 RAG 的研究迅速扩展。Gao 等人对 RAG 的范式演进进行了系统梳理，将其划分为朴素 RAG、高级 RAG 与模块化 RAG 三个阶段，并讨论了检索质量、上下文组织与引用忠实度等关键问题[2]。Karpukhin 等人提出的稠密段落检索（Dense Passage Retrieval，DPR）使用双塔编码器在向量空间中检索文档，为稠密检索提供了可训练的基线[3]。

在检索质量之外，**引用与接地（grounding）** 逐渐成为独立问题：模型生成的引用编号是否真正对应所检索到的片段，直接影响用户对结果的信任程度。本文在设计中把引用映射作为独立环节处理（见 5.5 节）。

#### 1.2.2 工具调用与智能体

让语言模型调用外部工具的研究以 Toolformer 与 ReAct 为代表。Schick 等人提出的 Toolformer 通过自监督方式让模型学会在需要时插入 API 调用[4]；Yao 等人提出的 ReAct 则把"推理"与"行动"交替进行，形成"思考—行动—观察"的循环，在问答与决策任务上同时提升了可解释性与成功率[5]。

在此基础上，自主智能体（autonomous agent）的研究进一步引入了任务分解、记忆、反思与多智能体协作等机制。Wang 等人对基于大语言模型的自主智能体进行了系统综述，将其归纳为规划、记忆、工具使用三个能力维度[6]；Shinn 等人提出的 Reflexion 通过语言化的自我反馈提升后续尝试的质量[7]。

这些工作普遍关注**能力上限**，而工程落地中同样重要的问题是**能力边界**：当模型可以调用文件写入、命令执行等具有副作用的工具时，如何约束其行为、如何记录其行为、以及在执行中断后如何判断副作用是否已经发生。本文在第五章与第六章中对后一组问题给出了具体设计。

#### 1.2.3 个人知识管理

个人知识管理（Personal Knowledge Management，PKM）工具的发展大致经历了三个阶段：以文件夹与标签组织的文件管理器、以双向链接与图谱组织的笔记工具、以及在笔记之上叠加检索与自动化的工具。已有工具的共性是**以人为主要操作者**：检索由人发起，整理由人完成，工具提供的是更好的组织方式而非主动的执行能力。

近年来，把语言模型引入 PKM 的尝试开始出现，主要形式是对个人笔记做问答。这类方案面临的共同困难是：笔记内容与任务、执行记录之间缺少统一的标识体系，导致"问答结果"难以回流为可复用的资产。

#### 1.2.4 本地优先软件

Kleppmann 等人在 2019 年提出"本地优先软件"（local-first software）的概念，主张把设备上的数据副本作为主要工作对象，同时保留跨设备协作的能力，并给出了七条理想属性，其中包括"数据持久可用"与"用户保留数据所有权"[8]。该理念为本课题的数据存储与降级策略提供了直接依据。

在工程实践层面，本地优先意味着需要自行承担基础设施的部署与生命周期管理，这对桌面应用提出了额外要求：安装包必须携带或能够获取运行时所依赖的组件，且必须在启动、异常退出与卸载等环节保证数据不丢失。

#### 1.2.5 现有方案的不足

综合来看，现有方案在以下方面存在不足：

1. **资料、任务与执行记录相互隔离**。资料检索工具不产生任务，任务工具不引用资料，执行记录不回流为知识。
2. **检索结果与生成内容之间缺少可验证的引用关系**。多数系统给出引用编号，但不校验编号与实际检索片段的一致性。
3. **具备本机操作能力的系统缺少权限边界与审计**。工具调用往往以"全有或全无"的方式授予，且执行过程不留下可追溯的记录。
4. **执行中断后的状态不确定**。进程被终止、超时或工具执行到一半失败时，副作用是否已经发生通常无法判断。
5. **对模型服务的强依赖**。服务不可用时系统整体失效，而不是降级为可用的子集。

本文的工作针对上述第 1、2、3、4 点给出设计与实现，第 5 点通过提供方抽象与离线引擎处理。

## 第二章 相关技术与理论基础

本章介绍系统实际采用的技术与理论依据。对于未在系统中使用的技术不作展开。

### 2.1 大语言模型与工具调用

大语言模型（Large Language Model，LLM）是以 Transformer 为骨干、在海量文本上预训练的神经网络，具备上下文学习能力[9]。在工程系统中，模型的输出通常不是终点而是中间结果：系统需要把模型生成的自然语言转化为结构化的动作。

工具调用（tool calling）是这一转化的主要形式。系统向模型提供一组工具的**声明**（名称、用途、参数模式），模型在生成时选择工具并给出参数，由系统负责实际执行并把结果回填给模型。Toolformer 通过自监督方式验证了模型可以学会在需要时插入调用[4]；工程实现中更常见的做法是由调用方在提示中给出工具模式，并对模型输出做严格解析。

本系统采用后一种方式：工具声明以 JSON 模式给出，模型输出经解析后与工具签名比对，解析失败时按可重试错误处理，而不是把解析失败当作执行失败（见 6.4 节）。

### 2.2 智能体执行循环与任务规划

ReAct 提出的"推理—行动—观察"循环是当前智能体的基本形态[5]：模型先给出推理，再选择一个动作，系统执行后把观察结果返回模型，循环直到模型给出最终答案或触发终止条件。

本系统的智能体循环在此基础上增加了两个约束。其一是**步骤与写操作上限**：单次运行的步数上限默认 8（可由调用方指定，上限 16），写操作次数设有独立上限，超出即终止并记录原因。其二是**执行校验**：工具返回后由系统而非模型判断结果是否成功，校验失败的步骤允许重试，重试次数受策略限制。终止原因被显式记录（正常结束、空响应、检测到循环、达到步数上限），使"为什么停下来"成为可查询的事实而不是推断。

任务规划是循环的前置环节：给定一个目标，系统要求模型输出分阶段的步骤列表，每个步骤包含标题、说明与预期产出，经规范化后写入数据库。规划结果同时用于进度展示与执行阶段的步骤边界判定。

### 2.3 检索增强生成

检索增强生成把生成过程建立在检索结果之上[1]。系统的处理流程为：对用户问题做查询改写，从知识库中检索相关分块，按预算组装上下文，要求模型在生成时标注引用编号，最后把编号映射回具体来源。

引用映射是本文关注的重点之一。系统使用正则表达式 `\[(\d{1,2})\]` 从生成文本中提取引用编号，并校验每个编号是否落在实际提供的来源数量范围内；越界或未出现的编号不会被视为有效引用。需要强调的是，**编号映射成功只说明引用格式正确、编号与来源对应，并不证明所引用的片段在语义上支持该结论**。这一区别在 7.5 节与 8.3 节中进一步说明。

### 2.4 文档分块、稠密检索、稀疏检索与结果融合

**分块**是把长文档切分为可独立检索的片段。系统采用按语义边界贪心打包的策略：先按标题与段落切分为句子序列，再按目标长度（默认 900 字符）打包，相邻窗口保留重叠（默认 150 字符）以保持跨窗口语义连续；小于 120 字符的尾块被并入前一块，避免产生过短的碎片。

**稠密检索**把查询与文档映射到同一向量空间，按向量相似度排序。它擅长语义相近但用词不同的匹配，代价是依赖嵌入模型的质量。

**稀疏检索**以词项统计为基础。系统实现了 Okapi BM25 的一种常见形式：

$$ \text{score}(q,d) = \sum_{t \in q} \text{idf}(t) \cdot \frac{f(t,d) \cdot (k_1 + 1)}{f(t,d) + k_1 \cdot (1 - b + b \cdot \frac{|d|}{\text{avgdl}})} $$

其中 $\text{idf}(t) = \ln\left(1 + \frac{N - df(t) + 0.5}{df(t) + 0.5}\right)$，$k_1 = 1.5$、$b = 0.75$。稀疏检索对术语精确匹配敏感，但对同义表达无能为力。

**结果融合**采用线性加权：对两路得分分别归一化后按 $\text{score} = \alpha \cdot s_{dense} + (1-\alpha) \cdot s_{sparse}$ 融合，$\alpha$ 默认取 0.6。融合后的结果再经过一次词汇级重排，其得分由覆盖率、精确短语命中、标题匹配与长度先验加权构成，最终分数为融合分与词汇分的加权和。

系统在融合前把候选窗口扩大（取 `top_k` 的三倍，且不少于 `top_k`），以减少两路检索各自遗漏造成的损失。

### 2.5 嵌入与向量数据库

嵌入模型把文本映射为定长向量。系统通过提供方抽象支持两类嵌入来源：云端嵌入服务（默认 `text-embedding-3-small`，1536 维）与内置离线嵌入（确定性哈希 n-gram，384 维）。两者维度不同，因此系统在写入时记录产生向量的模型标识，并在知识库层面拒绝混用不同模型的向量（见 7.8 节）。

向量存储使用 Qdrant，索引类型为 HNSW（Hierarchical Navigable Small World）[10]，构建参数取 $m = 16$、`ef_construct = 128`。HNSW 通过分层图结构在近似最近邻搜索中取得对数级查询复杂度，是当前向量检索的主流索引结构。每个向量的载荷中包含分块标识、所属文档与知识库、分块序号、标题与内容前缀，用于在检索命中后直接取回上下文而无需二次查询。

### 2.6 本地优先架构与桌面应用

本地优先软件主张以设备上的数据副本为主要工作对象[8]。本系统把这一原则落实到三点：**数据存储在本机**（本地 PostgreSQL 集群、本地向量索引、本地缓存）；**模型可替换**（云端模型、本地 Ollama 与离线引擎通过统一抽象接入）；**离线可用**（无可用云端凭据时降级为确定性离线引擎，系统功能不中断，界面如实标注当前提供方）。

桌面客户端采用 Qt 6 与 QML。选择原生界面而非内嵌浏览器运行时，主要出于三点考虑：一是避免在安装包中携带完整的浏览器运行时；二是原生控件与操作系统的高对比度、缩放设置配合更直接；三是界面与业务逻辑之间的边界更清晰——QML 只能调用桥接层显式暴露的槽，未暴露的能力在界面上不可达。

### 2.7 Python 异步处理、数据库事务与权限控制

后端采用 Python 的 `asyncio` 并发模型，HTTP 框架为 FastAPI，数据库访问使用 SQLAlchemy 2.0 的异步接口配合 asyncpg 驱动。异步模型下的关键约束是**会话生命周期**：数据库会话必须在同一个事件循环内创建与释放，跨循环复用连接会引发难以定位的错误。系统通过统一的会话作用域上下文管理器处理这一问题（见 6.1 节）。

后台任务采用**数据库队列**而非独立的消息中间件：任务记录存入数据库表，工作进程通过带状态条件的原子更新抢占任务，并定期回收超时的僵死任务。这一选择减少了需要部署的组件数量，代价是吞吐量低于专用队列——对于单用户桌面场景，这一取舍是合适的（见 3.5 节）。

权限控制采用**声明式策略 + 执行前检查**的结构：每个工具声明其所需的能力级别，执行器在调用前向权限模块查询该工具在当前策略下是否允许，拒绝时返回结构化的拒绝原因而不是抛出异常。策略本身可持久化、可修改，并在界面中可读（见 5.7 节）。

### 3.5 可行性分析

#### 3.5.1 技术可行性

系统所用的组件均为成熟且活跃维护的开源项目：Python 3.13 与 FastAPI 提供异步 HTTP 服务；SQLAlchemy 2.0 与 Alembic 提供异步 ORM 与迁移能力；PostgreSQL 16、Redis 5 与 Qdrant 1.12 提供数据、缓存与向量存储；Qt 6 与 PySide6 提供原生界面能力。这些组件在 Windows 平台均有官方支持，且可在目标机器上以独立进程方式运行，无需修改系统配置。

关键技术的可实现性已在本文的实现中得到验证：混合检索、离线嵌入、受约束的工具执行、进程内桥接通信、数据库队列与迁移接纳机制均已落地并通过测试（见第七章）。

#### 3.5.2 经济可行性

系统在开发与运行两个阶段均不产生许可费用。运行阶段的直接成本来自模型调用，且为按量计费。需要说明的是，**本文未对模型调用的成本进行系统性测量**；仅在验证连接可用性时执行过少量真实调用，单次调用的令牌量在千级以内。若配置本地 Ollama 或使用离线引擎，则模型调用成本为零。硬件方面，系统在普通个人计算机上可运行，向量索引与数据库均在本机，不产生额外的托管费用。

#### 3.5.3 操作可行性

系统以桌面应用形式交付，通过安装包部署，安装后从桌面快捷方式启动，不需要用户配置 Python 环境或手工启动数据库。首次启动时系统自行完成运行环境的准备（初始化数据目录、启动本地服务、执行迁移），并在界面中显示就绪状态。日常使用中，用户的主要操作是导入资料、提问与下达任务，均在界面内完成。

#### 3.5.4 法律与合规可行性

系统处理的资料由用户自行提供，且保存在用户本机；系统不向第三方上传整库资料，仅在调用云端模型时把当次检索到的片段作为上下文发送。密钥由用户自行配置并按账号保存在本机，界面只显示掩码。系统内置的受保护路径列表避免了对凭据目录与浏览器用户数据的读写。需要指出的是，若用户导入的第三方资料受版权保护，其使用范围由用户自行负责。

#### 3.5.5 进度可行性

系统采用迭代方式开发，从可运行的纵向切片开始（单一页面的端到端流程），逐步扩展功能域与页面数量，每一轮以自动化测试与实机验证收尾。这一方式的可行性已由实际开发过程验证：当前版本包含 242 次提交、34 张数据表、155 个 API 操作与 1377 个测试用例。

## 第四章 系统总体设计

### 4.1 设计目标与原则

系统设计遵循以下原则，这些原则直接决定了后续的模块边界与取舍。

**原则一：数据以本机为权威副本。** 用户资料、分块、向量、任务与执行记录全部保存在本机。调用云端模型时只发送当次检索到的片段，不发送整库资料。

**原则二：职责按"认知—行动—交付"划分，而不是按技术分层。** 认知层负责理解与规划，行动层负责在约束下执行，交付层负责产出物的校验与验收。这一划分使得"谁有权做决定"与"谁有权执行"在结构上分开：模型在认知层做决定，但它不能直接触碰文件系统；执行发生在行动层，且必须经过权限检查。

**原则三：能力必须显式暴露。** 界面只能调用桥接层显式声明的槽，后端只能通过服务层访问数据。未声明的能力在对应层不可达，而不是"可以调用但不建议调用"。

**原则四：失败必须可见。** 加载、空数据、失败与成功是四种不同状态，界面必须分别呈现；提供方不可用时必须标注当前实际使用的提供方，而不是静默降级。

**原则五：可重建的东西不进入版本库。** 运行时二进制、依赖目录、构建产物与安装包均由脚本生成或下载，版本库只保存源码与配置。

### 4.3 运行环境与进程模型

#### 4.3.1 进程构成

系统的运行涉及四类进程，其生命周期由不同主体管理：

**表 4-3 进程构成**

| 进程 | 数量 | 启动者 | 生命周期 |
|---|---|---|---|
| 桌面客户端（含内嵌后端） | 1 | 用户（快捷方式） | 用户关闭窗口时结束 |
| PostgreSQL | 1 | `scripts/infra-start.ps1` | 由客户端启动，随客户端关闭 |

后端**不以独立 HTTP 服务的形式运行**，而是作为模块加载进桌面客户端进程。这一设计的理由是单用户场景下不需要跨进程边界：省去端口占用与鉴权开销，也使界面与业务之间的调用不经过网络。HTTP 接口仍然保留，用于自动化测试与脚本调用，此时以后台进程方式运行。

基础设施以子进程方式运行，由启动脚本负责拉起与探活。脚本记录自己启动的进程标识，关闭时只停止由本次启动的进程，不触碰外部已有的同名服务——这一约束避免了"关闭应用时杀掉用户自己的数据库"。

### 5.3 迁移策略与既有数据库接纳

#### 5.3.1 迁移的引入

系统的早期版本在启动时调用 `Base.metadata.create_all` 建表，同时仓库中并不存在迁移脚本。这种"两套机制管同一个 schema"的状态产生了一个不易察觉的问题：**模型定义与迁移历史描述的结构已经不一致，而 `alembic_version` 仍然报告已是最新**。在实际测量中，模型声明 33 张表，仅靠迁移建库得到 29 张，缺少的 4 张（`conversations`、`installed_skills`、`messages`、`tool_audit_log`）游离在迁移历史之外。

#### 5.3.2 三种数据库状态的处理

启动时按数据库的实际状态分三路处理（实现于 `app/core/schema_guard.py`）：

1. **空数据库**（全新安装）：执行 `alembic upgrade head` 建库，使新库自诞生起就带有与其一致的迁移历史。不使用 `create_all`。
2. **有表且有迁移记录**：**只检查，不修复**。记录的修订必须等于当前 head；不等则启动失败，并在错误中给出两个修订号与可执行的修复命令。**不做 stamp**——把没有人执行过的修订号写入记录，正是产生"声称拥有某结构而实际没有"的原因。
3. **有表但无迁移记录**（早期版本产生的数据库）：进入**接纳**判定。接纳的**充要条件**是"与迁移描述的全部差异都是**新增**"——即缺少的表、缺少的列。满足时按模型元数据补齐缺失部分、写入修订号，此时该库确实具备 head 所描述的全部内容。若存在其他差异（列类型不符、出现无人声明的表、可空性不一致），则**拒绝**并列出具体差异，因为"补上缺的"无法修复"已有的东西不一致"。

这一设计的价值在于把"记录"与"事实"绑定：写入修订号的前提是该库确实具备该修订的效果，而不是因为希望它如此。

### 5.4 文档摄取与分块

#### 5.4.1 解析

系统接受四类文件：`.md`、`.markdown`、`.txt`、`.pdf`，单文件上限 25 MB。Markdown 与纯文本直接读取；PDF 使用 `pypdf` 抽取文本，并设置页数上限以避免超长文档耗尽内存。

上传文件写入本地存储目录，写入前经 `ensure_within_root` 校验目标路径位于允许的根目录内，防止路径穿越。

#### 5.4.2 分块

分块算法（`ai/rag/chunker.py`）采用"先按语义边界切分、再贪心打包"的两阶段策略：

1. **切分**：按 Markdown 标题与段落边界把正文切为句子序列，同时记录每个句子所属的标题路径（面包屑）。
2. **打包**：按目标长度（默认 900 字符）把句子贪心装入窗口；相邻窗口之间保留重叠（默认 150 字符），重叠部分由上一窗口的尾部句子重建，保证语义连续。
3. **收尾**：小于 120 字符的尾块并入前一块，避免产生过短、无法独立检索的碎片。

重叠长度被钳制为不超过窗口长度的一半，防止在极小窗口配置下出现死循环。每个分块保留其标题路径，检索命中后可作为上下文的一部分展示给用户。

#### 5.4.3 向量化与写入

分块后逐批生成向量（批大小默认 16），写入 Qdrant。每个向量的载荷包含分块标识、文档标识、知识库标识、账号标识、分块序号、标题、文档标题、内容前缀与**产生该向量的模型标识**。

模型标识的用途是**拒绝混用**：若某知识库已存在由模型 A 生成的向量，而当前配置的嵌入模型为 B，写入被拒绝并说明原因。这一约束防止了不同语义空间的向量混入同一集合，从而使相似度比较失去意义。

嵌入结果按内容哈希缓存，缓存键由模型标识与文本内容哈希构成，避免相同内容重复调用嵌入服务。

### 5.5 RAG 检索与引用

#### 5.5.1 混合检索

检索分两路并行执行：稠密检索在 Qdrant 中按向量相似度取候选；稀疏检索在数据库中按 BM25 打分取候选。两路各自归一化后按 $\alpha$ 加权融合（默认 $\alpha = 0.6$，偏向稠密一侧）。

融合后的候选再经一次词汇级重排，重排分数由四项加权构成：查询词覆盖率（0.45）、精确短语命中（0.25）、标题匹配（0.20）与长度先验（0.10）；最终得分为融合分与词汇分的加权和（0.65 / 0.35）。重排的候选窗口取 `top_k` 的三倍且不少于 `top_k`，以降低单路遗漏的影响。

#### 5.5.2 上下文组装与引用

检索结果按令牌预算（6000）顺序装入上下文，并编号为 1..n。提示词要求模型在生成时用 `[n]` 标注依据来源。

生成完成后，系统用正则 `\[(\d{1,2})\]` 提取全部引用编号，并执行两项校验：编号是否落在 1..n 范围内；同一结论是否携带引用。越界编号被丢弃，不进入来源列表。

**需要明确的是校验的边界**：编号映射成功只证明引用格式正确、编号与实际提供的片段对应，**不证明被引用的片段在语义上支持该结论**。系统实现的是前者，后者需要人工判断或引入专门的蕴含判定模型，本文未实现。

#### 5.5.3 检索阶梯

系统提供四级检索阶梯：优先尝试记忆命中，其次知识库检索，再次通用检索，最后退化为无检索的直接生成。每一级在无结果时降级到下一级，降级事实记录在运行记录中。该阶梯的设计目的是在个人资料不足时仍给出可用回答，同时让"本次回答有没有依据"成为可查询的事实。

### 5.6 Provider 与模型调用

#### 5.6.1 统一抽象

模型访问经两个接口抽象：`LLMProvider`（对话与工具调用）与 `EmbeddingProvider`（向量化）。已实现的提供方包括：

**表 5-4 提供方实现**

| 提供方 | 类型 | 说明 |
|---|---|---|
| `deepseek` | 对话 | 云端模型，默认模型 `deepseek-flash` |
| `openai_compatible` | 对话 / 嵌入 | 任意 OpenAI 兼容端点 |
| `ollama` | 对话 / 嵌入 | 本地模型服务 |
| `heuristic` | 对话 / 嵌入 | 确定性离线引擎，无外部依赖 |

离线引擎是本系统降级策略的关键：它以分词、n-gram 哈希与抽取式策略实现对话与嵌入能力，**不依赖任何外部服务**。在无可用凭据时系统自动使用它，界面明确标注当前提供方为离线引擎，并说明"回答质量不如云端模型"。这一设计使系统在缺少凭据时仍然可用，而不是失效。

#### 5.6.2 配置的分层与优先级

配置采用四层合并，优先级由高到低为：**账号级文件 → 安装级文件 → 环境变量 → 默认值**。账号级配置保存在数据目录下的 `ai-config/<账号 id>.json`，安装级配置保存在同目录的 `ai-config.json`。设置界面写入的是账号级配置，因此一台机器上的多个账号互不影响。

配置解析需要知道"这是谁的配置"，而模型调用发生在流水线深处，调用方并不传递账号参数。系统通过上下文变量传递账号标识：请求进入时设置一次，解析配置时读取；未设置时退化为安装级配置。**这一机制要求每个入口都显式绑定账号**——若某个入口遗漏绑定，它会读到安装级配置，从而出现"界面显示已配置、实际调用使用另一份配置"的现象。系统在验收过程中发现并修复了一处此类遗漏（见 7.3 节）。

#### 5.6.3 配置状态判定

配置状态分为五档，由配置内容与最近一次连接测试的结果共同决定：

**表 5-5 配置状态**

| 状态 | 判定条件 |
|---|---|
| 离线模式 | 生效提供方即为离线引擎 |
| 未配置 | 选择了云端提供方但缺少必需字段（模型名或密钥） |
| 已配置，未测试 | 必需字段齐备，且没有针对当前配置的测试记录 |
| 连接成功 | 存在测试记录且成功，且记录的提供方、模型、基址与当前配置一致 |
| 连接失败 | 存在测试记录且失败，且指纹一致 |

测试记录包含被测试的提供方、模型与基址。**改变其中任何一项都会使记录失效**，状态回到"已配置，未测试"——一条比它所描述的对象活得更久的绿灯，是对当前配置的错误陈述。

连接测试由用户主动触发，系统向配置的端点发送一次真实请求并记录耗时与结果。**系统不会在打开页面时自动测试**：一个每次打开都要发请求的状态，是每次查看都要花钱的状态。

### 5.7 智能体规划、工具调用与执行记录

#### 5.7.1 规划

规划阶段要求模型输出结构化的步骤列表，每个步骤包含标题、说明与预期产出。系统对模型输出执行规范化：字段缺失时补默认值、数值字段越界时钳制、优先级取值不在枚举内时回退为默认值。规范化后的计划落库，并成为执行阶段的步骤边界。

规范化而非拒绝的设计理由是：模型输出的格式稳定性有限，因单个字段格式不符而放弃整次规划，代价远大于按已知默认值补齐。

#### 5.7.2 工具目录

系统包含两组工具，其定位不同：

**业务工具（11 个）** 作用于系统自身的业务数据，由 `ai/agent/tools.py` 声明：`knowledge_search`、`knowledge_document_read`、`project_list`、`task_list`、`task_create`、`task_create_batch`、`task_update`、`task_planner`、`note_create`、`knowledge_link`、`calculator`。

**计算机操作工具（44 个）** 作用于本机文件系统与进程，按 8 类组织，见表 5-6。

**表 5-6 计算机工具分类**

| 类别 | 数量 | 示例 |
|---|---|---|
| 文件系统 | 14 | `file_read`、`file_write`、`file_delete`、`file_move`、`file_search` |
| 版本控制 | 8 | `git_status`、`git_diff`、`git_commit`、`git_restore` |
| 终端 | 5 | `cmd_exec`、`powershell_exec`、`python_exec`、`node_exec` |
| 项目 | 4 | `run_build`、`run_tests`、`run_lint` |
| 进程 | 4 | `process_start`、`process_list`、`process_stop` |
| 代码 | 4 | `code_search`、`code_analyze`、`code_patch`、`code_replace` |
| 网络 | 3 | `http_get`、`http_post`、`download_file` |
| 观察 | 2 | 屏幕捕获类工具 |

`calculator` 工具的实现值得单独说明：它**不使用 Python 的 `eval`**，而是自行解析四则运算与幂运算表达式，并对表达式长度、除零与操作数范围设限。这一选择的原因是：把一个能执行任意代码的函数暴露给模型，等价于把权限检查之外的后门交给模型。

#### 5.7.3 执行循环

执行循环（`ai/agent/autonomous.py`）的每一轮包含五个动作：模型选择工具与参数 → 权限检查 → 执行 → 校验结果 → 持久化并回填观察结果。

**终止条件**被显式记录，取值包括：模型给出最终答案、模型返回空响应、检测到重复调用（循环）、达到步数上限。步数上限默认 8，可由调用方指定但不超过 16；写操作次数设有独立上限。**终止原因是可查询的事实**，而不是需要从日志推断的结论。

#### 5.7.4 执行记录

每次工具调用在 `tool_calls` 表中产生一条记录，包含：所属运行与步骤、工具名、参数、结果摘要、开始与结束时间、状态与错误信息、调用标识，以及**对账时间**。运行记录（`ai_runs`）保存输入、令牌用量、耗时、成本估算、终止原因与错误信息；`agent_runs` 保存目标、计划与最终答案。

记录的设计目标是使"这次运行做了什么"可以在事后完整回答，而不依赖运行时的日志。

### 5.8 权限检查与工具执行

#### 5.8.1 四级能力与三种模式

工具按所需能力分为四级：**观察**（只读）、**工作区**（项目目录内读写）、**系统**（工作区外或需要执行命令）、**完全控制**。策略同时包含执行模式：**辅助**（不执行写操作）、**监督**（默认，写操作前需确认）、**自主**（按策略执行）。

工具在注册时声明其所需级别，执行器在调用前查询策略，拒绝时返回结构化的拒绝原因（包含工具名、所需级别、当前级别），而**不抛出异常**。这一区分很重要：权限拒绝是策略生效的正常结果，不是系统故障，因此不计入执行失败。

#### 5.8.2 检查内容

执行前的检查包含四项：

1. **能力级别**：当前策略是否允许该工具。
2. **工具开关**：该工具是否被单独禁用。
3. **路径检查**：读写目标是否位于允许的根目录内，是否命中受保护路径列表（凭据目录、浏览器用户数据、系统目录、项目 `.env` 与配置文件等）。
4. **命令风险**：对终端类工具的命令做风险分级，命中高危模式（如递归强制删除、磁盘格式化、强制推送）时要求确认或直接拒绝。

网络类工具额外校验目标域名是否在白名单内，白名单外的请求被拒绝。

### 5.9 中断识别、UNKNOWN 状态与对账

这是本系统在工程上较为特殊的设计，其出发点是一个具体问题：**当进程在工具执行期间被终止、超时或崩溃时，"这次调用是否已经产生了副作用"无法从状态字段判断**。简单地把未完成的调用标记为"失败"是错误的——它可能已经写入了文件；标记为"成功"同样错误。

系统的处理方式是引入第三种状态：**`UNKNOWN`**，其含义是"无人知道这次调用是否生效"。与之配套的是**对账机制**（`ai/tools/reconcile.py`）：

- 只有实现了 `reconcile` 接口的工具才可对账——对账要求工具能够**检查**外部世界的实际状态（例如"这个文件是否存在、内容是否与预期一致"），而不是依赖调用记录。
- 对账过程对每个处于 `UNKNOWN` 的调用执行检查，得到确定结论（已生效 / 未生效）后更新状态并记录对账时间。
- **无法得出结论的调用保持 `UNKNOWN` 且不写入对账时间**，以便后续再次尝试。这一细节保证了"尝试过但没有结论"与"没有尝试过"可以被区分。

`tool_calls` 表因此包含 `invocation_id`（调用标识）与 `reconciled_at`（对账时间）两个字段，并由迁移 `3f1c9d7a52be` 引入。

### 5.10 记忆与偏好

记忆模块的设计目标是把"用户在某次交互中表达的长期有效信息"沉淀为后续可用的约束。其流程为：从交互中抽取候选 → 按相关度净化 → 高分项直接生效，中分项进入候选池等待确认，低分项丢弃 → 装配进后续上下文。

偏好被建模为**约束而非建议**：当用户表达"页数更少"这类偏好时，系统将其记录为带范围的硬约束（例如 15 分钟的演示对应 10–14 页），在后续生成时作为约束参与判定，而不是作为提示中的一句软性描述。

记忆设有生命周期管理：相似度高于阈值的记忆合并，长期未被使用且置信度下降的记忆衰减，相互矛盾的记忆对交由用户确认。

### 5.11 交付、机器验证与用户验收

交付模块区分两个概念：**已验证**（机器读回产出物并确认其结构符合预期，例如演示文稿的实际页数、文档的实际段落数、表格的实际工作表数）与**已验收**（用户确认接受该产出物）。二者是不同的断言，系统分别记录。

产出物带版本链：同一交付物可以产生多个版本，每次生成记录版本号、结构摘要与文件大小；用户拒绝时记录拒绝，后续版本在链上延续。若产出物部分生成成功（例如多份文件中部分失败），状态标记为"部分完成"并列出已完成与未完成的部分，而不是笼统地报告成功或失败。

## 第六章 系统实现

本章以实际代码为依据，说明关键模块的实现方式与设计取舍。为避免堆砌代码，仅引用必要的片段并标注其所在文件与函数。

### 6.1 依赖注入与会话生命周期

数据库会话通过上下文管理器统一管理（`app/infrastructure/database.py::session_scope`）：

```python
async def session_scope() -> AsyncIterator[AsyncSession]:
    """Transactional scope: commit on success, rollback on any exception."""
    factory = get_session_factory()
    session = factory()
    try:
        yield session
        await session.commit()
    except Exception:
        await session.rollback()
        raise
    finally:
        await session.close()
```

这一实现的三个要点：**事务边界由服务层持有**（会话在服务方法内开启、在方法返回前提交或回滚）；**异常一律回滚**，不存在"部分提交"；**会话总是关闭**，避免连接泄漏。

在异步框架下，这一封装还解决了一个具体问题：SQLAlchemy 的连接池持有的连接绑定在创建它的事件循环上，跨循环复用会引发与连接池无关的错误信息。统一的作用域使会话的创建与释放总在同一循环内发生。

### 6.2 异步任务与运行时协调

后端是异步的，而界面是同步的事件循环。二者通过 `AsyncRunner`（`desktop-native/awbnative/async_runner.py`）协调：该类在独立线程中运行一个事件循环，界面线程通过 `submit()` 投递协程工厂，运行结束后以 Qt 信号回传结果。

```python
def submit(self, request_id: str, factory, *, timeout: float = 120.0) -> None:
    """Schedule ``factory()`` and emit `completed`/`failed` when it settles."""
```

三个实现细节值得说明。**其一，投递的是工厂函数而非协程对象**：协程对象在创建时即绑定到创建它的事件循环，若在界面线程构造再交给运行线程执行，会附着到错误的循环上；工厂函数则在实际执行的循环中构造协程。**其二，结果通过信号回传**，跨线程的信号连接默认是队列连接，因此回传发生在界面线程的事件循环中，避免了在后台线程触碰界面对象。**其三，关闭时先取消再停止**：仅调用取消只是"安排"了取消，随即停止循环会使这些任务从未收到取消通知，Python 会在每次退出时打印"任务被销毁但仍处于挂起状态"。实现中在停止循环前等待在途任务归零，最多等待 2 秒。

### 6.3 Provider 配置的保存、读取与优先级

配置的解析实现于 `app/ai/runtime_config.py::resolve()`，其合并顺序为：账号级文件 → 安装级文件 → 环境变量 → 默认值。

```python
def resolve(owner_id: Any = None) -> ResolvedAIConfig:
    owner = _coerce_owner(owner_id) or current_owner()
    account = load(owner) if owner else {}
    install = load(None)
    runtime = {**install, **account}
```

其中 `current_owner()` 读取的是上下文变量。**该机制的关键约束是"每个入口都必须绑定账号"**，这一点在验收过程中以一处真实缺陷的形式暴露出来：

`loadRuntimeInfo` 槽在读取"运行信息"时没有绑定账号，因此 `resolve()` 退化到安装级配置，而安装级配置中没有账号保存的密钥。其后果是同一屏上出现两处互相矛盾的显示：上方字段区（读取账号配置）显示"已配置 sk-****(len=35)"，下方运行信息区显示"离线模式：是（未配置 Key）"。两处都在如实显示各自读取的内容，问题在于它们读的不是同一层。

修复方式是在该槽中显式绑定账号；同时把状态判定从"读进程环境"改为"读账号配置并给出五档状态"，使界面不再需要自行推断。该缺陷的回归测试见 `backend/tests/unit/test_ai_config_status.py`，其中一条测试直接断言 `resolve(None)` 看不到账号的密钥，另一条驱动该槽并断言 `offline` 为假。

### 6.4 智能体工具选择与调用

工具声明以结构化的方式提供给模型：名称、说明、参数 JSON 模式。模型返回的调用请求经解析后与工具签名比对。

解析失败与执行失败被区别对待：解析失败按**可重试的格式错误**处理，执行失败按**执行结果**记录。这一区分避免了把"模型输出格式不规范"记为"工具执行失败"，从而不污染执行成功率统计。

工具调用的参数在传入执行器前经过规范化：数值参数按声明的范围钳制，枚举参数回退到默认值，字符串参数做长度限制。规范化的目的是让越界输入产生可预期的行为，而不是在执行阶段引发异常。

### 6.5 工具执行前的权限检查

执行器在调用工具前向权限模块查询判定结果（`ai/tools/permissions.py`）。判定结果有三种：允许、需确认、拒绝。**拒绝以结构化结果返回而非抛出异常**，调用方据此向模型回填一条说明"该操作因权限不足被拒绝"的观察结果，模型可以据此调整策略（例如改为只读方案）。

这一设计使权限约束成为**可协商的边界**而非硬性失败：模型知道为什么被拒绝，因而有机会换一条路；同时用户看到的是"策略生效"，而不是"系统出错"。

### 6.6 工具结果的持久化与回填

每次工具调用产生一条 `tool_calls` 记录，包含调用标识、参数、结果摘要、起止时间、状态与错误信息。结果摘要经过长度截断，避免超长输出撑大数据库；完整输出保存在工作区文件中，记录中保存其路径。

回填给模型的观察结果是**结果摘要**而非完整输出。这一取舍的原因是上下文预算有限：完整输出可能远大于模型能够利用的信息量，而摘要保留了判断所需的要点。

### 6.7 RAG 的检索、上下文组装与引用映射

检索由 `Retriever` 负责（`ai/rag/retriever.py`），其内部流程为：并行的稠密与稀疏检索 → 归一化 → 融合 → 重排 → 取回分块内容。

上下文组装由 `RAGPipeline` 负责（`ai/rag/pipeline.py`），按令牌预算装入分块并编号：

```python
_CITATION = re.compile(r"\[(\d{1,2})\]")
_CONTEXT_BUDGET_TOKENS = 6000
```

生成完成后，`analyse_citations` 提取引用编号并校验范围。返回的引用信息区分三类：**有效引用**（编号在范围内）、**越界引用**（编号超出范围，被丢弃）、**无引用结论**（存在未标注来源的陈述）。第三类信息用于提示用户该结论缺少依据，而不是被静默忽略。

### 6.8 异常、超时、重试与中断处理

**异常分类**：系统定义了统一的错误层次，模型服务相关的错误进一步区分为鉴权失败、限流、超时、服务端错误与响应格式错误。分类的用途有二：决定是否重试（鉴权失败与配置错误不重试，限流与超时重试）、以及向用户给出可操作的提示。

**重试策略**：采用指数退避加随机抖动，最大尝试次数、最大延迟与最大总时长均可配置。退避的随机抖动用于避免多个并发调用同时重试造成的同步冲击。

**错误呈现**：界面不直接显示原始异常文本。系统实现了错误信息的映射层（`desktop-native/qml/errors.js`），把异常映射为"标题 + 建议动作 + 原始文本"三部分：标题用用户的语言描述问题，建议给出下一步动作，原始异常保留在可展开的"技术详情"中。这一设计的依据是：原始异常（例如 `UnicodeEncodeError`、`ConnectionRefusedError`）描述的是程序内部的失败，而不是用户能够处理的问题；但完全隐藏又会使问题无法诊断，因此保留但不置于首位。

**中断处理**：见 5.9 节的 `UNKNOWN` 状态与对账机制。实现上，工具调用记录在调用前写入（状态为执行中），执行后更新状态；进程在两次写入之间终止时，记录停留在执行中，后续由对账流程处理。

### 6.9 原生界面通过桥接层调用业务服务

界面与业务之间的边界是 `ServiceBridge`（`desktop-native/awbnative/bridge.py`），它以 Qt 槽的形式暴露后端能力，共 46 个 `@Slot` 装饰的方法。

调用采用**带标识的异步请求**模式。界面侧维护一个待处理请求表：

```javascript
shellRoot.pending[id] = { kind: kind, callback: callback, onError: onError,
                          epoch: shellRoot.pageEpoch }
```

每个请求带有标识与**页面纪元**（epoch）。响应到达时，若请求所属的纪元与当前页面纪元不一致，则该响应被丢弃——这一机制处理的是"用户在请求返回前切换了页面"的场景：没有它，旧页面的回调会在新页面上执行，产生难以复现的错乱。

桥接层还承担两项职责：**启动等待**（界面先于基础设施显示，业务调用等待就绪信号，避免首个查询撞上仍在启动的数据库）、以及**账号绑定**（见 6.3 节）。前者使窗口在 1 秒内出现而数据在其后就绪，后者保证所有槽读取同一份配置。

界面侧的资源管理遵循同样的原则：页面切换时由加载器销毁旧页面，页面内持有的请求随纪元失效，避免了跨页面的状态残留。

### 7.9 中断恢复与副作用对账

该组测试模拟进程在工具执行期间被终止的场景，断言：

**局限**（逐项说明，不作估计）：

1. **未测量检索质量**。缺少相关性标注集，因此没有召回率、准确率或排序质量指标。
2. **未进行性能与并发实验**。没有吞吐量、延迟分布或并发压力测试数据。系统在设计上面向单用户桌面场景，未针对并发访问优化。
3. **未进行多设备与跨平台验证**。系统在单台 Windows 设备上验证；多显示器与混合 DPI 缩放场景未测试。
4. **真实模型调用未做系统性测量**。仅在验证连接可用性时执行过少量真实调用，未对响应时间、令牌消耗与成本做统计分析。
5. **引用校验的边界**。测试断言的是引用编号与来源的对应关系，**不是被引用片段对结论的语义支持**。存在引用编号不等于结论已被证据支持。
6. **离线引擎与云端模型的效果差异未量化**。系统的降级路径（离线引擎）在功能上可用，但其回答质量与云端模型的差距未做对照实验。
7. **安装包未做代码签名**，因此未验证签名相关的系统行为。

## 第八章 总结与展望

### 8.1 工作总结

本文围绕"在保留本地数据主权的前提下，把资料、任务与模型执行组织成可追溯的闭环"这一目标，设计并实现了一个本地优先的个人知识管理与智能任务执行平台。完成的主要工作包括：

**架构方面**，提出并按"认知—行动—交付"三层划分系统职责，使决策与执行在结构上分离；后端内部采用 API / 服务 / AI / 仓储 / 模型的分层，事务边界由服务层持有。

**数据方面**，设计了覆盖 11 个业务域的 34 张数据表，并以 9 个版本化迁移管理结构演进；实现了对早期版本数据库的接纳机制，其判定条件为"与迁移描述的全部差异均为新增"，并在不满足时拒绝而非修复。

**检索方面**，实现了文档解析、语义边界分块、稠密检索、稀疏检索（BM25）、结果融合与词汇级重排的完整链路，并把引用编号的提取与范围校验作为独立环节。

**执行方面**，实现了"规划—执行—观察—校验"循环，工具调用经四级权限策略与路径、域名、命令风险检查，执行记录完整持久化；对执行中断引入 `UNKNOWN` 状态与基于工具自检的对账机制。

**客户端方面**，使用 Qt 6 与 QML 实现原生界面，通过带请求标识与页面纪元的桥接层调用后端，避免引入 Web 运行时。

**验证方面**，建立了四层测试体系（1377 个后端用例、控件树验证、布局审计、安装与运行环境检查）。

### 8.2 已实现并验证的能力

以下能力已实现，并有自动化测试或可重复执行的检查作为依据：

- 资料摄取：四类格式的解析、分块、向量化与状态流转；重复摄取幂等；删除级联清理分块与向量。
- 检索与问答：三种检索模式；引用编号的提取与范围校验；检索结果的来源列表。
- 任务管理：状态流转、依赖关系与环检测、任务与资料的关联。
- 智能体执行：规划、工具调用、结果校验、执行记录与终止原因。
- 权限约束：四级能力、三种模式、受保护路径、路径越界检查、命令风险分级、网络白名单。
- 中断对账：`UNKNOWN` 状态的识别与基于工具自检的对账。
- 配置管理：四层配置合并、账号隔离、五档状态判定、主动连接测试。
- 降级能力：无云端凭据时自动使用离线引擎，界面如实标注当前提供方。
- 交付校验：产出物读回校验与"已验证/已验收"分离。
- 数据迁移：三种数据库状态的启动处理与拒绝逻辑。
- 桌面交付：原生界面的安装、启动、关闭与数据保留。

### 8.3 已实现但验证范围有限的能力

以下能力已实现，但验证覆盖有限，其结论应谨慎使用：

- **记忆与偏好**：记忆的抽取、净化与生命周期有单元测试覆盖，但"记忆是否真的改善了后续结果"未做对照实验。
- **交付层的版本链与验收流程**：流程与状态记录有测试覆盖，但用户实际接受/拒绝行为的影响未做统计分析。
- **检索阶梯**：四级降级逻辑有测试覆盖，但各级的命中率未量化。
- **引用校验**：编号映射已验证，语义支持未验证。
- **界面适配**：三种窗口尺寸下的布局已审计，但未覆盖多显示器与极端 DPI 组合。

### 8.4 当前限制

1. **语义检索依赖外部嵌入服务**。未配置嵌入凭据时，语义检索不可用，检索退化为关键词路径。系统在界面中如实标注这一状态，但语义能力的缺失是实际的能力边界。
2. **引用不等于证据**。系统校验引用编号与来源的对应关系，但不判断片段是否在语义上支持结论。
3. **无检索质量度量**。缺少标注数据集，无法给出召回率、准确率等指标。
4. **单用户、单设备**。系统面向单机单用户场景，未实现多设备同步与协作。
5. **未做并发与性能优化**。数据库队列、向量检索与模型调用均未针对高并发调优。
6. **代码签名缺失**。安装包未签名，首次运行会有系统警告。
7. **离线引擎能力有限**。离线引擎提供的是确定性的降级能力，而非可替代云端模型的生成质量。

### 8.5 后续工作

1. **构建检索质量标注集**。针对个人资料场景构造查询与相关性标注，测量召回率与排序质量，为分块粒度、融合权重与重排权重的调参提供依据。
2. **引用忠实度的自动判定**。引入蕴含判定或专门的校验模型，把"编号对应"提升为"片段支持结论"。
3. **执行成本与效率的测量**。对不同规模的资料集与不同复杂度的任务，测量响应时间、令牌消耗与失败率，形成可比较的基线。
4. **多设备与同步**。在保持本地优先的前提下探索设备间同步，需要解决冲突合并与数据所有权表达的问题。
5. **权限模型的细化**。当前的四级模型是粗粒度的；可探索按资源类型与操作类型组合的策略表达，以及策略的可解释性展示。
6. **离线引擎的能力增强**。探索更有效的本地检索与抽取策略，缩小与云端模型在检索增强问答上的差距。

### 8.6 关于本文工作的定位

需要说明的是，本文的工作是**软件工程层面的系统设计与实现**，其价值在于把已有的技术（检索增强生成、工具调用智能体、向量检索、本地优先架构）组织成一个完整、可用、可验证的系统，并针对工程落地中的具体问题（配置分层的绑定一致性、执行中断的副作用判定、引用校验的边界、数据库迁移的接纳条件）给出可复现的解决方案。**本文不主张算法层面的原创性**：所采用的分块、BM25、向量检索与重排方法均为已有方法的工程实现，参数取值基于默认配置与工程经验，未经系统性调优实验。
