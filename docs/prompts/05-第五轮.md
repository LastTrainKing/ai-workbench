# 第一部分：我已经定位了重试死循环的根因（先读这个）

我读了 `backend/app/ai/agent/autonomous.py`。**根因不是重试上限，是 `_recover` 的返回值被丢掉了。**

看这段（`autonomous.py:589-616` 与 `:702-708`）：

```python
# _recover 向模型要一段分析
async def _recover(self, step, observations) -> str:
    ...
    analysis = (chat.content or "").strip()
    ...
    self.controller.emit("state", message=analysis[:400] or "继续重试")
    return analysis          # ← 返回了

# 调用点
await self._recover(step, observations)     # ← 返回值没有赋给任何东西
step.status = StepStatus.RUNNING
# 下一轮仍然用同一个 step.description、同一个工具、同样的参数
```

**`_recover` 的分析结果只进了事件流给人看，从来没有回到模型的下一次尝试里。**

后果：所谓"恢复"只是**把同一件事再做一遍**。模型拿到的上下文和上一轮完全一样，于是做出同样的决定、同样的失败——重复到 `MAX_TOOLS_PER_STEP`（12）× 重试次数烧光，撞上 `max_tool_calls=100` 的全局上限，报 `LIMIT_REACHED`。

**这不是"上限调小了"，是"重试"这个机制本身没有生效。**

第二个相关缺陷：`MAX_TOOLS_PER_STEP = 12`（`autonomous.py:47`）在**单次尝试内**允许 12 次调用，`max_retries` 默认 3 —— 单步最坏 36 次，两步就能烧穿 100 次全局预算。

## 1.1 必修：让恢复真正改变下一轮

**核心要求：恢复分析必须进入下一次尝试的上下文。**

设计方向（你可自行优化，但语义必须成立）：

1. **累积失败历史**：`PlanStep` 增加 `attempts: list[dict]`，每轮记录
   `{attempt, tools_used, error, analysis}`
2. **重试时把它注入**：下一轮该步骤的提示词里带上
   ```
   你之前尝试过以下方式并且失败了：
     第 1 次：调用 file_write 写 notes/outline.md → 验证失败：产出格式不是 .pptx
              分析：应该直接使用 document_write
     第 2 次：调用 document_write 但 sections 为空 → 失败：没有段落
   不要重复这些做法。换一个不同的方式。
   ```
3. **强制换策略**：如果连续两次尝试**使用了完全相同的工具 + 完全相同的参数**，判定为无效重试，**立即跳过该步骤并进入恢复，不再消耗调用预算**
4. **单个步骤的预算封顶**：给每个步骤单独设上限（例如全局预算的 1/3），**防止一个步骤吃掉整个运行**
5. **`_recover` 失败时不许静默**：现在 `except (TimeoutError, Exception)` 会让分析变成一句占位文字然后继续重试——改成明确上报

# 第二部分：偏好是约束，不是指令（本轮第二个核心）

## 2.1 上一轮失败的真实机理

```
目标：做一份 15 分钟的答辩 PPT
偏好：页数更少
结果：2 页        ← 偏好被字面执行，"15 分钟"这个目标自身的约束被忽略
```

**根因：偏好被当成了"要做的事"，而不是"做这件事时的标准"。**

一个 15 分钟的汇报有它的**物理下限**——大约 10~15 页。这不是偏好，是任务本身的硬约束。偏好只能在硬约束**之内**起作用。

## 2.2 要实现的语义

```
任务目标（硬约束）  >  长期偏好（软约束）  >  默认行为
```

- **无冲突**：偏好直接生效
- **有冲突**：满足硬约束的前提下**尽可能**贴近偏好，并且**明确说明取舍**
- **无法满足**：**明确报告做不到**，不许假装满足

## 2.3 必须能通过的具体判据

**这是本轮的验收题，请照着做：**

| # | 输入 | 期望 |
|---|---|---|
| 1 | 目标「15 分钟答辩 PPT」+ 偏好「页数更少」 | 页数落在 **10~14** 之间，且说明"在 15 分钟约束下的最小值" |
| 2 | 同目标 + 偏好「图表更多」 | **每页至少 1 张图**（writer 已支持），`images` 字段 > 0 |
| 3 | 目标「3 分钟快速汇报」+ 偏好「内容详尽」 | 服从 3 分钟约束（约 3~5 页），并**说明为什么没有做详尽** |
| 4 | 目标「做一份 PPT」+ 偏好里有一条无法满足的（例如"用公司模板"但模板不存在） | **明确报告该偏好无法满足**，不是静默忽略 |

**第 4 条尤其重要：一个系统无法执行的偏好，比它明确拒绝的偏好更糟，因为用户会以为它生效了。**

## 2.4 快循环：用微型 Demo 迭代，不要每次都跑完整链路

完整 Demo 1 一次要跑 3 份资料 + 多步规划，成本高、迭代慢。

# 第七部分：推进顺序与纪律

```
第一步  修重试死循环（第一部分）→ 三个场景验收
第二步  偏好语义（第二部分）→ 微型场景先验证，再跑完整
第三步  Demo 1 后半段（第三部分）→ 三条判据全中
第四步  Demo 2 / Demo 3
第五步  工作区卫生 + 任务页实测 + 记忆页追溯
第六步  冷启动验收
第七步  文档同步 + 简历/面试题
第八步  重建交付 + 最终报告
```

**第一步和第二步没做完之前，不要开始第三步。**

**不要问：** 技术选型、命名、配色、目录结构、页面细节、文案。
**可以问：** 需要付费 / 需要外部登录 / 需要新 API Key / 无法恢复的数据破坏风险 / 产品方向真正无法判断的分歧。

**遇到环境摩擦超过 2 次就换实现方式**，不消耗轮次，不降低断言严格度。

**每完成一项就 commit**，message 写清「做了什么 + 怎么验证的」。

**不要用推断代替证据。** 写结论前先问：我有日志 / 输出 / 文件能证明吗？

**不要为了让报告好看而标 PASS。** 没跑就是 `NOT VERIFIED`，这在过去几轮里执行得很好，继续保持。
