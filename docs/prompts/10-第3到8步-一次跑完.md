### 1.5 产品定义(最终形态,不许改)

> **一个私人 agent。开局它先认识你,然后主动去公开渠道替你把该有的资料和做法找回来、验证过、装好。之后你交给它活,它带着"你的记忆 + 你的资料 + 你的做法"去干,干完给你验收,你退回一次它下次就改对。**

**它是 agent,不是 AI。** AI 给的是答案,agent 给的是结果。
用词是「执行 / 交付 / 验收」,不是「回答 / 回复 / 输出」。

**三层资产(产品题眼):**

```
① 记忆      关于你的事实     ← 精纯：记错比不记更糟
② 知识库    你的资料         ← 它自己查找、自己补充
③ Skill     你的做法         ← 它自己去找、验证、导入
        ↓ 三者结合
   按你的方式，完成你的事 —— 更快、更个性化
```

**和 OpenClaw / WorkBuddy 的区别:它们强在能力本身,同一套发给所有人;本产品强在替你干活时不用从零开始。**

## 第二部分:第 3 步 —— 分级检索(先把"更快"变成数字)

### 2.1 为什么先做这个

用户明确要求过:**"相对于其他 AI 调用工具更快的输出"**。

**但"更快"不测就是空话。** 这一步先把度量建起来 —— 因为第 4 步(Skill 层)做完,得靠它证明"真的变快了"。

### 2.2 要实现的分级

```
接到一个问题
  ↓
① 记忆里有直接相关的事实吗？      ← 最快，一次查表
  ↓ 没有
② 有匹配的 skill 吗？             ← 快，直接拿做法，跳过推理
  ↓ 没有
③ 知识库里有资料吗？              ← 中等，一次检索
  ↓ 没有
④ 才走通用路径（推理 + 工具 + 可能联网）   ← 最慢
```

**层级越靠上命中,越快、越个性化。**

### 2.3 必须做的

1. **每一级都要埋点**:命中与否、耗时毫秒、走了几级
2. **给出真实对比数据**(同一个问题,三种情况):

```
① 记忆 / skill 命中     →  ___ ms
② 知识库命中            →  ___ ms
③ 都没有，走通用路径     →  ___ ms
```

**这是"更快"的唯一证据。没有它,报告里写"更快"就是吹牛。**

3. **检索失败要如实说"我没有相关资料"**,不许降级到通用回答还不说明
4. **工作台的"本次上下文"要能看到:这次是从哪一级拿到的答案**

### 2.4 验收

- 三级各自的命中路径有测试
- 三种情况的真实毫秒数(给出测量方法与原始输出)
- 检索为空时用户能看到明确说明,而不是一段无来源的回答

## 第三部分:第 4 步 —— Skill 层(本轮核心,从零建)

### 3.1 这是什么(用户原话)

> **"查找验证skill,是你自己去github等公开渠道,找到一个甚至几个适合合适的skill文件,自己导入进去,以保证个性化。"**

**关键词:主动出去找 → 评估 → 验证 → 导入。** 不是等它从用户行为里慢慢长出来。

**这个区别很重要:**
- 靠用户行为积累 → 新产品永远是空的,前几个月没用
- **主动出去找 → 第一天它就能带着合适的东西进场**

### 3.2 Skill 的形态(技术决定,理由已给)

支持两种,用一个统一格式:

| 类型 | 内容 | 风险 | 验证方式 |
|---|---|---|---|
| **文档型** | 提示词 + 步骤说明 + 参考资料 | 低 | 用一次看结果 |
| **脚本型** | 含可执行脚本(如处理表格的 Python) | **高** | 沙箱试运行 + 看 exit code |

**允许脚本型**,因为用户的例子明确包含"简单工程"。风险用已有的三重机制兜住:**权限 + 沙箱 + 快照回滚**。

**Skill 文件格式**(自行设计,但要能表达):

```
name          名称
description   什么时候该用它
when_to_use   触发场景
body          做法（提示词模板 / 步骤）
scripts[]     可选：附带的脚本
params[]      可参数化的位置     ← 【个性化注入点】
source        来源（仓库 + commit hash）
license       许可
verified      验证结果与时间
version       版本
```

**`params[]` 是最关键的设计** —— 它就是"通用 skill"变成"你的 skill"的接口。

### 3.3 六个阶段

```
① 发现 FIND
   输入：用户档案 + 当前需求
   动作：生成搜索词 → 去 GitHub 等公开渠道搜
   现状：网络工具有 HTTP 能力（带 URL 白名单），需要扩展 GitHub 搜索

② 评估 ASSESS
   筛掉：过期、不完整、与场景不匹配
   输出：3–5 个候选，附理由（为什么适合这个人）
   ★ 这一步的产出必须给用户看，让用户选 —— 不许全自动

③ 验证 VERIFY
   安全扫描：有没有外发数据、越权访问、下载可执行文件的操作
   格式校验：符不符合本系统格式
   沙箱试运行：只读、限定目录、先建快照
   许可检查：能不能合法使用
   记录来源：仓库地址 + commit hash（可追溯、可复现）

④ 采纳 ADOPT
   用户确认 → 入库
   params 绑定到用户的档案 / 偏好    ← 【个性化在这里发生】

⑤ 使用 USE
   执行时仍过权限（环境会变，一次性验证会失效）
   叠加记忆 + 知识库 → 产出

⑥ 复盘 REVIEW
   用得好就留，不好就标记，可以换更好的
   ★ 不能省：否则 skill 库会变成另一个垃圾场
```

### 3.4 个性化在哪里发生(这条必须理解)

> **从 GitHub 导入的 skill 文件是通用的,不是个性化的。**
>
> **真正让它个性化的,是执行时那一层:**
>
> ```
> 通用 skill 骨架  ← 从公开渠道导入
>       + 你的记忆（你是某校学生会某部部长）
>       + 你的知识库（你们学校的公文格式、往期通知）
>       = 按你的样子把这件活干完
> ```

**所以:光有导入不够,记忆层和知识层必须真的接通。** 否则导入进来的还是一堆通用模板,跟直接问 ChatGPT 没区别。

**验收必须包含这一条**:一个导入的 skill,叠加用户的记忆和知识库之后,产出**明显不同于**裸用该 skill。

**用词要求:** 描述 Skill 用途时写**"用它把这类活干完"**,不写**"用它来回答这类问题"**。它是 agent,skill 是做法,不是话术。

### 3.5 前端

在「我的」下面加 **Skill 页**:已安装列表(来源、版本、验证状态、用过几次)、候选待确认、搜索新 skill、禁用/卸载。

### 3.6 第 4 步的自测(写完立刻做,再往下走)

```
[ ] 真实搜一次公开渠道，能拿到候选（给出搜索词与返回）
[ ] 候选评估能筛掉明显不合适的（给出被筛掉的和理由）
[ ] 安全扫描能拦住一个构造的恶意样例（自己造一个：含外发数据或越权访问）
[ ] 沙箱试运行建了快照、限定目录
[ ] 未经用户确认不会入库
[ ] 导入后叠加记忆+知识库，产出与裸用不同（给出两份对比）
[ ] 复盘：用一次之后能标记好坏
```

**任何一条没做,先修它,再进第 5 步。**

## 第四部分:第 5 步 —— 知识库自动补充

### 4.1 用户原话

> **"查找补充知识库"**、**"知识库等等个性化的东西,可以自己检索,自己添加。"**

现状:手动上传、手动选库、手动打标签。

### 4.2 要做的

1. **丢文件夹进来** → 扫描 → 识别类型 → 提取 → 分块 → 嵌入 → **自动归类**
2. **归类依据**:内容主题 + 已有知识库描述 + 用户档案里的领域/目标
3. **重复检测**:内容高度重合 → 提示"和已有文档 X 重合 80%,合并还是并存",**不静默重复入库**
4. **缺口补充**:发现用户提的领域在库里没资料 → **主动提议**去公开渠道找(**不是静默下载**)
5. **摄取完成后主动汇报**:"我读了 7 个文件,归到了『毕业设计』,抽出 43 个概念"

### 4.3 验收

丢一个含 5+ 文件的真实文件夹:
- 无需任何手动操作 → 全部入库、归类正确
- 概念有抽取(给出数量)
- 重复的能被识别并提示
- 完成后有主动汇报

**给真实数字。**

## 第五部分:第 6 步 —— 记忆生命周期(宜精不宜多)

### 5.1 用户原话

> **"宜精不宜多,保证记忆库的精与纯净。"**

现状:有表、有写入链路、有确认机制,**但没有任何生命周期管理** —— 搜 `decay` / `consolidat` = 0 个文件。

### 5.2 要做的

1. **合并** —— 语义高度重合 → 合并成一条,`use_count` 累加,**不新增**
2. **衰减** —— 长期未用的低置信记忆 → 转 `decayed`,**退出检索但不删除**
3. **定期整理** —— 后台每日扫描 → 输出整理报告(合并几条、衰减几条、几处冲突)
4. **冲突可见** —— 矛盾记忆 → 生成冲突候选问用户,**已有条目不变**
5. **主动复习** —— 被用到就更新 `last_used_at` / `use_count`,并在「我的」里显示哪些记忆真的在被使用
6. **可遗忘且真的遗忘** —— 删除后检索不到、注入不到

### 5.3 验收(必须给真实数字)

```
记忆总数 / 对话轮数 / 交付次数
被合并的条数
被衰减的条数
平均 use_count       ← 证明记忆真的在被用，不是死数据
用户拒绝的候选占比    ← 证明确认机制在工作
一份真实整理报告（含具体条目）
```

## 第八部分:工程铁律(不变)

1. **三态分明**:PASS / FAILED / NOT VERIFIED
2. **不用推断代替证据**:写结论前先问,我有日志 / 输出 / 文件能证明吗?
   —— "用推断代替证据"已犯过三次(作者身份推断、钩子没触发推断、截断的文件名推断)
3. **禁止吞异常**,禁止 `except: pass`。**新增代码里任何"失败就回退成 `None`/空/默认"的地方都要重新审视** —— 这个形状已出现 9 次,最近一次是向导主路径从来没成功过
4. **一个决定只能有一个实现者**。"某路径/配置从哪来"只允许一处实现;加第 5 个之前先找齐前 4 个
5. **不可谈判的行为不许破坏**:本地优先 · 记忆精纯 · 记忆触发是执行沉淀 · 验证与验收分离 · 偏好是约束不是指令 · 失败可见 · 一个 AI 一个语气 · 安装后独立可用
6. **Demo / 测试在隔离环境做**,禁止污染正式仓库
7. **编码规则**:见 1.4
8. **每完成一项就 commit**,message 写清「做了什么 + 怎么验证的」
9. **遇到环境摩擦超过 2 次就换实现方式**,不消耗轮次,不降低断言严格度
