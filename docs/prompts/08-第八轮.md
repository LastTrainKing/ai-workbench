## 第〇部分:产品定义(最终,不许改)

### 0.1 一句话

**一个私人 agent。开局它先认识你,然后主动去公开渠道替你把该有的资料和做法找回来、验证过、装好。之后你交给它活,它带着"你的记忆 + 你的资料 + 你的做法"去干,干完给你验收,你退回一次它下次就改对。**

### 0.1.1 它是 agent,不是 AI(用户明确纠正过,不许再漂回去)

```
AI     你问 → 它答 → 你自己去做
Agent  你说要什么 → 它去做 → 做完给你看
```

**AI 给的是答案,agent 给的是结果。**

这个字不是措辞问题,是产品分类问题。它决定:

- 用词:**"执行 / 交付 / 验收",不是"回答 / 回复 / 输出"**
- 每个功能的落点:**它去做了什么事,不是它说了什么话**
- 成功的判据:**活干完了没有 → 干得对不对 → 你认不认**,而不是"答得好不好"
- 界面的组织:**以"事"为单位(工作台 / 产出物 / 验收)**,不是以"对话"为单位

**个性化的真正含义也随之改变:**

> 不是"它更懂你说什么",而是**"它更懂该怎么替你干"**。

```
记忆   →  它知道上次这么干你为什么退回,这次不重犯
知识   →  它知道东西去哪找,不用每次问你
Skill  →  它知道这类活你的做法是什么,不用重新推理
```

**三层资产的作用,是让"这次"站在"上次"的肩膀上。**

通用 agent 每接一个活都从零开始;本产品第二次干同类的活时,已经知道你是谁、你库里的东西在哪、你的做法长什么样。

**"更快"的真正来源不是模型跑得快,是不用从零再来一遍。**

### 0.2 核心机制(这是产品的题眼)

```
开局:它问你 → 你是谁、你要什么、你想让它做什么
        ↓
   ┌────────────────────────────────────────┐
   │  ① 记忆      关于你的事实(精纯、有生命周期)  │
   │  ② 知识库    你的资料(它自己查找、自己补充)  │
   │  ③ Skill     你的做法(它自己查找、验证、导入)│
   └────────────────────────────────────────┘
        ↓  三者结合
   按你的方式,完成你的事 —— 更快、更个性化
```

### 0.3 和 OpenClaw / WorkBuddy 的区别(必须理解)

它们强在**能力本身**:工具多、模型强、生态大。**同一套能力发给所有人。**

本产品强在**它替你干活时不用从零开始**:

| | 通用 agent | 本产品 |
|---|---|---|
| 接到"写个活动通知" | 从零推理:这是什么 → 搜 → 猜格式 → 问你要什么口吻 → 才动手 | 开局就知道你是某校学生会某部部长 → 直接动手,格式和口吻都是你的 |
| 接到"做个汇报 PPT" | 用通用最佳实践 | 用它**在你身上验证过的**做法,引用**从你库里查出的**资料 |

**它们卖的是能力;本产品卖的是"替你干这类活时,已经知道你的事了"。**

**能力可以复制,挑选不行** —— 因为挑选的输入是"你是谁",而那个只有你有。

### 0.4 一个用户给的例子(用来校准粒度,不许偏离)

> 一名大三艺术类学生,同时是学生会某分部部长、班干部。
> 需要它查找并记忆:学生工作、艺术基础、简单工程这三类知识。
> 保证无论问学生相关、做 PPT、还是问艺术问题,都能比其他 AI **更快、更个性化**。

**开局对话问完,系统就应该自动建立:**

```
知识库(自己查找、自己补充)
  学生工作 → 学生会流程、活动策划、通知写作、部门协作
  艺术基础 → 设计原理、色彩、构成、艺术史脉络
  简单工程 → 基础工具、文档/表格/演示的制作规范

Skill(自己查找、验证、导入)
  "写活动通知"     → 本校公文格式 + 部长口吻
  "做汇报 PPT"     → 给老师看 / 给同学看,两套做法
  "解答专业课问题" → 先讲原理还是先给例子
```

### 0.5 三条原则(用户原话,写进 README)

**本地 · 精纯 · 私定**

- **本地**:档案、记忆、偏好、知识全留在本机
- **精纯**:记忆宜精不宜多,**记错比不记更糟**;skill 也一样,**没验证过的比没有更糟**
- **私定**:不是让用户配置 Agent,而是 Agent 随着使用逐渐成为"这个人的 AI"

### 0.6 这个产品的立场(写进 README,它是项目存在的理由)

> **AI 的浪潮下,普通学生感到的不应该是恐惧和摆烂,而是利用好 AI 的能力,去实现自己天马行空的设想。**
>
> **这个项目不是"做出来了什么",而是"一个学生能通过 AI 完成一个完整的、符合自己预期的项目"。**

## 第二部分:开放与冻结(这一节决定你能动什么)

用户已授权"哪怕推翻重来"。但"重写"只有在有安全网时才成立。

### 2.1 不可谈判(改了就是产品坏了)

- **本地优先** —— 档案/记忆/偏好/知识留在本机,发给模型的上下文必须可见可控
- **记忆精纯** —— 有生命周期:合并、衰减、遗忘、可追溯
- **记忆的触发是执行沉淀**,不是聊天副产品
- **验证与验收分离** —— 机器 `verified`,用户 `accepted`,用户是最终裁判
- **偏好是约束不是指令** —— `任务硬约束 > 长期偏好 > 默认行为`
- **失败可见** —— 无法满足的偏好/无法执行的 skill 必须明确报告,不许静默忽略
- **一个 AI,一个语气** —— 用户不需要管理多个 Agent
- **安装后独立可用** —— 删掉开发目录仍然能跑

### 2.2 重新开放(之前被当成资产,现在按最终定义重估)

- **信息架构 / 导航 / 页面划分** —— 全部重排
- **引擎里服务不了这版定义的模块和抽象** —— **不为"已经写了"而保留**
- 三个产品的化石层(知识闭环 / 自主 Agent / 个人 AI OS 的遗留表与页面)
- 测试里**测具体实现**的可以重写;**测不变量**的必须保留
- 技术栈与目录结构可重新考虑,不用"反正已经这样了"当理由

### 2.3 重写契约(硬规则,不接受讨论)

> **重写可以。但 2.1 那些行为在重写后必须全部仍然为真。**
>
> **证明方式就是那 438 个后端测试 + 114 个前端测试。它们是安全网,是唯一让"重写"区别于"赌博"的东西。**

操作纪律:

```
改任何模块之前 → 先跑测试,确认是绿的
改完之后       → 再跑一遍,绿了才算改完
测试对行为说谎 → 可以改测试,但必须说明为什么,
                 并且改完的测试要能测出原来那个错误
```

### 2.4 垂直切片(防止"推翻重来"变成第五个半成品)

> **每一轮结束,必须有一条端到端可用的完整链路。**
> **不允许出现"四个模块都改了一半"。**

广度可以铺,深度只有一条。**广度几乎免费,深度不免费。**

## 第三部分:本轮要建的东西(按依赖顺序)

### 能力 A —— 开局对话(整个产品的入口)

**用户原话:"开局你给我一个对话框,问完我的基础信息,我需要的等等等。"**

这**不是注册表单,是一次对话**。它要拿到三类东西:

```
① 你是谁      身份、阶段、领域、正在做的事
② 你要什么    当前目标、长期方向、最近在忙什么
③ 你要它怎么帮你  输出风格、语言、汇报对象、禁忌、要不要先确认
```

**关键:第 ③ 类直接变成初始的偏好和 skill 配置。**

设计要求:

1. **允许一句话自由描述** —— 例如「我是大三艺术类,学生会某分部部长,也是班干,最近在准备毕设和实习」。AI 抽取 → **展示它理解成了什么** → 用户确认 → 才写入
2. **两条路都必须通**:「从介绍自己开始」和「先随便看看」,**不许强制填表**
3. **对话结束要产出真实的东西**,不是一句"设置完成":
   ```
   已建立:
     档案    身份/阶段/领域/当前目标
     知识分类  学生工作 · 艺术基础 · 简单工程   ← 空的知识库骨架,等资料
     初始 skill  3 条候选(来自公开渠道,待验证)
     偏好     输出语言、风格、汇报对象
   → 问用户:这个理解对吗?哪里要改?
   ```
4. **结束时主动提出**:「要不要我现在去找几个适合你的 skill?」← 这是能力 B 的入口

**修掉一个已知缺陷:** `frontend/src/pages/LoginPage.tsx:104` 注册与登录共用 `navigate(redirectTo)`,**新用户注册后永远进不了 `/welcome`**。注册分支改为跳 `/welcome`。

### 能力 B —— Skill 层(本轮的核心,从零建)

**用户原话:"查找验证skill,是你自己去github等公开渠道,找到一个甚至几个适合合适的skill文件,自己导入进去,以保证个性化。"**

**关键词:主动出去找 → 评估 → 验证 → 导入。** 不是等它从用户行为里慢慢长出来。

#### B1. Skill 的形态(技术决定,理由已给)

支持两种,用一个统一格式:

| 类型 | 内容 | 风险 | 验证方式 |
|---|---|---|---|
| **文档型** | 提示词 + 步骤说明 + 参考资料 | 低 | 用一次看结果 |
| **脚本型** | 含可执行脚本(如处理表格的 Python) | **高** | 沙箱试运行 + 看 exit code |

**允许脚本型,因为用户的例子明确包含"简单工程"。** 风险用已有的三重机制兜住:权限 + 沙箱 + 快照回滚。

**Skill 文件格式**(自行设计,但要能表达):

```
name          名称
description   什么时候该用它
when_to_use   触发场景
body          做法(提示词模板 / 步骤)
scripts[]     可选:附带的脚本
params[]      可参数化的位置  ← 个性化注入点
source        来源(仓库 + commit hash)
license       许可
verified      验证结果与时间
version       版本
```

#### B2. 五个阶段的实现

```
① 发现 FIND
   输入:用户档案 + 当前需求
   动作:生成搜索词 → 去 GitHub 等公开渠道搜
   现状:网络工具有 HTTP 能力(带 URL 白名单),需要扩展 GitHub 搜索

② 评估 ASSESS
   筛掉:过期、不完整、与场景不匹配
   输出:3–5 个候选,附理由(为什么适合这个人)
   ★ 这一步的产出必须给用户看,让用户选 —— 不许全自动

③ 验证 VERIFY
   安全扫描:有没有外发数据、越权访问、下载可执行文件的操作
   格式校验:符不符合本系统格式
   沙箱试运行:只读、限定目录、先建快照
   许可检查:能不能合法使用
   记录来源:仓库地址 + commit hash(可追溯、可复现)

④ 采纳 ADOPT
   用户确认 → 入库
   参数位置绑定到用户的档案/偏好 ← 【个性化在这里发生】

⑤ 使用 USE
   执行时仍过权限(环境会变,一次性验证会失效)
   叠加记忆 + 知识库 → 产出

⑥ 复盘 REVIEW
   用得好就留,不好就标记,可以换更好的
   ★ 不能省:否则 skill 库会变成另一个垃圾场
```

#### B3. 个性化在哪里发生(这条必须理解)

> **从 GitHub 导入的 skill 文件是通用的,不是个性化的。**
>
> **真正让它个性化的,是执行时那一层:**
>
> ```
> 通用 skill 骨架  ← 从公开渠道导入
>       +
> 你的记忆(你是某校学生会某部部长)
>       +
> 你的知识库(你们学校的公文格式、往期通知)
>       =
> 按你的样子把这件活干完
> ```

**所以:光有导入不够,记忆层和知识层必须真的接通。** 否则导入进来的还是一堆通用模板,跟直接问 ChatGPT 没区别。

**用词要求:** 描述 Skill 的用途时,写**"用它把这类活干完"**,不要写**"用它来回答这类问题"**。它是 agent,skill 是做法,不是话术。

#### B4. 前端

在「我的」下面加 **Skill 页**:已安装列表(来源、版本、验证状态、用过几次)、候选待确认、搜索新 skill、禁用/卸载。

### 能力 C —— 知识库自动补充

**用户原话:"查找补充知识库"、"知识库等等个性化的东西,可以自己检索,自己添加"。**

现状:手动上传、手动选库、手动打标签。

要做:

1. **丢文件夹进来** → 扫描 → 识别类型 → 提取 → 分块 → 嵌入 → **自动归类**
2. **归类依据**:内容主题 + 已有知识库描述 + 用户档案里的领域/目标
3. **重复检测**:内容高度重合 → 提示"和已有文档 X 重合 80%,合并还是并存",**不静默重复入库**
4. **缺口补充**:发现用户提的领域在库里没有资料 → **主动提议**去公开渠道找(不是静默下载)
5. **摄取完成后主动汇报**:"我读了 7 个文件,归到了『毕业设计』,抽出 43 个概念"

**验收:** 丢一个含 5+ 文件的真实文件夹 → 无需手动操作 → 全部入库、归类正确、概念有抽取、重复能被识别。给真实数字。

### 能力 D —— 记忆生命周期(宜精不宜多)

**用户原话:"宜精不宜多,保证记忆库的精与纯净。"**

现状:有表、有写入链路、有确认机制,**但没有任何生命周期管理**。

要做:

1. **合并** —— 语义高度重合 → 合并成一条,`use_count` 累加,**不新增**
2. **衰减** —— 长期未用的低置信记忆 → 转 `decayed`,**退出检索但不删除**
3. **定期整理** —— 后台每日扫描 → 输出整理报告(合并几条、衰减几条、几处冲突)
4. **冲突可见** —— 矛盾记忆 → 生成冲突候选问用户,**已有条目不变**
5. **主动复习** —— 被用到就更新 `last_used_at`/`use_count`,并在「我的」里显示哪些记忆真的在被使用
6. **可遗忘且真的遗忘** —— 删除后检索不到、注入不到

**验收(必须给真实数字):**

```
记忆总数 / 对话轮数 / 交付次数
被合并的条数 · 被衰减的条数
平均 use_count       ← 证明记忆在被用,不是死数据
用户拒绝的候选占比    ← 证明确认机制在工作
一份真实整理报告(含具体条目)
```

### 能力 E —— 分级检索(这是"更快"的实现方式)

用户明确要求"相对于其他 ai 调用工具更快的输出"。**实现方式是分级,不是把模型换强。**

```
接到一个问题
  ↓
① 记忆里有直接相关的事实吗?    ← 最快,一次查表
  ↓ 没有
② 有匹配的 skill 吗?           ← 快,直接拿做法,跳过推理
  ↓ 没有
③ 知识库里有资料吗?            ← 中等,一次检索
  ↓ 没有
④ 才走通用路径(推理+工具+可能联网)  ← 最慢
```

**层级越靠上命中,越快、越个性化。**

要做:

- 每一级都要有**命中率与耗时指标**(证明"更快"不是感觉)
- 检索失败要**如实说"我没有相关资料"**,不许降级到通用回答还不说明
- 这一层要能在工作台的"本次上下文"里看见:**这次是从哪一级拿到的答案**

**验收:** 同一个问题,在有 skill / 有资料 / 都没有 三种情况下的耗时对比。**给真实毫秒数。**

## 第四部分:安装程序

### 4.1 目标体验

## 第八部分:工程铁律

1. **禁止假数据、假状态、假成功**,标 `NOT VERIFIED`
2. **禁止吞异常**,禁止 `except: pass`。**新增代码里任何"失败就回退成 None/空/默认"的地方都要重新审视** —— 这个形状在本项目已出现 8 次,最近一次关掉了整个记忆学习回路
3. **不许破坏已有数据**,动手前 `git commit`
4. **旧路由继续可用**
5. **Secret 零容忍**:安装包、安装目录、截图里都不能有真实凭据
6. **Demo 在隔离环境做**,禁止污染正式仓库
7. **编码陷阱**:`.bat` 纯 ASCII(**且不能用 shell 内联命令写 .bat**,`\v`/`\r` 会被折叠);`.ps1` 含非 ASCII 必须带 BOM
8. **不要用推断代替证据。** 写结论前先问:我有日志/输出/文件能证明吗?
   —— 上一轮从"作者身份不同"推出"Agent 污染了仓库",实际是另一个进程用 `-c user.email=` 提交的。**用"审计日志里没有"去排除,比用"身份不一样"去指认更可靠。**
9. **遇到环境摩擦超过 2 次就换实现方式**,不消耗轮次,不降低断言严格度
