### 0.3 一个已经踩过的坑：猜阈值，两次都错了

第 3 步里，"知识库有没有回答这个问题"这个判断，**两次尝试、两次失败**：

1. **用检索器的融合分数 + 0.35 阈值** —— 一个知识库里完全没有的问题
   （"解释量子纠缠和相对论"）**拿到了 0.70 分**。混合分数是在返回结果集内归一化的，
   所以不管有没有命中，它的最高分都很高。**在它上面卡阈值分不出"覆盖了"和"五段勉强相关"。**
2. **用词项重叠**（第 1 层用的同一个信号）—— 同一个不相关的问题**命中了知识层**，
   因为中文双字组在常用词上就会撞："关系"、"一下"。**一个在虚词上就会触发的信号，不是相关性信号。**

**由此确立一条规则，本轮继续适用：**

> **在选阈值之前，先测分数的分布。**
> **连续两次靠猜，就说明该去测量而不是再猜一次。**

并且：**两次猜测都必须留下证据**，写进 PROGRESS.md，而不是悄悄换一个数再试。

## 第三部分：第 4 步 —— Skill 层（本轮核心，从零建）

### 3.1 用户原话

> **"查找验证skill，是你自己去github等公开渠道，找到一个甚至几个适合合适的skill文件，自己导入进去，以保证个性化。"**

**关键词：主动出去找 → 评估 → 验证 → 导入。**

- 靠用户行为积累 → 新产品永远是空的，前几个月没用
- **主动出去找 → 第一天它就能带着合适的东西进场**

### 3.2 Skill 的形态

| 类型 | 内容 | 风险 | 验证方式 |
|---|---|---|---|
| **文档型** | 提示词 + 步骤说明 + 参考资料 | 低 | 用一次看结果 |
| **脚本型** | 含可执行脚本（如处理表格的 Python） | **高** | 沙箱试运行 + 看 exit code |

**允许脚本型**（用户的例子明确包含"简单工程"），风险用已有三重机制兜住：
**权限 + 沙箱 + 快照回滚**。

**Skill 格式**（自行设计，但要能表达）：

```
name          名称
description   什么时候该用它
when_to_use   触发场景
body          做法（提示词模板 / 步骤）
scripts[]     可选：附带的脚本
params[]      可参数化的位置     ← 【个性化注入点】
source        来源（仓库 + commit hash）
license       许可
verified      验证结果与时间
version       版本
```

**`params[]` 是最关键的设计** —— 它就是"通用 skill"变成"你的 skill"的接口。

### 3.3 六个阶段

```
① 发现 FIND
   输入：用户档案 + 当前需求
   动作：生成搜索词 → 去 GitHub 等公开渠道搜
   现状：网络工具有 HTTP 能力（带 URL 白名单），需要扩展 GitHub 搜索

② 评估 ASSESS
   筛掉：过期、不完整、与场景不匹配
   输出：3–5 个候选，附理由（为什么适合这个人）
   ★ 必须给用户看，让用户选 —— 不许全自动

③ 验证 VERIFY
   安全扫描：有没有外发数据、越权访问、下载可执行文件的操作
   格式校验：符不符合本系统格式
   沙箱试运行：只读、限定目录、先建快照
   许可检查：能不能合法使用
   记录来源：仓库地址 + commit hash（可追溯、可复现）

④ 采纳 ADOPT
   用户确认 → 入库
   params 绑定到用户的档案 / 偏好    ← 【个性化在这里发生】

⑤ 使用 USE
   执行时仍过权限（环境会变，一次性验证会失效）
   叠加记忆 + 知识库 → 产出

⑥ 复盘 REVIEW
   用得好就留，不好就标记，可以换更好的
   ★ 不能省：否则 skill 库会变成另一个垃圾场
```

### 3.4 个性化在哪里发生（这条必须理解）

> **从 GitHub 导入的 skill 文件是通用的，不是个性化的。**
>
> **真正让它个性化的，是执行时那一层：**
>
> ```
> 通用 skill 骨架  ← 从公开渠道导入
>       + 你的记忆（你是某校学生会某部部长）
>       + 你的知识库（你们学校的公文格式、往期通知）
>       = 按你的样子把这件活干完
> ```
>
> **光有导入不够，记忆层和知识层必须真的接通。** 否则导入进来的还是一堆通用模板，
> 跟直接问 ChatGPT 没区别。

**用词要求：** 描述 Skill 用途时写 **"用它把这类活干完"**，
不写 **"用它来回答这类问题"**。它是 agent，skill 是做法，不是话术。

### 3.5 前端

在「我的」下面加 **Skill 页**：已安装列表（来源、版本、验证状态、用过几次）、
候选待确认、搜索新 skill、禁用/卸载。

## 第四部分：第 5 步 —— 知识库自动补充

### 4.1 用户原话

> **"查找补充知识库"**、**"知识库等等个性化的东西，可以自己检索，自己添加。"**

现状：手动上传、手动选库、手动打标签。

### 4.2 要做的

1. **丢文件夹进来** → 扫描 → 识别类型 → 提取 → 分块 → 嵌入 → **自动归类**
2. **归类依据**：内容主题 + 已有知识库描述 + 用户档案里的领域/目标

5. **摄取完成后主动汇报**："我读了 7 个文件，归到了『毕业设计』，抽出 43 个概念"

### 4.3 验收

## 第五部分：第 6 步 —— 记忆生命周期（宜精不宜多）

### 5.1 用户原话

> **"宜精不宜多，保证记忆库的精与纯净。"**

现状：有表、有写入链路、有确认机制，**但没有任何生命周期管理**
—— 搜 `decay` / `consolidat` = 0 个文件。

### 5.2 要做的

1. **合并** —— 语义高度重合 → 合并成一条，`use_count` 累加，**不新增**
2. **衰减** —— 长期未用的低置信记忆 → 转 `decayed`，**退出检索但不删除**
3. **定期整理** —— 后台每日扫描 → 输出整理报告（合并几条、衰减几条、几处冲突）
4. **冲突可见** —— 矛盾记忆 → 生成冲突候选问用户，**已有条目不变**
5. **主动复习** —— 被用到就更新 `last_used_at` / `use_count`，
   并在「我的」里显示哪些记忆真的在被使用
6. **可遗忘且真的遗忘** —— 删除后检索不到、注入不到

### 5.3 验收（必须给真实数字）

```
记忆总数 / 对话轮数 / 交付次数
被合并的条数
被衰减的条数
平均 use_count       ← 证明记忆真的在被用，不是死数据
用户拒绝的候选占比    ← 证明确认机制在工作
一份真实整理报告（含具体条目）
```

## 第八部分：工程铁律（不变）

1. **三态分明**：PASS / FAILED / NOT VERIFIED
2. **不用推断代替证据**：写结论前先问，我有日志 / 输出 / 文件能证明吗？
   —— "用推断代替证据"已犯过三次（作者身份推断、钩子没触发推断、截断的文件名推断）
3. **禁止吞异常**，禁止 `except: pass`。**新增代码里任何"失败就回退成 `None`/空/默认"
   的地方都要重新审视** —— 这个形状已出现 9 次，最近一次是向导主路径从来没成功过
4. **一个决定只能有一个实现者**。"某路径/配置从哪来"只允许一处实现；
   加第 5 个之前先找齐前 4 个
5. **不可谈判的行为不许破坏**：本地优先 · 记忆精纯 · Skill 精纯（没验证过的比没有更糟）·
   记忆触发是执行沉淀 · 验证与验收分离 · 偏好是约束不是指令 · 失败可见 ·
   一个 AI 一个语气 · 安装后独立可用
6. **Demo / 测试在隔离环境做**，禁止污染正式仓库
7. **编码规则**：见 1.6
8. **每完成一项就 commit**，message 写清「做了什么 + 怎么验证的」。
   提交信息用**文件传**（`git commit -F`）—— PowerShell 会把消息里的反引号当转义符，
   这个项目已经因此丢过几次标识符名字
9. **遇到环境摩擦超过 2 次就换实现方式**，不消耗轮次，不降低断言严格度
