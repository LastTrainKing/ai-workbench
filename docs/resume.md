## 完整版本（简历项目栏）

### AI Workbench · 本地优先的私人 AI Agent
*个人项目 · 2026 · Python / TypeScript / Rust*

一个运行在 Windows 上的桌面 AI Agent。用户说出目标，它在授权范围内操作文件、代码、Git、终端，验证结果，失败时自行修复，全部过程可追溯、可回滚。

**核心能力**

- **自主 Agent 循环**：PLAN → EXECUTE → OBSERVE → VERIFY → FIX → RETRY → DONE。关键设计是**模型决定做什么、代码决定是否成功**——验证是一次工具调用，读它的 exit code，而不是让模型评价自己的输出。支持暂停 / 恢复 / 取消，取消会真正终止子进程树。
- **42 个计算机工具 + 权限体系**：文件、代码、终端、Git、构建测试、进程、网络、屏幕观察。四级权限（观察 / 工作区 / 系统 / 完全），deny 优先于 allow，受保护路径（SSH 私钥、浏览器凭据、项目 .env）内置且设置无法解除。高风险命令弹确认框并说明原因与影响。
- **快照 / Diff / 回滚**：运行前自动快照，结束后可看逐文件 diff。回滚记录运行前后两份 manifest，**如果文件在运行结束后被改动过就拒绝回滚**，避免销毁用户自己的修改。
- **Personal Context Layer**：Profile / Memory / Preferences / Context 四层严格分离。记忆评估器做规则预筛 + 模型结构化判定 + 去重 + 冲突检测 + 置信度路由；敏感信息永不落库；冲突生成候选问用户而非自动覆盖。上下文组装有硬 token 预算并按优先级裁剪，实际注入内容全部可回看。
- **RAG 知识库**：文档导入 → 解析 → 分块 → 向量化 → 混合检索 → 重排 → 带引用作答。
- **文档产物**：`document_write` / `document_read` 支持 docx / xlsx / pptx / pdf / md / csv，风格读用户偏好（简洁 / 学术 / 商务），**生成后必须回读校验**才算完成。
- **Windows 桌面交付**：Tauri + WebView2 原生窗口，无浏览器、无地址栏、无控制台窗口。关闭应用时通过 Windows 作业对象（`KILL_ON_JOB_CLOSE`）保证后端服务被清理，崩溃或被强杀也不例外。

**工程数据**

- 后端约 2 万行 Python（FastAPI + PostgreSQL + Redis + Qdrant），29 张表
- 前端约 1.2 万行 TypeScript（React + Vite），Rust 约 900 行
- 测试：后端单元测试 + 前端 114 个 + 三套真实运行测试脚本（浏览器交互 26+22 项、桌面九条断言 × 三种退出场景、API 31 项、记忆闭环 18 项）
- 交付：EXE + NSIS 安装包 + 源码包，密钥扫描 0 处

## 可以单独展开的三个技术点

### 1. 验证交给代码，不交给模型

大多数 Agent 框架让模型给自己打分。这里 VERIFY 是一次工具调用，读 exit code——`run_tests` 返回 1 就是失败，模型说"应该修好了"没用。

配套的细节是**区分诊断步骤和断言步骤**："运行测试并记录失败"这一步的目的是看到失败，exit 1 说明它正常工作了；"修复函数"这一步 exit 1 就是失败。这个区分是被测试逼出来的——Demo 里 Agent 明明正确定位了 bug，却因为诊断步骤被判失败而反复重试到耗尽次数。

### 2. 三层套娃的关窗 bug

用户反馈"关掉窗口后数据库和 API 还在跑"。第一次猜"关窗钩子没触发"——**错**。加了全链路生命周期日志之后：

1. 钩子确实触发了
2. `project_root` 字段在"后端已运行"的提前返回路径上永远是 `None`，`stop()` 在守卫处直接返回——而这正是用户每次重开程序走的路径
3. 真正的拦路虎：停止脚本的注释里含 UTF-8 破折号，**cmd.exe 按 ANSI 读 .bat**，字节被破坏后注释里的词被当成命令执行，脚本 0.3 秒就以 255 退出

修好前两层它依然跑不起来，因为脚本自己是坏的。最终方案是作业对象（内核级进程分组）+ 生命周期日志 + 纯 ASCII 脚本 + BOM 检查。

**教训**：加日志之前的所有结论都是假设。这个项目三轮下来，我没有一次推断是对的。

### 3. 记忆为什么不许自动覆盖

用户说"以后都用 React"，三个月后说"改用 Vue 了"。哪条对？只有用户知道。自动覆盖等于替用户做他才有资格做的判断。

所以矛盾不落库、不覆盖，而是生成候选问用户。

这里也有个真实的坑：最初的冲突检测是**词法的**（字符重合度 + 否定词）。它对近义改写有效，但对真正的矛盾完全失效——"默认用 React"和"改用 Vue 了"意思相反，用词却几乎不重合。修复是把这个问题交给模型（它本来就在被调用，多问一句"是否与已有记忆矛盾"零额外成本），语义矛盾正是模型擅长而字符串比较不擅长的事。

## 第五轮：让"第二次做对"真正成立

第四轮证明了它能产出真东西（一份 70 KB / 11 页的真实 PPT）。第五轮要证明的是**它真的会学习**——对失败的学习，和对用户偏好的学习。这一轮修掉的四个缺陷都来自真实运行，不是设想。

### 1. 重试机制从来没生效过（最有深度的一处）

现象：一次运行在**两步里烧掉 105 次工具调用**，撞上全局 100 次上限，报 `LIMIT_REACHED`。

根因不是上限太小，而是 `_recover` 的返回值被丢掉了：那段根因分析进了事件流给人看，**没有回到模型的下一次尝试里**。于是"恢复"只是把同一件事再做一遍——同样的步骤描述、同样的工具、同样的参数、同样的上下文 → 同样的决定 → 同样的失败。调大 `max_tool_calls` 只是把墙往后挪。

修法是四件事，缺一不可：
1. `PlanStep.attempts` 记录每次尝试的工具、参数、错误、分析；
2. **把历史注入下一次尝试的提示词**（"你之前已经尝试过…不要重复"）——这才是真正的修复；
3. 连续两次「完全相同的工具 + 完全相同的参数」判定为**无效重试**，立即停止该步骤；
4. 单步预算封顶（全局的 1/3），一步吃不掉整个运行。

顺带发现第二个同类缺陷：恢复调用的 600 token 预算让推理模型抛 `ai_reasoning_budget_exhausted`（思考阶段用光预算，**没有任何输出**，不是截断），于是"恢复"静默退化成"放弃"。实测后统一改为 6000 上限 + 超限自动升档——`max_tokens` 是上限不是目标，给足了不会多花钱。

验收：三个场景真跑（正常任务不触发恢复 / 失败后第 2 次尝试内容确实不同 / 达上限后停止该步骤而不是烧穿预算），全部 PASS。

### 2. 偏好被当成指令执行

```
目标：做一份 15 分钟的答辩 PPT
偏好：页数更少
结果：2 页
```

没有任何报错，所有检查都通过。问题在于"页数更少"被当成**要做的事**，而不是**做这件事时的标准**——一个 15 分钟的汇报有它的物理下限。

实现的语义是 `任务目标（硬约束） > 长期偏好（软约束） > 默认行为`，关键做法是**硬约束在代码里推导**（15 分钟 → 10~14 页，3 分钟 → 3~5 页），不由模型决定；偏好则按"意图"逐条解析（一条记忆可能含两个偏好，整句匹配会静默丢掉一个），分别给出 `applied` / `bounded` / `unsatisfiable` 三种结论。**无法执行的偏好必须报告**——一个被静默忽略的偏好比被明确拒绝的更糟，因为用户会以为它生效了。

### 3. 图表从来没画出来过（失败可见性的直接收益）

`_render_chart()` 在渲染失败时返回 `None` 并打一条 warning，于是"图表没画出来"和"这一页本来没有图表"变得无法区分：幻灯片出来了，结果是成功的，用户"图表更多"的偏好被静默地没有执行。

改成抛异常之后，立刻暴露出真正的契约缺陷：模型发送的 `series` 是 `[{name, data}]`（字段名最自然的读法，也是所有图表库接受的形式），而实现只接受私有形状 `{name: [values]}`。**如果当初那个 `None` 还在，这个 bug 会一直以"用户偏好没生效"的形式存在，而且永远查不到。**

### 4. 两个并发运行会在记忆计数上互相阻塞（在 `pg_stat_activity` 里找到的）

```
pid=24344 state=active wait=Lock/transactionid since=0:04:40
  q='UPDATE memory_entries SET last_used_at=...'
blocked=24344 by=20740 state_of_blocker=idle in transaction
```

两个运行都是对的，只是没法同时记录"我用过这条记忆"。原因是上下文组装器在**运行的会话**上更新使用计数，而那个会话要开几分钟；一把行锁握几分钟，就会把每一个用到同一条记忆的并发运行串行化。

修法是两点：计数写入放进**自己的短事务**（毫秒级释放锁），并且加**锁超时**（1.5s）——计数是遥测，值得写，不值得等。测试里专门有一条回归用例断言"被占用的行只造成有界等待"。

### 5. 顺带修掉的一致性问题

- `_final_verify` 把 `file_exists` 回答"否"当成通过——同一个 bug 在 `_verify_step` 里已修，最终闸门还留着；
- 有失败步骤的运行仍可能报 `COMPLETED`；
- **运行 `FAILED` 却登记了 `verified=True` 的产出物**：新增 `PARTIAL` 状态，未完成运行留下的文件会带一条失败的 `run_state` 检查，不再挂 `verified`；
- 工作区默认值从 `%USERPROFILE%\Desktop\AI Workbench Workspace` 改为 `<项目>/.runtime/workspace`，并建立 `deliverables/ notes/ sources/ .tmp/` 目录约定——一个"私人工作台"不该把杂物倒在用户桌面上。

### 这一轮的可量化结果

- 重试场景 A/B/C 全 PASS；卡死步骤实际只花 33 次工具调用（上限 100）
- 偏好四判据：15 分钟 + 页数更少 → 10~14 页并说明取舍；图表更多 → images > 0；3 分钟 + 详尽 → 服从时长并说明做不到详尽；模板不存在 → 明确报告
- 新增单测/集成测试 42 条（恢复机制 13、偏好语义 25、工作区 10、并发锁 4）
- 桌面从 19 个顶层条目降到 13 个（全是用户的），项目杂物全部归档、未删除任何文件
