## A. Architecture & design

### 1. 为什么选择 FastAPI？

**考什么** — 是否理解框架选型的取舍，而不是跟风。

**实际实现** — `backend/app/main.py` 用 `create_app()` 工厂创建应用，49 个路径由
`app/api/v1/*.py` 的 router 聚合；Pydantic v2 同时承担请求校验与响应序列化；
`/docs`、`/redoc`、`/openapi.json` 由框架自动生成。

**标准回答** — 三个原因：一是原生 async，我的检索链路（Qdrant + PostgreSQL + 模型调用）
全是 IO 密集，同步框架会白白浪费并发；二是 Pydantic 与框架同源，校验、序列化和 OpenAPI
文档是一份代码产出的，不需要维护两套 schema；三是依赖注入足够轻，`get_db` 和
`get_current_user` 都是普通函数，不引入额外概念。代价是生态比 Django 小，但这个项目
不需要 admin、模板或 ORM 自动迁移。

**追问** — "FastAPI 和 Django 怎么选？" 需要带后台管理、模板渲染、成熟权限体系选 Django；
面向 API、追求吞吐与类型安全选 FastAPI。"怎么处理同步阻塞调用？" 放到线程池或独立 worker，
这个项目里文件解析和分块就是放在 worker 里跑的。

### 2. 描述你的系统架构。

**考什么** — 能不能用一张图讲清楚系统，而不是罗列技术。

**实际实现** — `docs/architecture.md` 有完整图。链路是
`api → services → repositories → models`，AI 层（`app/ai/`）横切，worker（`app/worker/`）
异步消费任务。

**标准回答** — 五层。接口层只做参数校验和响应组装；服务层承载业务编排；
仓储层是唯一写 SQL 的地方；AI 层封装 Provider、Prompt、RAG、Agent；基础设施层
管数据库、向量库和文件。横切三条约束：接口层不许写 SQL；AI 层只依赖 Provider 接口，
不依赖任何厂商 SDK；Agent 只能通过 Tool 访问数据。这条约束是可验证的——
`tests/unit/test_project_integrity.py` 会扫描整个包，任何越层引用都会让测试失败。

**追问** — "为什么不把 AI 逻辑放进 service？" 因为 AI 层要被多个 service 复用
（文档分析、RAG、规划、Agent），放进去会形成交叉依赖。"repository 里能写业务判断吗？"
不能，只能有查询和数据访问语义。

### 3. 为什么要单独做 Repository 层？直接用 SQLAlchemy 不行吗？

**考什么** — 是否理解分层的真实收益，还是教条式分层。

**实际实现** — `app/repositories/base.py` 提供 `BaseRepository`，
`knowledge_repo.py` / `work_repo.py` / `ai_repo.py` 是具体仓储。

**标准回答** — 有两个具体收益，不是形式主义。第一，查询被集中定义后可以复用和优化，
比如 `DocumentRepository.query()` 一处实现，列表、分页、筛选三个接口共用。第二，
它给了我一个强制检查点：我审计过"哪些地方会生成错误的 SQL"。这个审计真的抓到了 bug——
通用方法 `list()` 始终按 `self.model` 生成 SQL，用它查询子实体（比如用 AIRunRepository
查 ToolCall）会静默返回错误的实体类型。修复方式就是引入显式的
`list_of / get_one_of / count_of`，让跨实体查询必须写明目标模型。如果 SQL 散落在
service 里，这种错误会到处出现且难以发现。

**追问** — "会不会过度封装？" 会，如果仓储只是 `session.query(X)` 的转发就没有价值。
我的标准是：有复用、有复杂条件、或者需要被多个 service 共享时才建仓储。

### 4. 数据库为什么用 PostgreSQL？

**考什么** — 是否理解所选数据库的能力边界，而不是"因为大家都在用"。

**实际实现** — 22 张表，见 `app/models/`；`docs/database.md` 有逐列说明。
用到三个具体特性：JSONB（`ai_runs.request_payload`、`documents.metadata`）、
`SELECT ... FOR UPDATE SKIP LOCKED`（`jobs` 队列）、以及严格的唯一约束和外键级联。

**标准回答** — 有三处用到了 PostgreSQL 独有的能力。一是 JSONB：AI 的请求和结果结构
不固定，用 JSONB 既能存又能索引，不用为每种 AI 任务建表。二是 `SKIP LOCKED`：
后台队列靠它实现多 worker 安全抢占，不用引入消息中间件。三是完整的外键与级联：
删知识库要连带删文档和分块，数据库层面保证一致性比应用层删更可靠。
另外全文检索能力也留着——虽然中文没装分词器所以现在用的是 ILIKE + BM25 打分。

**追问** — "数据量增长 100 倍怎么办？" 分三块：文档表按 `owner_id` 分区；
分块表已经是只增不改的，可以按知识库分片；检索候选集是瓶颈，先加 Qdrant 的 payload
索引和 HNSW 参数，再考虑把稀疏检索搬到独立的搜索引擎（如 OpenSearch）而不是继续用 ILIKE。
"JSONB 会不会拖慢查询？" 只存不查就不慢，我确实只在执行详情页按主键取，没做 JSONB 索引。

### 5. 为什么要 Redis？缓存了什么？

**考什么** — 是不是"为了用而用"。

**实际实现** — `app/core/cache.py` 顶部注释里有一张表，写明了四类缓存、TTL 和失效策略。

**标准回答** — 四类，每类都有明确理由。**检索结果** 180 秒：一次混合检索要跑一次
embedding、一次向量检索和一次 SQL 候选集打分，是最贵的读路径。**Prompt 模板** 600 秒：
每次 AI 调用都要读，但很少变。**仪表盘统计** 30 秒：多个聚合查询，容忍短暂不一致。
**Embedding 结果** 24 小时、以 `(模型, 内容哈希)` 为键：embedding 是确定性的，
同一段文本绝不重复调用，重跑文档时命中率很高（实测 8/8 命中）。失效策略用的是
命名空间版本号（`bump_namespace`）——写 Prompt 时把版本号 +1，整个族一次失效，
比逐个删 key 更简单也没有竞态。

**追问** — "Redis 挂了怎么办？" 降级为无缓存并打 warning，请求照常成功，
`cache_stats()` 里能看到错误计数。缓存不是正确性依赖。"为什么不用 Redis 做队列？"
队列要保证"任务状态与业务数据同事务提交"，Redis 做不到；用 PostgreSQL 队列可以
让"创建文档 + 入队"在一个事务里完成，不会出现"文档存了但任务丢了"。

### 6. 你的分层里"应用层"和"领域层"在哪？

**考什么** — 是否照搬 DDD 名词却不知道对应什么。

**实际实现** — `app/services/` 是应用层，`app/domain/enums.py` 承载领域枚举
（`DocumentStatus`、`TaskStatus`、`RunType` 等），业务规则写在 service 里
（例如 `TaskService._VALID_TRANSITIONS` 的状态机、`_creates_cycle` 的环检测）。

**标准回答** — 我没有照搬 DDD 的四层命名。应用层就是 `services/`：它编排仓储和
AI 层，承载用例。领域概念以枚举和规则的形式存在——状态机的合法迁移表、任务依赖的
环检测、文档状态的推进条件都在 service 里，因为它们需要同时读仓储和做判断。
我选择不引入独立领域实体层，因为聚合根逻辑还不足以撑起一层抽象，硬拆会让简单的
CRUD 变成三倍代码。这是权衡，不是省略。

**追问** — "什么情况下会拆出领域层？" 当同一套规则需要在多个 service 复用，
或者需要脱离数据库做纯内存测试时。现在状态机已经接近这个边界。

### 7. 接口设计上你做了哪些统一约定？

**考什么** — 是否有 API 设计意识。

**实际实现** — `app/core/response.py`（信封与分页）、`app/core/errors.py`
（错误分类与处理器）、`app/api/deps.py`（分页依赖、鉴权依赖）。

**标准回答** — 四条。**统一信封**：成功 `{success, data, message?}`，
失败 `{success, error:{code, message, details}, request_id}`，前端只需要写一套解包逻辑。
**稳定错误码**：20 余种，`not_found`、`conflict`、`validation_error`、`ai_timeout` 等，
前端按 code 分支，不解析文案。**统一分页**：`{items, meta:{page, page_size, total,
total_pages, has_next, has_prev}}`。**可追踪**：每个请求带 `request_id`，
响应头回写 `X-Request-ID` 和 `X-Process-Time-Ms`，排查问题时一句话就能定位全部日志。

**追问** — "为什么不直接返回 200 加业务码？" 那样会丢掉 HTTP 语义，网关、监控、
浏览器缓存都没法按状态码工作。"错误详情会不会泄漏内部信息？" `debug=false` 时
未预期异常只返回通用文案，堆栈只进日志。

### 8. 前端为什么不用组件库？

**考什么** — 是否有产品与视觉判断，而不是只会拼组件。

**实际实现** — `frontend/src/components/ui/primitives.tsx`、`feedback.tsx`、
`overlay.tsx` 是手写的 Tailwind 组件；`tailwind.config.js` 用 CSS 变量定义语义色
（`bg-surface`、`border-subtle`、`text-muted`），深色为默认主题。

**标准回答** — 两个原因。一是这个项目的定位是"开发者工具"，视觉参考是
Linear / Notion / Obsidian 这类高信息密度、低装饰的界面，组件库的默认样式反而是负担，
覆盖样式的成本高于自己写。二是手写组件让我必须把状态想清楚：每个列表都要有
loading 骨架、empty 状态和 error 状态，这是设计约束，不是样式问题。
代价是开发慢一些，也没有现成的可访问性支持，需要自己补 ARIA。

**追问** — "团队协作会怎么选？" 如果团队大、迭代快，会用组件库换取一致性；
个人项目追求差异化和对细节的控制，手写更合适。

## B. RAG & retrieval

### 9. RAG 是怎么实现的？完整讲一遍。

**考什么** — 是否真的做过，还是只会说"向量检索 + 大模型"。

**实际实现** — `app/ai/rag/pipeline.py` 的 `RAGPipeline.answer()` 是完整链路。

**标准回答** — 九步。① 查询改写：用 `query_rewrite` 模板把口语化问题改写成 2–3 条
检索友好的查询，改写失败不致命，直接退回原问题。② 稠密检索：Qdrant 余弦相似度，
带知识库过滤，候选 40 条。③ 稀疏检索：PostgreSQL 用 ILIKE 生成候选，再在进程内按
BM25 公式打分。④ 融合：两路分数先 min-max 归一化，再加权求和
`α·dense + (1-α)·sparse`，α 默认 0.6。⑤ 重排：用词面特征重新打分。⑥ 上下文组装：
按序号拼成 `【资料 n】`，受 token 预算约束。⑦ 生成：Prompt 明确禁止使用先验知识。
⑧ 引用抽取：把回答里的 `[n]` 映射回 chunk_id。⑨ 追踪：检索元信息与来源全部落库。

**追问** — "为什么候选 40 条最后只用 8 条？" 40 是召回窗口，8 是送给模型的上下文量，
中间隔着融合和重排。候选太小会漏掉正确答案，太大则重排成本上升。"改写用了几次模型调用？"
一次，而且结果走 Redis 缓存。

### 10. 分块策略是怎么设计的？为什么不按固定长度切？

**考什么** — 是否理解分块对检索质量的实际影响。

**实际实现** — `app/ai/rag/chunker.py`，10 个单元测试覆盖。

**标准回答** — 三步，结构优先。① 先按 Markdown 标题把小节切开，保证一个分块不会
横跨两个不相关主题。② 小节内部按句子边界累积到目标长度（默认 900 字符），
而不是按字符硬切——硬切会把一句话截断，语义不完整。③ 相邻分块保留 150 字符重叠，
避免答案正好落在边界上时两边都只拿到半句。另外每个分块的向量化文本前面会加上
标题路径，比如 `JVM > 垃圾回收`，因为这个前缀补充了段落本身缺失的主题信息，
实测对中文技术文档的召回提升明显，也让引用展示更好读。

**追问** — "分块大小怎么定的？" 900 字符约 300–400 token，是权衡：太短上下文不足，
太长会稀释语义向量并浪费上下文窗口。中文技术文档 400–1000 字是常见区间。
"超长句子怎么办？" 单个句子超过 2 倍分块大小时会退化为硬切，否则永远切不完。

### 11. 为什么要混合检索？纯向量不够吗？

**考什么** — 是否理解向量检索的真实短板。

**实际实现** — `app/ai/rag/retriever.py` 的 `_sparse_search` 与 `_fuse`。

**标准回答** — 向量检索擅长语义相似，但对专有名词、编号、错误码这类字面匹配不敏感。
举个例子：用户搜"G1 与 CMS 的区别"，如果资料里写的是"G1 可以预测停顿，CMS 会产生碎片"，
向量能召回；但如果搜的是 `-XX:Metaspacesize` 这种参数名，向量可能完全找不到，
关键词一路却能精确命中。所以两路都要。融合时先归一化——稠密分数在 -1 到 1 之间，
BM25 分数是无上界的正数，量纲不同不能直接相加。

**追问** — "为什么用加权求和而不是 RRF？" 加权求和能保留分数幅度信息，
调参也更直观（α 就是稠密权重）；RRF 只用排名，对"两路都排第一"和"一路第一一路第十"
区分度不够。我保留了 RRF 作为后续对比实验的 TODO。"权重怎么调？" 中文技术文档
关键词一路贡献不小，实测 0.5–0.7 之间比较稳，默认 0.6。

### 12. 为什么中文不用 PostgreSQL 的全文检索？

**考什么** — 是否知道所选方案的具体限制，而不是想当然。

**实际实现** — `app/ai/rag/retriever.py` 里有一段注释说明原因。

**标准回答** — PostgreSQL 的 `to_tsvector` 默认没有中文分词器，需要额外安装
zhparser 或 pg_jieba 扩展。这个项目要求"装好 PostgreSQL 就能跑"，不能依赖用户去编译
扩展。所以稀疏一路改成两段式：先用 ILIKE 在数据库里生成候选集（利用索引做粗筛），
再把候选拉到进程内，用 Python 计算 BM25 打分。这样零扩展依赖，代价是候选集之外的
文档无法命中，所以候选数放大到 4 倍 top_k。

**追问** — "这样会不会很慢？" 候选集有限（通常几百行），打分是纯内存操作。
实测混合检索 30ms 以内。"数据量大了怎么办？" 就该换真正的搜索引擎了，
ILIRE 前缀匹配在百万级文档上不可接受。

### 13. 重排用了什么模型？

**考什么** — 会不会把"没做"包装成"做了"。

**实际实现** — `Retriever._rerank()` 是**词面重排**，不是交叉编码器。

**标准回答** — 说实话：没有用交叉编码器，用的是词面特征重排。四个特征——
查询词在分块正文中的覆盖率、二元短语是否命中、标题匹配度、以及长度先验
（200–1600 字符的片段更有用）。最终分数是 `0.65 × 融合分 + 0.35 × 词面分`，
保留 0.65 的权重是为了不让语义强相关但字面不同的片段被误杀。
不部署交叉编码器的原因是它需要下载几百 MB 的模型，与"本地优先、开箱即用"的定位冲突。
如果条件允许，正确做法是对融合后的 Top-20 做交叉编码重排，召回不变但精度会明显提升。

**追问** — "为什么不至少用个小的？" 那就要引入 torch 和模型分发，安装体积从几十 MB
涨到几 GB。这是明确的取舍，我把它写进了 README 的"未实现"清单。

### 14. 怎么保证模型不编造？

**考什么** — 是否有防幻觉意识，还是只靠 prompt 里写"不要编造"。

**实际实现** — `rag_answer` 模板 + `RAGPipeline` 的引用校验逻辑。

**标准回答** — 三层。**Prompt 层**：明确列出规则——只能使用资料片段、
每条结论必须标注 `[n]`、资料不足必须明说还缺什么、不要复述规则本身。
**数据层**：检索为空时根本不调用模型，直接返回"知识库中没有找到足够依据"，
并给出排查建议（确认文档状态、换关键词）。**校验层**：生成后解析 `[n]`，
只保留落在有效范围内的编号；如果一个编号都没有，会在回答后追加说明
"模型未在正文中标注引用编号，以下为本次检索使用的资料"，而不是假装有依据。
`grounded` 字段如实返回给前端。

**追问** — "如果模型标了编号但内容和编号不符呢？" 目前无法自动检测语义一致性，
这是已知局限。可行的改进是用第二个模型做归因校验，但会增加延迟和成本。
"引用能点到原文吗？" 能，每条引用带 `document_id`、`chunk_id` 和片段内容。

### 15. 检索不到内容怎么排查？

**考什么** — 排障思路，而不是背概念。

**实际实现** — 文档状态机、`GET /documents/{id}/embedding-status`、
`GET /ai-runs/{run_id}` 的 `retrieval` 字段、`GET /search` 的 `dense_hits`/`sparse_hits`。

**标准回答** — 从上往下查四层。① **文档层**：文档状态是不是 COMPLETED？
`embedding-status` 能看出有多少分块真正写入了向量库。② **检索层**：`/search`
返回的 `dense_hits` 和 `sparse_hits` 分别是多少——如果稠密 0 而稀疏有值，
说明是 embedding 或向量库的问题；如果两路都 0，是查询词或知识库过滤的问题。
③ **融合层**：`GET /ai-runs/{run_id}` 的 `retrieval` 里有 `unique_chunks` 和
`used_chunks`，能看出是召回不足还是上下文预算把内容截掉了。
④ **生成层**：看 trace 里的 `response_text` 和引用数量。

**追问** — "向量库和数据库不一致会怎样？" 会出现"向量命中但数据库没有对应行"，
`_hydrate` 会记录 `stale_vector_point` 警告并跳过，不会把无法引用的内容返回给用户。

### 16. 更换 embedding 模型会发生什么？

**考什么** — 是否考虑过真实运维场景。

**实际实现** — `app/infrastructure/vector_store.py` 的 `ensure_collection()`。

**标准回答** — 会失败，而且是**主动失败**。Qdrant 集合的向量维度是固定的，
新模型的维度不同时写入会报错。所以 `ensure_collection` 会比对集合现有维度和
embedding provider 报告的维度，不一致就抛出带明确指引的错误："Embedding 维度已变化
但集合已存在，请执行 `python -m app.cli reindex --drop` 或删除集合后重建"。
如果维度碰巧相同（比如都是 1536），不会报错但检索质量会崩——这是已知风险，
缓解办法是在分块表里记录 `embedding_model`，检索时可以按模型过滤。
集合是**惰性创建**的：第一次真正需要写入时才按检测到的维度创建，
所以从云端 1536 维切到本地 768 维不需要改任何代码。

**追问** — "重新索引要多久？" 取决于文档量。因为 embedding 结果按内容哈希缓存，
如果只是重建集合而模型没变，向量可以直接从缓存复用，很快；换模型则要全部重算。

### 17. 上下文窗口怎么控制？

**考什么** — 是否有 token 预算意识。

**实际实现** — `RAGPipeline._assemble_context()` 和 `app/ai/tracing.py` 的
`truncate_for_prompt()`。

**标准回答** — 给上下文分配固定预算（默认 6000 token），按检索得分从高到低填充，
每加一段就扣减预算，剩不到 200 token 就停。单个片段超长时先按预算截断再加进去。
同时我会统计 `context_tokens` 写进检索元信息，这样从执行记录里就能看出
"是召回不足还是预算把内容挤掉了"。注意我用的是自己实现的 token 估算
（中文按 1 字符 1 token、拉丁文按 4 字符 1 token），而不是 tiktoken——
因为 tiktoken 会在运行时下载 BPE 词表文件，与本地优先的定位冲突。

**追问** — "估算不准会不会出问题？" 会偏保守（估算值通常高于真实值），
所以留了 10% 余量。真实 token 数以模型返回的 `usage` 为准，那个是准确的。

### 18. 为什么要在分块前加标题路径？

**考什么** — 是否做过效果调优，而不是只看论文。

**实际实现** — `chunk_text()` 最后一步：`display = f"{breadcrumb}\n{content}"`，
同时把 breadcrumb 存进 `document_chunks.heading` 用于引用展示。

**标准回答** — 因为单独一段正文经常丢失主题。比如"默认比例 8:1:1"这句话，
脱离"新生代由 Eden 和两个 Survivor 组成"这个上下文，向量几乎无法匹配任何有意义的查询。
加上 `JVM 内存结构 > 新生代` 之后，这个片段既有正文语义又有主题语义。
副作用是分块长度增加了十几到几十字符，对 900 字符的目标影响很小。

**追问** — "会不会污染检索？" 标题词会重复出现在同一节的每个分块里，
理论上会略微降低区分度。用 BM25 的 IDF 能部分抵消——标题词在很多分块里出现，
IDF 自然下降。实测这个收益远大于损失。

---

### 19. 文档重复上传会怎样？

**考什么** — 幂等性和边界处理。

**实际实现** — `documents` 表上有 `UniqueConstraint(knowledge_base_id, content_hash)`，
`DocumentService.register_upload()` 先查重。

**标准回答** — 上传时按内容做 SHA-256，在同一知识库内查重。命中就删掉刚存的文件、
返回已有文档并标记 `duplicate: true`，不重新解析、不重新向量化。用内容哈希而不是
文件名，所以改名重传也能识别。同一份文件上传到不同知识库是允许的，因为
`knowledge_base_id` 参与唯一约束——不同知识库是不同语境。

**追问** — "如果只是改了一个字呢？" 哈希完全不同，会被当成新文档。
这是取舍：用哈希能保证绝对准确，代价是无法识别"近似重复"。
"并发上传同一文件会怎样？" 唯一约束会拦下第二个，返回数据库错误，
前端看到的是 500 而不是 409——这是已知的待改进点，应该捕获 IntegrityError 转成 409。

---

### 20. 为什么解析和向量化要异步？

**考什么** — 是否理解请求-响应模型的边界。

**实际实现** — 上传接口立即返回 202 和 `job_id`，`jobs` 表驱动 worker 处理。

**标准回答** — 因为这几步的耗时不可控。一份 20 MB 的 PDF 解析可能几秒到几十秒，
向量化要调用外部 API 或本地模型，网络抖动时更长。同步做会让 HTTP 请求超时、
占用连接、用户体验成谜。异步化后上传接口 100ms 内返回，前端拿到 job_id 后轮询进度。
另外异步还带来两个好处：失败可以重试而不需要用户重新上传；进度可以分阶段展示
（PARSING / CHUNKING / EMBEDDING），用户知道系统在做什么。

**追问** — "轮询会不会很浪费？" 只在前端可见且状态未终结时才轮询（react-query 的
`refetchInterval`），完成即停。"为什么不做 WebSocket？" 对一个单机项目来说，
轮询的实现和运维成本都更低，收益是延迟从 2 秒降到 200 毫秒——不值得。

## C. Agent & tools

### 21. Agent 和普通对话有什么区别？

**考什么** — 是否理解 Agent 的本质是"能改变状态"，而不是"回答更聪明"。

**实际实现** — `app/ai/agent/executor.py` 的 `AgentExecutor.run()`。

**标准回答** — 普通对话只产生文本，Agent 产生**副作用**。这个项目的 Agent
会真的创建任务、写笔记、建立知识关联——这些操作会落库，用户刷新页面还能看到。
所以 Agent 的核心问题不是"怎么让它更聪明"，而是"怎么保证它的动作是安全、可解释、
可回放的"。我的答案是三件事：工具必须有明确的参数 schema；每一步都记录在案；
执行有硬上限。截图里那次运行创建了 30 多个任务和一条笔记，全部有据可查。

**追问** — "怎么防止它乱建任务？" 写操作有配额上限（默认 40 次/次运行），
超过就抛错终止；并且每次运行的产物 id 都记录在 `agent_runs.created_entity_ids`，
出问题可以精确回滚。

---

### 22. Tool Calling 是怎么实现的？

**考什么** — 是调用厂商的原生 function calling，还是自己拼 prompt 解析。

**实际实现** — `app/ai/agent/tools.py`（接口与注册表）+ `executor.py`（循环）。

**标准回答** — 分两层。**工具层**：`Tool` 抽象类声明 `spec: ToolSpec`（名称、描述、
JSON Schema 参数）和 `is_write` 标记，实现 `execute(ctx, **kwargs)` 返回 `ToolResult`。
`Tool.run()` 负责参数校验（必填检查、类型转换、丢弃模型幻觉出的多余参数）、
写操作计数、异常兜底，把任何异常转成 `ok: false` 的结果而不是抛出。
**循环层**：把工具 schema 转成 OpenAI 的 tools 格式传给模型；模型返回 tool_calls 就
取第一个执行，把结果作为 `role: tool` 消息塞回对话，继续下一轮；模型不再返回工具调用
就结束。关键是 assistant 消息要带上 `tool_calls` 字段，tool 消息要带 `tool_call_id`，
否则 OpenAI 协议会 400。

**追问** — "模型返回的 JSON 参数不合法怎么办？" 参数解析失败时保留原始字符串，
校验层会给出明确错误，模型能看到错误并重试。"一次返回多个工具调用呢？"
只取第一个。Prompt 里明确要求"每次只能调用一个工具"，多工具并行会让依赖关系
难以推理，也更容易出错。

---

### 23. 如何防止 Agent 乱调用工具？

**考什么** — 安全边界设计，不是 prompt 工程。

**实际实现** — 五道防线，都在 `executor.py` 和 `tools.py`。

**标准回答** — ① **架构隔离**：Agent 拿不到数据库会话，只能调工具；
`ToolContext` 里虽然有 session，但那是给工具内部用的，Agent 无法直接使用。
② **参数校验**：每个工具的 JSON Schema 在注册时就确定，执行前强制校验，
模型编造的参数直接丢弃。③ **步数上限**：默认 8 步，可配到 16 步，到了就停。
④ **重复调用检测**：把 `(工具名, 排序后的参数)` 做签名，同一签名出现第二次就
判定为死循环，记录一条 SKIPPED 并终止。⑤ **写操作配额**：`max_write_ops` 默认 40，
超过抛错。另外只读工具和写工具在目录里明确标记，前端也会展示，方便用户预期。

**追问** — "为什么不做人工确认？" 对本地单用户工具来说太重。如果是生产环境，
写操作应该走审批流，这是我在文档里标注的改进方向。"提示注入呢？"
文档内容可能包含"忽略之前的指令"，但因为工具参数受 schema 约束、
且 Agent 无法执行任意代码，最坏情况是它调错工具，影响范围可控。

---

### 24. Agent 怎么保证能停下来？

**考什么** — 是否会写出死循环。

**实际实现** — `for step_index in range(1, steps_allowed + 1)` + 重复签名检测 +
`while...else` 分支处理"用满步数"的情况。

**标准回答** — 四个终止条件，任何一个满足就退出循环。① 模型不再请求工具，
返回最终答复——正常路径。② 步数用尽，`for...else` 的 else 分支会生成一条说明
"已达到最大步数"，而不是静默结束。③ 检测到重复调用。④ 模型返回空内容，
给出一条明确提示而不是空字符串。循环结束前一定会写 `agent_runs.final_answer`
和 `stopped_reason`，所以前端永远能显示"为什么停了"。

**追问** — "如果模型一直请求不同参数的同一个工具呢？" 签名不同就不会触发重复检测，
但步数上限兜底。"`stopped_reason` 有哪些值？" `final_answer`、`max_steps`、
`loop_detected`、`empty_response`。

---

### 25. 举一个你实现的工具，讲清楚它的实现。

**考什么** — 是否真的写过工具，还是只看了文档。

**实际实现** — `CalculatorTool` + `safe_eval()`，以及 `TaskCreateBatchTool`。

**标准回答** — 讲计算器，因为它最能体现"安全边界"。`CalculatorTool` 不调用 `eval`，
而是用 `ast.parse(expression, mode='eval')` 解析成语法树，然后递归求值，
只允许 `Add/Sub/Mult/Div/FloorDiv/Mod/Pow` 和白名单内的常量与一元运算符，
其他任何节点类型（属性访问、下标、推导式、lambda、名称引用）直接抛
`ValidationError`。另外限制表达式长度 200 字符、指数绝对值不超过 64（防止
`2**1000000` 打爆内存）、除零报错。10 个单元测试覆盖了 `__import__('os').system('ls')`
这类攻击载荷。

再说 `TaskCreateBatchTool`，它更"重"：先调用 `PlannerService.generate_plan()` 生成计划，
再调 `persist_plan()` 落库，最后把创建的任务 id 注册到 `ctx.artifacts`。
这样 Agent 的产物能被追溯到具体实体。

**追问** — "为什么工具里要再调一次规划？" 因为 Agent 的职责是编排，
具体怎么拆解任务属于服务层的能力，工具只负责把两者接起来。
"工具失败了怎么办？" 返回 `ok: false` 和错误信息，模型看到后会尝试别的路径，
最终答复里会说明哪一步失败了。

### 26. 工具和服务的边界在哪？

**考什么** — 是否理解"为什么不让 Agent 直接调 service"。

**实际实现** — `tools.py` 里所有工具方法体都是几行：导入 service、调用、包装结果。

**标准回答** — 工具是**面向模型的适配层**，服务是面向业务的实现层。工具做三件服务
不该关心的事：把自然语言参数校验成类型安全的值、把异常转成模型能理解的错误文本、
把结果裁剪成适合塞进上下文的大小（`to_payload(limit=2500)`）。
如果让 Agent 直接调 service，它就要面对 Python 异常、ORM 对象和可能很大的返回体——
这些都超出了模型能可靠处理的范畴。

**追问** — "会不会太薄没必要？" 有争议，但这层让"Agent 能做什么"变成一个可枚举的
清单（11 个工具），而不是"它能调任何 service 方法"。安全边界靠的是可枚举性。

## D. AI engineering

### 27. Prompt Version 为什么重要？

**考什么** — 是否把 prompt 当代码管理。

**实际实现** — `prompts` + `prompt_versions` 两张表，`app/ai/prompts/registry.py`。

**标准回答** — 因为 prompt 是系统行为的一部分，改一句话就能让输出完全变样，
但早期做法是硬编码在代码里，改了以后**无法回答"三天前那个奇怪的回答是用哪个
prompt 产生的"**。现在的做法是：prompt 存在数据库里，每次修改生成新版本（不可变），
只有一个是 `is_current`。业务代码按名字取用，AI 执行记录里保存
`prompt_name` 和 `prompt_version`。这样任意一次执行都能精确复现它当时用的 prompt。
还支持激活历史版本做回滚、以及一键恢复内置模板。

**追问** — "版本内容改了但没发布怎么办？" 有 `activate` 参数，可以创建新版本但不激活，
先灰度。"Prompt 存数据库会不会拖慢调用？" 有 Redis 缓存，写操作时 bump 命名空间版本，
读路径基本不查库。

### 28. 模型超时怎么处理？

**考什么** — 是否有生产级的失败处理。

**实际实现** — `app/core/retry.py` + `openai_compatible.py` 的异常分类。

**标准回答** — 三层。① **超时设置**：httpx 客户端设置总超时（默认 90 秒）
和连接超时（15 秒），两者分开是因为连接失败应该快速失败。② **错误分类**：
超时抛 `AITimeoutError`（可重试），401/403 抛 `AIAuthError`（不可重试，重试一万次
也没用），429 抛 `AIRateLimitError`（可重试），5xx 抛 `AIProviderError`（可重试），
返回体不是 JSON 抛 `AIResponseFormatError`（可重试）。③ **有界重试**：
指数退避 + 抖动，最多 3 次，且总耗时不超过 180 秒。抖动很重要——
没有抖动时多个并发请求会同时重试，形成"重试风暴"。

**追问** — "为什么总耗时也要限制？" 只限次数的话，退避到第 5 次可能已经等了 30 秒，
用户早就关页面了。总耗时预算保证请求在可接受时间内必然返回结果或错误。
"重试会不会重复计费？" 会，所以只对幂等的生成类请求重试，且记录 `retry_count`。

### 29. 模型返回非法 JSON 怎么办？

**考什么** — 结构化输出的鲁棒性。

**实际实现** — `app/ai/rag/pipeline.py` 的 `load_json_object()`。

**标准回答** — 三级降级解析。① 直接 `json.loads`。② 失败则剥掉 Markdown 代码围栏
（```json ... ```），很多模型习惯加。③ 还失败就用正则找第一个 `{...}` 片段再解析。
三级都失败才抛 `AIResponseFormatError`，并且带上原文前 400 字符方便排查——
这个错误是可重试的，因为下一轮采样可能就正常了。另外对于必须结构化的场景
（比如任务规划），调用时会传 `response_format={"type": "json_object"}`，
让支持该参数的厂商在解码层面保证 JSON 合法。

**追问** — "解析出来的 JSON 结构不对呢？" 每个消费方都有归一化逻辑。
比如 `PlannerService._normalise_plan()` 会检查每个阶段、每个任务，
丢弃缺字段的项、把非法的优先级映射成 MEDIUM、把字符串数字转成整数，
如果整个结构都不可用就生成一个最小可执行计划而不是报错。

### 30. 如何避免重复 Embedding？

**考什么** — 成本意识。

**实际实现** — `app/ai/rag/embedding.py` 的 `content_hash()` 与缓存逻辑。

**标准回答** — 缓存键是 `sha256(模型名 + \x00 + 文本)`，存在 Redis 里 24 小时。
embedding 是确定性的——同样的输入同样的模型必然得到同样的向量，所以这个缓存
永远不会"过时"，唯一需要担心的是模型换了，所以模型名参与哈希。
效果实测：重新索引同一批文档时 8 个分块全部命中缓存，一次模型调用都没发生。
另外入库时按批处理（默认 16 条一批），既减少请求数也避免单次请求过大。

**追问** — "Redis 里存 1536 维向量会不会太大？" 一个向量约 7 KB JSON，
1000 个分块约 7 MB，可以接受。如果更大应该用二进制格式或直接不缓存向量、
只缓存"是否已嵌入"的标记。这是一个可优化点。

### 31. Token 和成本是怎么统计的？

**考什么** — 是否有可观测性意识。

**实际实现** — `app/ai/tracing.py` 的 `RunRecorder` + `estimate_cost()`。

**标准回答** — 优先使用厂商返回的 `usage` 字段（准确），厂商没返回时用启发式估算
（中文 1 字符 1 token、拉丁文 4 字符 1 token）。每次 AI 调用都会把 prompt/completion
token 累加到 run 记录上——注意一次 Agent 运行包含多轮模型调用，所以要累加而不是覆盖。
成本用一张硬编码的价格表估算（每百万 token 单价），模型不在表里就返回 0 而不是瞎猜。
仪表盘上能看到 30 天总 token、平均延迟、失败率和估算成本。

**追问** — "价格表过期怎么办？" 它是估算用的，不影响计费。真要准确应该对接厂商的
账单 API。"为什么要显示成本？" 让用户知道 Agent 一次运行可能花多少钱——
那次创建 30 个任务的运行消耗了 13347 token。

### 32. 为什么要记录执行链路（AI Execution Trace）？

**考什么** — 是否理解 AI 系统的可观测性需求。

**实际实现** — `ai_runs`（主记录）+ `tool_calls`（工具调用）+ `ai_run_sources`
（引用来源）+ `agent_runs`（Agent 轨迹）四张表。

**标准回答** — 因为 AI 系统最难回答的问题是"它为什么这么答"。传统日志只有
"调用了模型"，没有上下文。这套追踪记录了：用的哪个模型、哪个 prompt 版本、
检索了什么（查询变体、两路命中数、最终用了哪些片段）、调了哪些工具（参数和结果）、
花了多少 token、延迟多少、重试几次、失败原因是什么。有了这些，
用户能理解结果，开发者能复现问题，出了问题能定位到具体环节。
前端把它做成"概览 / 请求 / 检索与引用 / 工具调用 / 响应"五个标签页。

**追问** — "存储会不会爆？" 有 `_sanitize` 做深度和长度限制（字符串截断到 8000 字符、
列表最多 200 项）。"会不会存敏感信息？" 请求体经过脱敏，密钥类字段会被替换成 `<redacted>`。

### 33. 本地模型支持怎么做的？

**考什么** — 是否真的理解"本地优先"的技术含义。

**实际实现** — `app/ai/providers/ollama.py`，配置切换即可。

**标准回答** — 实现了 `OllamaProvider`，走 Ollama 的 `/api/chat` 和 `/api/embed`。
切换只需要改 `.env`：`AI_PROVIDER=ollama`、`AI_BASE_URL=http://127.0.0.1:11434`、
`AI_MODEL=qwen2.5:7b`，Embedding 同理指向 `nomic-embed-text`。因为业务代码只依赖
`LLMProvider` 接口，一行代码都不用改。这样做让知识库和向量完全留在本机——
对隐私敏感的场景这是核心卖点。Ollama 的 embedding 接口有新旧两个版本
（`/api/embed` 支持批量、`/api/embeddings` 只支持单条），代码里做了兼容。

**追问** — "本地模型效果差怎么办？" 这是取舍。小模型的推理能力确实弱，
但流程是真实的，而且可以换成 14B/32B。文档里如实说明了这一点。
"有没有测过 Ollama？" 没有——开发机上没装 Ollama，也没配置云端 Key，
所有 AI 验证走的是第三种实现（确定性离线引擎）。这一点在 README 和验收清单里
都写明了，不会假装跑过。

### 34. 什么是"确定性离线引擎"？为什么要有它？

**考什么** — 会不会用"降级"掩盖"没做完"。

**实际实现** — `app/ai/providers/heuristic.py`，约 500 行真实算法。

**标准回答** — 它是一个不依赖任何模型的降级实现，但**不是 mock**。
Embedding 用的是哈希 n-gram 向量化：中英混合分词（拉丁按词、中文按二元组），
每个 token 用 blake2b 哈希到 384 维桶里带符号累加，TF 做次线性压缩，最后 L2 归一化——
这样相同文本必然得到相同向量，语义相近的文本余弦相似度也更高（有单元测试验证）。
生成部分用抽取式算法：句子按查询词覆盖率、信息密度和位置先验打分，选出最相关的
几句拼成答案；结构化任务（摘要、概念抽取、TODO 提取、任务规划）用 TF-IDF 关键词
排序和标题切分实现。它存在的意义是让"没配 Key"也能完整跑通全部流程——
否则项目就变成了"必须先付费才能看效果"。同时它**永远不伪装成模型**：
每次执行记录的 provider 是 `offline`，健康检查里 `degraded: true` 并给出原因，
前端顶部有明确提示。

**追问** — "这算不算没做完 AI 部分？" 不算，云端和本地两条路径都实现了，
只是当前环境没 Key 所以用第三条验证。我的取舍是：与其把功能做成"配置好才可用"，
不如提供一个可用的兜底并如实标注。"怎么保证它不产生幻觉？" 它只能做抽取，
输出全部来自检索到的原文，没有生成能力，所以反而不会编造。

## E. Data & concurrency

### 35. 任务依赖怎么设计？怎么防止环？

**考什么** — 图结构的处理能力。

**实际实现** — `task_dependencies` 关联表 + `TaskService._creates_cycle()`。

**标准回答** — 用一张关联表 `(task_id, depends_on_task_id)` 表示"A 依赖 B"，
带唯一约束防止重复。加依赖前做环检测：从候选依赖出发做深度优先遍历，
如果能到达当前任务，说明会成环，抛 409 并带上两个任务的标题。
另外拒绝自依赖（422）。任务状态为 DONE 时，会检查所有依赖是否完成，
未完成则拒绝（409）；完成一个任务后，会遍历它的子任务，
如果子任务的依赖全部满足就自动从 BLOCKED 改成 TODO。

**追问** — "深度优先会不会很慢？" 依赖图通常很浅（任务树深度限制 4 层），
而且遍历时有 visited 集合。"为什么不在数据库用递归 CTE？"
可以，但对这个规模没必要，应用层实现更容易测试和给出友好的错误信息。

### 36. 后台队列为什么不用 Celery？

**考什么** — 是否做过真实的选型判断。

**实际实现** — `app/worker/runner.py`，基于 `jobs` 表。

**标准回答** — 三个理由。① **Windows 兼容性**：Celery 在 Windows 上需要
`solo` 池或者装 eventlet，这个项目要在 Windows 上开箱即用。② **事务一致性**：
Celery 是"先提交业务数据、再投递消息"，中间可能失败导致文档存了但任务丢了；
用数据库队列可以让"创建文档 + 入队"在同一个事务里完成。③ **状态可直接查询**：
用户要看"处理到哪一步了"，任务状态就在同一张表里，不用再去 broker 里查。
技术上用 `SELECT ... FOR UPDATE SKIP LOCKED` 实现多 worker 安全抢占，
有限次重试（失败后把 `scheduled_at` 推到未来，实现退避），
启动时回收超过 15 分钟仍为 RUNNING 的僵尸任务。

**追问** — "Redis 也能做队列啊？" 能，但同样有事务一致性问题，
而且 Redis 的持久化保证弱于 PostgreSQL。"吞吐量够吗？" 单机演示场景足够。
真要提高就多开 worker，`SKIP LOCKED` 天然支持水平扩展。

### 37. 讲一个你修过的并发 bug。

**考什么** — 真实的调试能力。

**实际实现** — `Worker.start()` 和 `tests/integration/test_worker.py` 的回归测试。

**标准回答** — Worker 主循环原本是这样：`while not stop: claimed = await
self._fill_slots()`，而 `_fill_slots` 在所有槽位都忙时**直接返回 True 且没有 await
任何东西**。于是循环变成同步空转，事件循环永远没机会调度 `_process` 任务——
后果是整个进程冻结，因为 worker 是跑在 API 进程里的，连 `/health` 都不响应。
现象很迷惑：日志停在 `job_started`，数据库里任务是 RUNNING，端口在监听但请求无响应。
定位方法是查 `pg_stat_activity` 排除了数据库锁（只有一个 idle in transaction），
又用隔离脚本单独跑 ingest 发现完全正常，从而把范围缩小到"worker 调度"。
修复是：无论是否抢到任务，没有可用槽位时都必须 await（等停止信号或轮询间隔）。
回归测试测量的是"并发协程两次 yield 之间的最大间隔"，饥饿时这个值会是秒级。

**追问** — "为什么隔离脚本没复现？" 因为脚本里 `progress` 回调不查数据库，
而真正的问题在调度循环，不在 ingest 本身——这正说明隔离复现的价值：
能快速排除一半假设。"还有别的饥饿风险吗？" 有，`parse_file` 和分块是同步 CPU 工作，
文档特别大时会阻塞事件循环。彻底解决要把 worker 拆成独立进程（已支持）。

### 38. 数据一致性怎么保证？

**考什么** — 是否考虑过"两套存储"的经典问题。

**实际实现** — PostgreSQL 存分块，Qdrant 存向量，`vector_id` 做关联。

**标准回答** — 承认这是两套存储，无法用事务保证强一致，所以采用"以数据库为准 +
补偿"的策略。**写入顺序**：先写数据库分块，再写向量，向量写入成功才把
`embedding_status` 改成 EMBEDDED。**删除顺序**：先删向量再删数据库行；
如果删向量失败，记 warning 但继续删数据库——因为残留的向量点检索时会因为
数据库查不到对应行而被跳过（`stale_vector_point` 警告），不会返回给用户。
反过来如果先删数据库行、删向量失败，用户就会搜到无法引用的内容，更糟。
**重跑幂等**：重新入库前先按 `document_id` 删掉旧分块和旧向量，所以不会累积。
**失败可见**：部分向量化失败时文档状态仍是 COMPLETED，但 `error_message` 会写
"部分分块向量化失败（3/19）"，不隐藏问题。

**追问** — "有没有对账机制？" 没有自动对账，但 `GET /documents/{id}/embedding-status`
能对比"数据库里的分块数"和"已嵌入数"。定期对账是改进方向。

### 39. 文件上传有哪些安全考虑？

**考什么** — 安全基本盘。

**实际实现** — `app/infrastructure/files.py`，41 个单元测试。

**标准回答** — 五条。① **扩展名白名单**：只允许 `.md/.markdown/.txt/.pdf`，
并且做 MIME 一致性检查——声明 `text/html` 上传 `.pdf` 会被 415 拒绝。
② **流式大小限制**：边读边累加，超过 25 MB 立刻中断并删掉半成品文件，
而不是等读完再判断（否则内存会被打爆）。③ **文件名不可控**：
落盘名是 `uuid4().hex + 扩展名`，原始文件名只存数据库；路径穿越、
NUL 字节、Windows 保留名（CON/NUL 等）在 `sanitize_filename` 里全部处理掉。
④ **路径包含检查**：任何按存储路径操作前都调用 `ensure_within_root`，
解析真实路径后确认在存储根目录内，否则拒绝——有测试验证"删除根目录外的文件"
会被拒绝且文件安然无恙。⑤ **空文件拒绝**：0 字节直接报错并清理。

**追问** — "为什么不用原始文件名落盘？" 原始名可能包含路径分隔符、控制字符、
超长字符串，而且同一目录下会冲突。"病毒扫描呢？" 没做，写在了安全文档的
"未实现"清单里。

### 40. 如果数据量增长 100 倍，哪里先出问题？

**考什么** — 是否有性能直觉，而不是空谈"加机器"。

**实际实现** — 可以从代码里指出现有的瓶颈点。

**标准回答** — 按出现顺序：① **稀疏检索的 ILIKE** 最先崩。它是全表扫描加
前缀匹配，百万级文档时不可接受。方案是换成真正的全文索引（OpenSearch）
或给 PostgreSQL 装中文分词扩展。② **Qdrant 的内存**。HNSW 索引常驻内存，
我把 `on_disk=True` 打开了，但百万级向量仍需要规划分片。
③ **PostgreSQL 单实例写入**。分块表是最大的表，按 `knowledge_base_id` 分区，
或者把检索元数据单独拆出来。④ **Embedding 成本和时间**。
这时候批量化和缓存的收益会被摊薄，需要引入队列限流和增量索引。
⑤ **API 层的 N+1**。目前检索结果的水合是一次 `IN` 查询，没问题；
但如果加上权限过滤和标签，需要重新审视。

**追问** — "会先做哪个优化？" 先做可观测性——现在没有查询耗时直方图，
无法判断瓶颈在哪。加指标比猜优化点更重要。"会换向量库吗？"
不会，Qdrant 的能力还远没到瓶颈，换库的迁移成本高于收益。
