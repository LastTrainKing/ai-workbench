## 2. 为什么 P0 是这样的设计

### 2.1 它解决的具体问题

两轮里出现过两次同一类缺陷，而**当时所有检查都是绿的**：

| 缺陷 | 提交 | 现象 |
|---|---|---|
| 首页读 `summary.llm`，真实路径是 `summary.providers.llm` | `b8803fb` 修 | 对配好 Key 的用户说"未配置 API Key" |
| 角色图标渲染成豆腐块（字体无回退链） | `27d84a1` 修 | 图标不可读 |

**都不是逻辑错误，是投影错误**：数据是对的，屏幕是错的。而仓库里没有任何设施能回答
"渲染出来的内容与数据一致吗" —— `check_qml_pages.py` 只查能否加载，`verify_native_shell.py`
只查存在性，`check_layout.py` 只查几何。所以它们全绿，用户读到假话。

### 2.2 它断言的是渲染树，不是文件字符串

每条断言读真实 QML 对象的属性：

- `isVisible()` —— **沿父链求有效可见性**，所以"存在但被隐藏"不会冒充"显示出来了"。
  这是这个工具存在的技术核心：只读 `text` 属性会把隐藏的也算进来，那样断言没有意义。
- `text` —— 真实渲染的文本。
- `property()` —— 绑定**求值后**的值（不是源码里写了什么）。

分两组：

- **纯映射**（`QJSEngine` 直接求值 `theme.js`）：不需要界面，快、确定。覆盖取值与优先级
  规则、未知值回退、空值处理。
- **渲染**（无头加载真实 `Main.qml`）：覆盖"数据 → 屏幕"这一段。

### 2.3 断言经过变异测试

**一条从未失败过的断言不算证据。** 所以逐条注入了真实缺陷，确认它们会被抓住：

| 注入的缺陷 | 结果 |
|---|---|
| 把 `providers.llm` 改回 `summary.llm`（上一轮的真实 bug） | **3 条失败**，失败信息重现用户看到的症状 |
| 从 `contractSections` 删掉「限制」一节 | **4 条失败** |
| 让合同永远不可见（改页面侧绑定） | **3 条失败**，"渲染出 0 个章节标题" |

**第三次变异第一次没有失败，但错的是变异本身**：在 `EmployeeContract.qml` 内部加
`visible: false` 不产生任何效果，因为实例化处的绑定会覆盖组件自己的值。改到页面侧才生效。
这条记录下来：**不产生变化的变异什么也证明不了，而它看起来和"测试没用"一模一样。**
