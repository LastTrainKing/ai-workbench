## 1. 这一版最重要的一件事：真实端到端跑通了，并且它抓出了一个已发布的缺陷

前几轮列的第一号阻塞项是「一个真实员工跑完一个真实任务并产出交付物，这条链路没有端到端
跑过」。这一轮拿到了 API Key，跑通了，而且第一次运行就抓到一个**在 2.4.0 里已经发出去的
缺陷**。

### 1.1 链路本身是通的

`desktop-native/verify_employee_delivery.py` 驱动 `ServiceBridge`（窗口用的那条路径），
对真实本地栈、真实模型：

| 步骤 | 结果 |
|---|---|
| 雇佣员工（岗位 `assistant`） | 成功，36 个工具 |
| 派发任务「写一份关于本地优先软件的简短工作报告，保存为 report-local-first.md」 | 成功 |
| 执行 | 61 秒，`EXECUTING → COMPLETED` |
| 交付物 | `report-local-first.md`，1358 字节，484 字符 |
| 文件真实存在 | ✓ `…\.runtime\workspace\report-local-first.md` |
| 文件非空 / 可读 / 是正文 | ✓ 1358 字节 / 484 字符 |
| 验证证据 | `{"checks":[{"ok":true,"name":"file_exists","detail":"1,358 bytes"},{"ok":true,"name":"readback","detail":"484 chars"}],"passed":true}` |
| 出现在交付物列表 | ✓ |
| 员工状态回到 `idle` | ✓ |

**11/11 通过**（修复后复跑；修复前 11/15，失败的 4 项全部指向同一个缺陷）。

### 1.2 第一次运行抓到的缺陷

修复前那一次：文件照样生成了、登记了、有验证证据，但

```
build_runs.status  = COMPLETED
ai_runs.status     = RUNNING     ← 从没落库
ai_runs.finished_at= NULL
employees.status   = working     ← 停在这里，一夜没变
```

根因在 `backend/app/ai/agent/autonomous.py`：

```
1231:  self.controller.set_state(RunState.COMPLETED, "成功标准已满足")
1265:  if snapshot_id:  ... 快照
1276:  answer = await self._final_report(plan, state, all_evidence)   ← 又一次模型调用
1277:  return self._result(...)
```

**终态是个判决，不是结束。** agent 宣布成功后还要生成最终报告，之后 `_execute_run` 才落库、
才释放员工。而 `build_executor._watch` 只看内存里的 `controller.state` —— 于是它在一次**还
在写**的运行上盖了「完成」，并从里面收走了交付物。进程在收尾前退出，两条记录就永远停在那
里，没有任何东西会纠正它们。

这正命中任务书 §9.1「任务状态必须真实 / 禁止模型说完成 = 自动成功」。

**四处修复**（提交 `591fa2e`）：

1. `RunController.settled` 成为结束信号，由 `_execute_run` 的 `finally` 写入；`_watch` 等它。
   终态但一直不结束的，由 `SETTLE_GRACE_SECONDS`（180 秒）兜底并降级为 `WAITING_USER` ——
   从一个运行已经走过的状态里读出"成功"，只是同一句假话换个地方说。
2. 员工释放移进 `finally`，独立会话、不抛异常。之前它在正常路径上，中途任何异常都会把员工
   永久留在「工作中」。
3. 新增 `_reconcile_stuck_employees()`，启动时把 `working` / `waiting_approval` 收回
   `idle`。这两个状态都由进程内对象（agent 任务、审批 broker）驱动，重启就不再成立。
4. `_persist_run` 补写 `finished_at` 与 `latency_ms`。此前**每一**次自主运行都是"状态
   SUCCEEDED、结束时间为空"。

新增 `backend/tests/integration/test_run_settlement.py`，8 个用例，其中一个是这条不变式本身
的回归守卫：**设置终态不得让 controller 变成 settled**。

## 2. 界面：从"开发者控制台"到"员工工作台"

### 2.1 首页（§4）

原来是一屏计数器加三个按数据模型命名的列表：最近项目 / 最近任务 / 最近运行。用户生成了一个
文件，在这个页面上**找不到它**。

现在是：**问候 + 在岗员工 → 输入框 → 最近成果**。每一条成果都能直接打开，或者交回给员工
接着做。示例胶囊换成任务书给的那五个（帮我写毕业论文 / 整理资料 / 制作PPT / 分析代码 /
生成报告）—— 原来那四个描述的是产品功能（"根据知识库回答问题"），这五个描述的是用户想干的
事。

三块各自独立的状态（加载中 / 空 / 出错，各自可重试）保留，因为那是对的：坏掉的面板和慢吞吞
的面板必须长得不一样。

### 2.2 成果交付（§6）

交付物页每一行新增四个操作，固定宽度列，按钮的 x 不随文件名长短浮动：

**打开 / 在文件夹中显示 / 继续修改 / 重新生成**

「重新生成」重跑的是**原来那句请求** —— 从产生这份文件的运行里查出来，不是拿标题猜。猜出来
的目标会生成一个"看起来相关但不是你要的"文件，而按钮上写着"重新生成"。

**「导出」没有做，这是有意的。** 这个构建里没有任何文档转换器，一个转不了格式的按钮就是假
功能，任务书 §13 明确禁止。「编辑」由「打开」覆盖 —— 它把文件交给系统默认程序。

### 2.3 Agent 页（§5 + §7）

**这一页原先根本不走员工路径。** 它只有一个目标输入框，运行走的是通用 agent 路径 ——
员工在名册里存在、能显示、能收窄权限，但从这个页面发起的任务不经过任何一个员工。任务书
§12 的验收是「提出需求 → **AI 员工**执行」，中间那个词在这里是断的。

现在有「交给」一行：在岗员工列表，选一个，`start()` 通过 `startBuildRun(goal, employeeId)`
下发 —— 同一条会收窄权限、会把产出登记成交付物的路径。下面多一张「员工在做」卡片：谁在做、
什么状态、走到第几步、结果摘要，以及通往文件的入口。

**顺带修掉一个排序缺陷**：首页的「交给员工执行」把目标和 `autoStart` 一起丢过来，页面一挂载
就开始跑，而 `loadEmployees` 是异步的 —— 那一刻员工 id 还是空的。用户按的是"交给员工"，
跑起来的却是不带员工的通用路径，而且看起来完全正常。自动开跑现在会等名册（或等名册调用
失败，那也放行：一个什么都不做的按钮比一个通用执行更糟）。

**普通 / 专家模式**：导航栏底部的分段控件，按账号持久化在
`.runtime/ui-preferences/<owner>.json`。

- 普通模式：任务、状态、结果。
- 专家模式：再加上步骤、工具调用、结束原因、步数。
- 技术区块是**隐藏**而不是变淡。半透明的技术面板会让普通用户以为自己漏看了什么；想看的人
  会去开专家模式。
- 两个模式名都写出来，不用单个开关：开关只说明"现在是哪边"，用户得先知道另一边叫什么才能
  决定要不要按。
- 偏好文件与 `ai-config` **分开**：后者存密钥、带着密钥形状的校验，让"切换显示模式"经过读
  API Key 的那段代码是一条本不该存在的路径。读写都白名单到 `expert_mode`，类型不符的忽略
  而不做转换 —— 字符串 `"false"` 在 QML 里是真值，静默把"普通模式"读成"专家模式"。

### 2.4 界面层抓到的一个真缺陷

首页把 `summary.llm.api_key_set` 当成了数据源，而字段实际是
`summary.providers.llm.api_key_set`。**写错字段名在这条路径上不抛任何异常** —— 它只是让
`api_key_set` 永远是 undefined，于是首页对着一个刚配好 Key 的用户说"未配置 API Key"，并
把他送去重新填一遍。

这不是测试能抓到的：所有测试都在看有没有异常，而这里没有异常，只有一句假话。它是**抓图**
看出来的。

### 3.1 全量测试

| 阶段 | 结果 |
|---|---|
| 第一次全量（改动后） | **18 failed**, 1471 passed, 11 skipped |
| 修完后分组复跑 | 全部通过（`test_api_contract` 25/25；`test_schema_guard` + `test_release_freeze_stub_provider` 17/17） |
| **最后一次干净全量** | **未跑** —— 见下方说明 |

**那 18 个失败分两类，性质完全不同：**

**17 个是测试环境问题，不是代码缺陷。** `backend/tests/conftest.py` 用**环境变量**把 provider 钉成
`offline`，而环境变量在解析顺序里**低于**安装级 `ai-config.json`。我这一轮配了真实 Key，
于是那个文件压过了 fixture。修法不是改断言，而是**给测试一个自己的 runtime 目录** —— 没有
文件可读，就没有东西能压过环境变量，这个文件自己文档里承诺的"测试绝不碰开发数据"从愿望变成
了结构。同时从机器 runtime 继承 `qdrant-api-key.txt`（那不是 AI 设置；测试够不到 Qdrant 就是
在测另一个产品 —— 第一次修复时正好踩了这个，探针把 Qdrant 报成 down）。

**1 个是我在 2.4.0 引入的真回归。** 把 schema guard 的拒绝拆成"前向升级"和"未知版本"两条之后，
后一条的文案以「请人工核对」结尾 —— 说了有问题，没说做什么，而这恰恰是读者无从判断哪边落后
的那条分支。现在它点名 `alembic current` 与 `alembic history`，并且**故意不提**
`alembic upgrade head`：那是刚刚被拒绝的操作，对着一个比程序更新的库跑它只会什么都不做或倒退。

测试原本断言字面量 `alembic upgrade head`，所以它抓住了这次改动 —— 过时的是它的期望，不是代码。
断言改为"消息里有一个能跑的命令"。

**为什么最后一次干净全量没跑**：这一轮的时间用在了真实端到端与 §9.1 的真缺陷上，修完两组失败后
只做了分组复跑。**这是一个应当补齐的缺口**，不应被读成"全绿"。

### 3.2 一处校验器修正

`check_qml_pages.py` 在不提供 `shell` / `bridge` 上下文属性的前提下加载每个页面，然后按
名字过滤由此产生的报错。它认识 `shell`，不认识 `bridge` —— 于是
`AgentWorkbenchPage` 里**早就存在**的 `Connections { target: bridge }` 被报成坏页面。
另一种措辞（`Cannot call method 'request' of undefined`）又额外盖住了四个页面。

两者都已按"检查器的缺口，不是页面的缺陷"过滤掉，并且写成精确短语而不是宽松的
`of undefined`，免得真的坏绑定被一起吞掉。修正后 20/20 页面干净加载。

## 5. 剩余问题（未达到"可候选发布"的全部条件）

1. **多员工协作未做。** 任务书 §11 的「研究员工分析 → 写作员工整理 → 审查员工检查」没有实现。
   单个员工可以被指定、被收窄、被追踪，但员工之间不能交接。
2. **首次启动引导未完成。** §5.2 六步里第 1、4、5 步仍未实现。
3. **多用户隔离只有测试，没有真实第二个账号。**
4. **「导出」缺失**（无转换器，见 §2.2）。
5. **多显示器 / 混合 DPI、代码签名**：未验证 / 缺失。
6. **检索增强的引用真实性审查（§9.4）这一轮没有做。** 记忆上限（§9.3）同样只做了代码阅读，
   没有实测。这两项在任务书里是独立的审查条目，这一轮的时间用在 §9.1 的真缺陷上。
7. **最后一次干净全量测试未跑**（见 §3.1）。修完两组失败后只做了分组复跑。
8. **「普通/专家模式」只在应用内切换过，没有验证过重启后是否保持** —— 偏好文件在安装版里是
   0 个（因为我没在安装版里切过），写入路径的实测是在开发环境做的。
