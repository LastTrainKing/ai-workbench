## 1. 为什么记忆要"精纯"而不是全量向量化？

**想考**：你是在做产品，还是在做 demo。全量向量化是最省事也最没用的做法，能不能看出这一点，区分了有没有产品意识。

**真实实现**：`MemoryEvaluator` 五段判定链 —— 规则预筛 → LLM 结构化判定 → 去重 → 冲突检测 → 路由（≥0.8 直接入库，0.5-0.8 进候选，<0.5 或敏感丢弃）。真实跑下来 9 次评估写入 0 条。

**回答**：全量向量化有三个后果，每一个都会让产品变差。第一，**召回噪声**：你问"帮我规划学习计划"，它召回你上周说的"我今天吃了牛肉面"，然后一本正经地说"我记得你最近在关注饮食"。第二，**记忆库无限膨胀**：向量检索的成本和噪声随条数增长，而信噪比下降。第三，也是最要命的——**你无法解释它为什么记得这件事**。用户问"你为什么觉得我喜欢简洁风格"，你只能说"因为向量相似度 0.73"。

所以我的判定标准不是"这段话有没有信息量"，而是"**对未来的我有没有用**"。规则层先拦掉寒暄和一次性事务，模型再回答具体问题（是否长期有效、属于哪个 kind、置信度多少、是否敏感），最后按置信度路由。宁可少记，不要记错——**记错比不记更糟**。

**追问**：怎么防止模型什么都觉得值得记？
> 提示词里明确列了反例（「我正在做毕业设计」属于项目状态不值得存、「我今天吃了牛肉面」不值得），并且要求"置信度低于 0.5 就填低分，不要勉强"。加上 0.8 的直接入库门槛，中间那一档会落到候选区等用户拍板。

## 2. 记忆冲突怎么处理？为什么不允许自动覆盖？

**想考**：你有没有想过"两条记忆互相矛盾"这种情况，以及你对"自动"的边界在哪。

**真实实现**：`evaluate()` 里模型返回 `contradicts` 字段（矛盾记忆的编号），命中则生成 `memory_candidates` 行并标记 `conflicts_with`，**原记忆一个字节都不改**。

**回答**：不允许自动覆盖，因为**系统没有资格判断哪个是"更新"**。

用户说"我以后都用 React"，三个月后说"我以后都改用 Vue 了"。这两条里哪条对？只有用户知道——也许他真换技术栈了，也许他在说某个特定项目，也许他只是在吐槽。系统自动覆盖，等于替用户做了他才有资格做的判断。

所以矛盾不落库、不覆盖，而是**生成一条候选问用户**：「你之前说默认用 React，现在说改用 Vue，以哪条为准？」用户确认后才生效。

**这里有个真实的坑**：我最初用词法相似度做冲突检测——比较字符重合度，加上否定词和"改成/换成"这类切换词。它对**近义改写**有效，但对真正的矛盾**完全失效**：

```
已有：用户希望所有项目默认使用 React + TypeScript
新的：我以后所有项目都改用 Vue 了，不要 React
```

这两句意思相反，但用词几乎不重合，阈值永远不触发。测试直接把它暴露了——判定结果是 `active`，两条矛盾记忆并存。

修复方式是把这个问题交给模型：它本来就在被调用，多问一句"是否与已有记忆矛盾、矛盾的是第几条"，零额外成本。语义矛盾正是模型擅长而字符串比较不擅长的事。词法检查保留为兜底，覆盖"否定词翻转的近义改写"。

**追问**：模型判断矛盾会不会误报？
> 会，所以误报的代价被设计成"用户多点一次确认"，而不是"记忆被改错"。这个不对称是有意的——漏报会导致两条矛盾记忆并存，误报只多问一句。

## 3. 上下文预算怎么定？超了怎么裁剪？

**想考**：你知不知道自己每次往 prompt 里塞了多少东西。

**真实实现**：`ContextAssembler`，默认 1800 token 硬上限，按 知识 55% / 记忆 20% / 项目 15% / 档案 10% 分配，超出时按 **知识 > 记忆 > 项目 > 档案** 的顺序整块丢弃。

**回答**：预算不是拍脑袋定的。这个产品的主场景是"基于我的资料回答我的问题"，所以知识片段占大头；档案是压缩摘要，永远带但很便宜；记忆控制在最多 6 条——**检索召回 30 条塞进上下文不叫个性化，叫噪声加了个置信度分数**。

裁剪策略是**整块丢弃，不做块内截断**。半截的知识片段通常比没有更糟，因为模型看不出它是不完整的。唯一的例外是档案：如果预算只剩一点，宁可保留一段硬截断的档案摘要，因为"你是谁"是唯一值得牺牲完整性的信息。

每次组装的实际内容写进 `context_snapshots`，包含逐字渲染的文本。所以"它当时知道什么"是可以事后回答的，不是一个说法。

**追问**：档案为空怎么办？
> 正常状态，不是错误。`assemble()` 返回空块，`render()` 返回空字符串，调用方拿到空串就照常往下走。新用户从第一天起就能用，不需要先填表。

## 4. 个性化会不会削弱权限安全？

**想考**：你有没有把"更懂用户"和"更听话"混为一谈。

**真实实现**：偏好只改**默认值**，`PermissionManager` 完全不读偏好；`AUTONOMOUS` 模式下高风险操作照样弹确认框。

**回答**：不会，因为我在架构上把两者**分开**了。

偏好能影响的是：输出语言、文档风格、是否先确认（这是工作流偏好）、默认工作目录。偏好**不能**影响的是：路径白名单、命令风险分级、确认阈值、资源上限。

具体说，`user_preferences` 表里存的是 `output_style`、`ppt_style`、`code_change_needs_confirm` 这类键；`PermissionManager` 读的是 `AgentPolicy`，两者之间**没有代码路径**。用户说"以后别问我了"改变的是"要不要弹确认框"的默认值，而不是"这个操作危不危险"的判断。

**安全不变式有一条可以验证**：我试过通过设置接口清空 denied 列表，`.ssh` 依然不可达——内置保护每次加载都会合并回来。**设置接口不是提权通道**，这一点是测过的，不是声称的。

**追问**：那用户想让 Agent 更自主怎么办？
> 提权限级别，那是显式的、有明确后果的操作。而且即使提到最高级，高危命令（格式化、注册表、提权）仍然确认。

## 5. 为什么 Agent 不能直接操作数据库？

**想考**：你知不知道分层是为了什么，还是只是在背模式。

**真实实现**：`Agent → Tool → Permission Manager → Tool Executor → Service → Repository → DB`。工具拿到的是 `ToolContext`（会话、权限、工作目录），没有任何仓储。

**回答**：三个理由，按重要性排。

第一，**权限无法审计**。Agent 直连数据库，它执行的是 SQL，不是工具调用。你没法对 SQL 做风险分级，也没法在"删一张表"之前弹确认框。工具化的价值就在于**每个动作都是具名的、可分类的、可拦截的**。

第二，**绕过业务规则**。仓储层承载了租户隔离、软删除、字段校验。Agent 写裸 SQL 等于把这些全部跳过——它可能"成功"地把别人的数据改成自己的。

第三，**审计粒度**。`tool_audit_log` 记的是"调用了 `file_write`，目标是 `x.py`，退出码 0"。如果 Agent 直连数据库，你只能记"执行了一条 UPDATE"，而这在事后没有任何诊断价值。

**追问**：那工具内部可以查数据库吗？
> 业务工具走 Service → Repository，这是正常路径。计算机工具（文件、shell）根本不碰数据库，它们拿到的是 `ToolContext` 里那个只读的会话引用，用来记审计。

## 6. 产物生成了，凭什么说它成功？

**想考**：你有没有把"没报错"当成"做对了"。

**真实实现**：`document_write` 的返回值里明确带 `verified: false` 和 `next_step: "调用 document_read 回读校验"`。Agent 必须回读并检查页数/行列数/大小，校验结果作为 VERIFY 步骤的证据。

**回答**：**生成成功不等于内容正确**，而"文件已生成"根本不算验证。

`document_write` 返回成功只说明一件事：库没抛异常、文件写进去了。它不说明这份 PPT 有 15 页还是 1 页，不说明 Excel 的公式算得对不对，不说明 Word 打开会不会报错。

所以工具自己在结果里写明 `verified: false`，并且 Agent 的 VERIFY 步骤必须用 `document_read` 取回客观证据——页数、行列数、文件大小、能否解析。这跟整个系统的验证哲学是一致的：**exit code 是唯一裁判，模型的自我评价不算数**。

实测数据：pptx 35729 字节 / 3 页、xlsx 6605 字节 / 1 表 + 1 图表 + 公式 `=SUM(B2:B3)`、docx 36794 字节 / 9 段、pdf 1824 字节 / 1 页。这些都是回读出来的，不是写入时记的。

**追问**：如果 document_read 也坏了呢？
> 那它也会返回失败，因为读不出来就是读不出来。工具不做"读不到就说成功"这种降级。

## 7. 为什么"诊断类步骤"非零退出码算成功，而"断言类步骤"必须为零？

**想考**：你对"验证"的理解是机械的还是带判断的。

**真实实现**：`is_diagnostic_step()` 检查步骤描述里的关键词（记录/读取/观察/定位/分析/列出/复现），命中则"产出真实输出"即为通过；其余步骤仍由 exit code 裁决。

**回答**：因为**两类步骤的目的不同**。

"运行测试并记录哪些失败了"——这一步的目的是**看到失败**。`pytest` 返回 1 说明它正常工作了，返回 0 反而说明没找到测试。把 exit 1 判成步骤失败，Agent 会反复重试诊断，永远走不到修复那一步。

"修复 median 函数"——这一步的目的是**让测试通过**。exit 1 就是失败，没有讨论余地。

这个区分是**被测试逼出来的**。Demo 2 里 Agent 连续四次失败：它明明已经正确定位到 bug（`median` 偶数长度取上中位数而不是平均），但诊断步骤被判定失败 → 重试 → 再判定失败 → 耗尽重试次数。日志显示它的分析一直是**对的**，是判定规则错了。

修复后加了一条硬性约束：诊断判定**只看步骤描述**，不看模型的自我陈述。模型不能说"我诊断完了所以通过"——它必须真的产出了输出。

**追问**：关键词匹配会不会误判？
> 会。一个描述里既说"分析"又说"修复"的步骤可能被误判为诊断。所以关键词表是保守的（偏向断言），而且误判的后果是"多跑一次"，不是"放过一次失败"。

## 8. 如果记忆库增长 100 倍怎么办？

**想考**：你有没有想过规模问题，以及你的设计里哪些地方会先坏。

**真实实现**：当前 `_existing()` 取最近 60 条做去重与冲突检测；`_memory_block()` 取最多 80 条按 `confidence × recency × use_count` 重排后取 6 条。

**回答**：先坏的地方是**去重与冲突检测**，因为它现在是 O(n) 线性扫描。

现在这个量级下扫描是对的——几十条记忆，比建向量索引便宜得多，而且逻辑透明可调试。涨到几千条时需要换成分层检索：先用向量粗召回候选集（top 50），再在候选集内做精确的语义比较。**关键是"语义比较"这一步不能省**，因为冲突检测恰恰是向量相似度不可靠的地方——两条矛盾记忆的向量可能很接近，也可能很远。

第二坏的是**注入选择**。现在按 `confidence × recency × use_count` 打分，这个公式在数据稀疏时表现好，在数据密集时会偏向老记忆（use_count 累积）。到时候需要引入**查询相关性**——现在是"取最有用的 6 条"，应该变成"取与当前问题最相关的 6 条"。

第三，**归档机制**。现在有 `archived` 状态但没有自动归档策略。长期应该有：连续 N 天未被使用且置信度下降的记忆自动归档，并通知用户。

**追问**：为什么不现在就上向量检索？
> 因为现在没有证据表明它是瓶颈。60 条记忆的线性扫描耗时可以忽略，而向量检索会引入一个不透明的中间层——去重为什么没生效，会变得很难查。**先让它正确，再让它快。**

## 9. 三层套娃的关窗 bug 是怎么找到的？

**想考**：你遇到查不出的问题时怎么办——猜，还是取证。

**真实实现**：`lifecycle.rs` 的生命周期日志，写绝对路径 + TEMP 回退，**每个 early-return 分支都留痕**。

**回答**：这个 bug 我猜错了两次，最后是日志解决的。

用户反馈"关掉窗口后 PostgreSQL、Redis、Qdrant、API 全都还在跑"。我的第一反应是"关窗钩子没触发"——**这是推断，不是事实**。加了全链路日志之后，事实完全不是这样：

```
startup: begin
startup: job object ready (before any branch)
startup: backend already healthy, returning early
event: ExitRequested                              ← 钩子触发了
event: ExitRequested -> calling stop()
stop: entered
stop: killing launcher tree pid 37624
stop: root from state: C:\Users\user\Desktop\ai-workbench
stop: running ...\stop-desktop.bat
stop: shutdown script exited with exit code: 0    ← 从 255 修复为 0
stop: finished
```

三层套娃：

1. **钩子确实触发**——我错了
2. **`project_root` 是 None**：启动流程发现后端已在运行就提前返回，从没写入过这个字段，`stop()` 在守卫处直接 return。而"重开程序"正是用户每次都走的路径
3. **真正的拦路虎**：`stop-desktop.bat` 的 REM 注释里含 UTF-8 破折号。**cmd.exe 按 ANSI 读 .bat**，字节被破坏后注释里的词被当成命令执行：

```
'actually' 不是内部或外部命令
'Redis' 不是内部或外部命令
```

脚本在停止任何服务之前就 255 退出了。**修好第 1、2 层它依然跑不起来**，因为脚本自己是坏的。

**追问**：为什么一开始没想到编码问题？
> 因为它不可见——文件在编辑器里看起来完全正常。教训是：Windows 上 `.bat` 必须纯 ASCII，`.ps1` 含非 ASCII 必须带 UTF-8 BOM。这两个现在都靠**检查脚本**覆盖，不靠记忆。这一轮我逐个验证了 10 个 `.ps1` 全部带 BOM、所有 `.bat` 纯 ASCII。

## 10. 作业对象是什么？为什么需要它？

**想考**：你对 Windows 进程生命周期的理解。

**真实实现**：`CreateJobObjectW` + `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`，在**任何分支之前**创建，把 launcher 加入其中。

**回答**：服务是 `Start-Process -PassThru` **detached** 启动的，所以它们**不在 launcher 的进程树里**。`taskkill /T` 只能杀掉树，够不着它们——这是第一层保险为什么不够。

作业对象是 Windows 内核提供的进程分组机制，`KILL_ON_JOB_CLOSE` 的语义是"最后一个句柄关闭时，杀掉组里所有进程"。桌面应用进程消失时句柄自然关闭，所以：

- 正常退出 → 作业触发，服务被清理
- **崩溃** → 进程消失，句柄关闭，服务被清理
- **`taskkill /F` 强杀** → 同上

这是唯一能在"进程被强杀"这种情况下还保证清理的机制。句柄故意**不主动关闭**——限制在最后一个句柄关闭时触发，进程退出会替我们关；提前关会在窗口还开着的时候杀掉后端。

**这里也有个真实的坑**：作业对象最初写在 spawn 分支里，于是"后端已在运行"的早退路径**根本不创建作业对象**。而测试没发现，因为每个场景前都先全停服务，永远走 spawn 路径——**测试形状的漏洞**。是读日志时发现早退路径没有 `job object ready` 那行才暴露的。

**追问**：孙进程会逃逸吗？
> Windows 8+ 的嵌套作业语义下不会。实测也证实了——三种退出场景（优雅关窗、强杀、双重启动后强杀）残留进程数都是 0。

## 11. 你怎么保证"Agent 说成功"和"实际成功"一致？

**想考**：你有没有想过模型会撒谎，以及你用什么机制防它。

**真实实现**：VERIFY 是一次**工具调用**，读它的 exit code。`EVIDENCE_TOOLS` 里的工具非零退出即失败。

**回答**：核心设计是**模型决定做什么，代码决定是否成功**。

验证不是让模型评价自己的输出，而是让它产出一个"能证明这一步的工具调用"，然后读那个调用的 exit code。`run_tests` 返回 1 就是失败，模型说"问题应该解决了"没用。

这个约束在 Demo 2 里被真实验证过：Agent 修好 `median` 之后，`run_tests` 返回 0，最终核验通过，状态 `COMPLETED`。我独立核验——`pytest` 19 passed / exit 0、git diff 恰好 2 行、只改了 `analyzer.py` 没动测试、原本失败的 `TestMedian` 类 6 个全过。**Agent 说的和实际发生的是一致的**。

**追问**：如果模型故意调用一个必然成功的工具来"通过"验证呢？
> 提示词要求"调用一个能取得客观证据的工具"，并给了示例（测试用 run_tests、检查文件用 file_exists）。如果它调用 `file_exists` 来"验证"一个逻辑修复，那是提示词层面的问题——但结果是**可审计的**：`context_snapshots` 和事件流里都能看到它调用了什么。透明本身就是防线。

## 12. 快照回滚怎么防止覆盖用户的新改动？

**想考**：你有没有想过"回滚"这个操作本身的危险性。

**真实实现**：快照记录**两份 manifest**（捕获时 + 运行结束后），回滚对比第二份；不匹配则报冲突，默认拒绝。

**回答**：危险序列是这样的：

```
1. 快照 A
2. Agent 改成 B
3. 用户改成 C
4. 回滚 → 会静默销毁第 3 步用户的改动
```

所以快照存两份清单：捕获时的状态，和**运行结束后的状态**。回滚时拿当前状态跟第二份比——如果某个文件已经不是运行留下的样子，说明有人动过，回滚就停下来报告冲突，而不是覆盖。

实测：模拟用户改 `demo_math.py` 之后，不带 force 的回滚返回 `restored: false, conflict: true`，理由是 "This file was modified after the agent finished"；带 force 才执行。

**追问**：为什么不直接问用户？
> 问了。冲突列表返回给前端，UI 展示"这 3 个文件在 Agent 结束后被修改过"，然后才给"强制回滚"按钮。**默认保护当前修改，强制是显式选择**。

## 13. 42 个工具是怎么组织给模型看的？

**想考**：你有没有想过 prompt 的 token 成本和模型的选择质量。

**真实实现**：`UnifiedToolRegistry` 一个目录两个执行路径，`_tool_catalogue()` 按能力域分组渲染，标注风险与是否需确认。

**回答**：分成两块呈现。业务工具（知识库、任务、项目）在前，因为原有提示词是围绕它们写的；计算机工具按能力域分组（filesystem / code / terminal / git / project / process / network / observation），每个工具标注 `[写]`、`[需确认]`。

这个顺序不是随意的——把已有工具放前面，意味着旧提示词的选择行为不变；新工具是**增量**，不是替换。

模型需要知道的另一件事是**哪些调用会停下来问用户**。所以 `[需确认]` 标记直接写进目录，这样它会更倾向于选择窄工具（`file_read`）而不是宽工具（`terminal_exec`）——不是因为它怕被拒，而是因为它知道宽工具会打断用户。

**追问**：42 个工具会不会太多，影响选择准确率？
> 会，这是真实的权衡。缓解方式是分组 + 风险标注。另一个方向是按任务裁剪目录（这个任务只给文件工具），但那会让"Agent 能自己决定用什么"这个卖点变弱。当前选择是保留全量但做好标注。

## 14. 审计日志为什么记录被拒绝的调用？

**想考**：你理解"审计"的目的是什么。

**真实实现**：`tool_audit_log` 每次调用都写，包括 `decision=deny` 的；工具内部抛出的 `PermissionDeniedError` 会把 verdict 重写成 deny 并带上 risk 与 target。

**回答**：因为审计要回答的问题是"**它试图做什么，我们拦住了什么**"。只记成功执行的日志，回答不了后半句。

这里也有个真实缺陷。原本工具内部的拒绝（比如 `file_read` 被允许、但它拿到的路径在 deny 列表上）在审计里记的是 `decision=allow`——因为工具级的粗检通过了，路径检查发生在工具内部。**一条把自己拦下的操作记成"允许"的审计日志，比没有审计更糟**，因为它让人以为有保护。

修复后：`.ssh`、`C:\Windows`、项目 `.env` 三条都记 `deny / high / DENIED` 并带正确的 target；工作区写入记 `allow / low / SUCCEEDED`。

另一个缺陷是 `target` 列为空——审计的价值就在回答"动了哪个文件"，空着等于没用。现在从参数推导（优先 path / command / url）。

## 15. 为什么 `ApiResult` 要抛出而不是返回错误？

**想考**：你对错误处理风格的理解，以及一致性。

**真实实现**：`request()` 抛异常，`requestResult()` 返回 `{ data }` 并在失败时抛。前端用 try/catch 或 React Query 的 error 状态。

**回答**：让**成功路径不需要分支**。

如果 API 返回 `{ ok, data, error }`，每个调用点都要写 `if (result.ok)` —— 漏写一次就是一个静默的 null。抛出的话，成功路径是直线代码，失败路径统一由 React Query 的 `isError` 或 try/catch 处理。

这个选择在写 `useAgentRun` 时暴露过一次：我按 `{ ok, data, error }` 的形状写，typecheck 直接报错——因为实际类型是 `{ data }`。**类型系统替我发现了假设错误**，这正是它该做的事。

**追问**：那怎么区分"业务失败"和"系统失败"？
> HTTP 状态码。404 是"不存在"，422 是"参数不对"，401 是"没登录"。UI 按状态码决定展示方式，而不是靠字符串匹配错误消息。

## 16. 你怎么发现"900 行 React 里藏着 bug"？

**想考**：你的验证方法是不是只有 typecheck 和 build。

**回答**：用真实浏览器点。`scripts/verify-agent-ui.mjs` 用 playwright-core 驱动系统 Edge，**点击真实按钮并断言渲染结果**。

typecheck 通过、lint 干净、build 成功——这三样加起来**证明不了按钮连着后端**。它们只能证明代码语法正确、类型匹配、能打包。一个把 `onClick` 写成 `onClick={() => {}}` 的按钮，三样全过。

所以断言的是**网络请求**：点暂停 → 必须出现 `POST /pause`；改模式 → 必须出现 `PATCH /agent/permissions` 且刷新后保持；切能力开关 → 必须出现 `PATCH /agent/capabilities`。以及轮询行为：终态后请求数不再增长、离开页面后不再增长。

这一套在 Agent 页面找到 3 个真 bug，在 Personal Context 页面 22/22 通过。

**追问**：为什么不写单元测试而要驱动浏览器？
> 两个都要。单元测试验证逻辑，浏览器测试验证接线。这个项目里出问题的一直是**接线**——函数写对了，没人调用它，或者调用时传错了参数。那类问题只有真跑才能发现。

## 17. `MemoryEvaluator` 的去重为什么用字符相似度而不是向量？

**想考**：你有没有想过"什么时候简单方案是对的"。

**真实实现**：`_similarity()` 做归一化后的字符重合度，阈值 0.82。

**回答**：因为要去重的东西**主要是词汇现象**。

"我以后都用 React" / "我以后所有项目默认用 React" —— 这是同一个意思的两种说法，字符重合度很高。真正需要语义理解的是**矛盾**，而矛盾我已经交给模型了。

用向量的代价是：每条候选都要一次 embedding 调用（成本 × 时间），引入一个不透明的中间层（为什么这两条被判重复了？看相似度 0.83），而且阈值更难调。**在能用一个便宜且可解释的方法解决时，不要上重方案。**

**追问**：什么时候该换？
> 当出现大量"语义重复但用词不同"的漏判时。现在没有证据表明这是瓶颈——真实跑下来去重和冲突都工作正常。

## 18. 首次启动向导为什么要有"先随便看看"这个选项？

**想考**：你有没有站在用户角度想过第一屏。

**回答**：因为**第一屏要求用户先付出再获得，用户会直接关掉**。

产品还没证明自己有用，就先要用户填身份、阶段、目标——这是把成本前置到价值之前。而"先随便看看"让用户立刻进入产品，上下文随后续使用慢慢生长。

这不只是体验问题，也是**架构约束**：如果"档案为空"会导致系统异常，那"先随便看看"就走不通。所以 `ContextAssembler` 把空档案当作**正常状态**处理——返回空块，`render()` 返回空串，调用方照常往下走。

另一个入口"从介绍自己开始"也有个硬要求：**AI 抽取的结果必须用户确认后才写入**。所以 `POST /profile/extract` 只解析、不落库，返回结构化的字段让用户改，确认后走 `PATCH /profile`。这跟记忆候选是同一个原则——**系统提议，用户决定**。

**追问**：这不就是多一步吗？
> 是，但这一步是"看到它怎么理解我"的机会。用户写"我在准备考研"，系统理解成"考研学生"还是"考研辅导老师"，差别很大。让用户在这一步纠正，比让他之后在对话里反复纠正便宜得多。

## 19. 你的"验证"和"测试"有什么区别？

**想考**：你有没有区分这两个概念。

**回答**：**测试**是开发时跑的，验证的是代码逻辑；**验证**是 Agent 运行时做的，验证的是任务是否真的完成。

测试：`pytest`、`verify-agent-ui.mjs`、`test_context_api.py`。它们回答"代码对不对"。

验证：Agent 的 VERIFY 步骤，用工具取得客观证据。它回答"**这件事做完了吗**"。

两者的哲学是同一个：**用客观证据代替主观判断**。但作用点不同——测试防的是回归，验证防的是"Agent 自信地说它做完了"。

一个具体的例子：`document_write` 返回成功，测试层面它是通过的（工具没报错）。但验证层面它**还没完成**——工具自己在返回值里写 `verified: false`，要求调用方回读校验。**生成成功不等于内容正确**，这两件事必须分开。

## 20. 这个项目里你觉得最有价值的一个决定是什么？

**回答**：把验证交给代码，而不是模型。

> **模型决定做什么，代码决定是否成功。**

这个决定看起来只是实现细节，但它决定了整个系统的可信度上限。大多数 Agent 框架让模型给自己打分——它说"我修好了"，框架就信了，用户过两天发现什么都没修。这类系统在 demo 里很惊艳，在真实使用中不可信。

具体落地就是：VERIFY 是一次工具调用，读它的 exit code。`run_tests` 返回 1 就是失败，模型说什么都没用。

这个原则在 Demo 2 里被反复验证。Agent 修好了 `median`，测试通过，我独立核验确认——`pytest` 19 passed、git diff 恰好 2 行、原本失败的测试类全过。**它说的和实际发生的一致**。

更有说服力的是反例：这个项目里被抓到的每一个难查的 bug，都是**因为"我以为"和"实际是"不一致**。关窗钩子（我以为没触发，实际触发了）、作业对象（我以为生效了，实际只在一条路径生效）、冲突检测（我以为词法够用，实际语义矛盾完全漏判）。**每一次都是加日志/加测试之后才看到真相。**

所以最有价值的决定不只是"让代码验证"，而是它背后那条纪律：**写任何结论之前先问自己，我有日志、有输出、有文件能证明吗？** 这个项目三轮下来，我没有一次推断是对的——而每一次取证之后，问题都变得可解。
