软件工程实践检查清单

一、需求与设计阶段
1. 需求必须可验证。避免使用"高性能""易用"这类无法度量的词。
2. 每个需求条目要有唯一的编号，方便在设计文档与测试用例之间建立追溯关系。
3. 接口设计先于实现。先确定输入、输出、错误码，再写代码。
4. 数据库设计要给出主键、外键、唯一约束与索引的说明，而不是只画表结构。
5. 涉及状态流转的实体，必须画出状态机并说明非法流转如何处理。

二、编码阶段
1. 分层要清晰：接口层只做参数校验与响应组装，业务逻辑放在服务层，
   数据访问集中在仓储层。禁止在接口层直接写 SQL。
2. 不要吞异常。捕获异常后要么记录日志并转换为业务错误，要么向上抛出。
   空的 except 分支是最危险的代码。
3. 所有外部调用都要设置超时。没有超时的网络调用等于把系统可用性交给别人。
4. 重试必须有上限，并且要区分可重试错误与不可重试错误。
   认证失败重试一百次也不会成功，只会浪费配额。
5. 幂等性。文件上传、任务创建这类操作要考虑重复提交的场景。

三、测试阶段
1. 单元测试覆盖纯逻辑，集成测试覆盖跨模块协作，接口测试覆盖契约，
   端到端测试覆盖用户可见的关键路径。
2. 测试要覆盖失败路径：超时、非法输入、依赖不可用、数据不一致。
3. 不要为了覆盖率写没有断言的测试。

四、交付阶段
1. 提交前清理临时文件、密钥与本地绝对路径。
2. 敏感配置通过环境变量注入，模板文件与真实配置文件分离。
3. 文档要能让新人独立把项目跑起来。如果跑不起来，文档就是不合格的。

五、可观测性
1. 每个请求都要有可追踪的 request id，并贯穿所有日志。
2. 关键指标：请求量、错误率、延迟分位数、依赖健康状态。
3. 日志里禁止出现明文密钥与用户敏感信息。

六、常见反模式
1. 上帝类：单个类承担过多职责，超过一千行就应该拆分。
2. 隐式依赖：在函数内部直接创建数据库连接或 HTTP 客户端。
3. 过早优化：在没有测量数据的情况下引入复杂方案。
4. 复制粘贴：相同逻辑出现在三个地方时，就应该抽取。
